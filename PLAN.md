# План разработки продукта

## Цель текущего этапа

Подготовить реализацию PRD 0.7 по решению от 3 ноября 2026: backend Node.js LTS/TypeScript strict/Fastify, TypeBox/OpenAPI, node-postgres/Kysely, pg-boss и отдельные replay workers. Для обеих БД выбран обычный PostgreSQL; история использует нативные месячные partitions без TimescaleDB. Приоритет: перенос и использование рыночных данных другими приложениями. Frontend и minute-only семантика сохранены. Текущий результат — согласованный технологический PRD и план ниже; код приложения, развёртывание, commit/push и reboot в этом поручении не выполняются.

## План реализации и запуска

Статусы описывают фактическое выполнение, а не намерения. Все этапы реализации пока `pending`. Этапы идут последовательно по зависимостям; независимую UI-работу можно вести параллельно по зафиксированному OpenAPI. Сначала тест ожидаемого поведения, затем реализация и рефакторинг; особенности БД проверяются интеграционно на настоящем изолированном PostgreSQL, а не только mock-ами.

### 1. Каркас и обязательные проверки — pending

- Подготовить в одном репозитории независимо собираемые сервис данных, платформу и web. Зафиксировать поддерживаемые совместимые версии и lockfile; серверные внутренности не импортируются другим приложением вместо API.
- Создать Fastify/TypeBox каркасы, OpenAPI и клиентский контракт. Подготовить две БД/роли, миграции, health/readiness и тестовую конфигурацию без production-секретов.
- Подключить весь утверждённый frontend-стек. Настроить strict typecheck, type-aware ESLint, проверки Tailwind/shadcn, Vitest, Playwright, сборку и CI. Проверки дизайн-системы имеют positive/negative fixtures; семантический HTML и допустимые внутренности Radix не блокируются.
- Готово, когда чистый checkout проходит проверки, каждая сборка запускается отдельно, некорректные API-входы и запрещённые UI-стили/контролы тестируемо отклоняются.

### 2. Переносимая БД и read API сервиса — pending

Зависимость: этап 1. На малом детерминированном наборе реализовать каталог бирж/инструментов, точные numeric OHLCV, месячные partitions, уникальность инструмента/минуты и карту покрытия. Создание секций охватывает как новые, так и старые даты; отсутствующая секция не приводит к молчаливой потере бара.

- Реализовать add-only запись с обнаружением отличающихся дублей, API каталога/покрытия и пакетного чтения с ограниченными страницами. Чтение не создаёт загрузок.
- Зафиксировать UTC/Unix-секунды, различие открытия свечи и окончания сигнальной минуты, decimal-строки API, порядок/курсоры и поведение при конкурентном пополнении.
- Готово, когда внешняя тестовая программа читает известный набор и пробелы, неавторизованный доступ отклоняется, повторная/конкурентная запись не меняет сохранённые значения, память чтения ограничена.

### 3. Bybit и устойчивое пополнение — pending

Зависимость: этап 2. Реализовать в сервисе адаптер Bybit 1m, асинхронные задания pg-boss, checkpoints, общий адаптивный допуск запросов, постоянный сбор и восстановление пропусков. Сначала mock/recorded ответы и искусственные часы, затем ограниченная проверка публичного API на нескольких инструментах, без провоцирования бана.

- Покрыть пагинацию/открытую свечу, 10006/429/разные 403, явное ожидание и отсутствие заголовков, restart во время cooldown, общий бюджет нескольких клиентов.
- Повторные/пересекающиеся запросы используют общую работу; отмена одного клиента не отменяет нужное другим пополнение. Постоянный сбор независим от платформы сетапов.
- Готово, когда сервис сам наполняет отсутствующие интервалы, после прерывания продолжает без полной перезагрузки истории, не сокращает ожидания и показывает прогресс/причины неполноты.

### 4. Независимый перенос данных — pending

Зависимости: этапы 2–3. Проверить эту основную цель до массовой загрузки и масштабирования.

- Подготовить процедуру pg_dump/pg_restore всего сервиса: рыночные/служебные таблицы, версии, задания/cooldown и несекретная конфигурация. Секреты отдельно; исходная копия не удаляется.
- Создать отдельный экспорт рыночных рядов с метаданными и manifest. Независимый потребитель должен использовать его без платформы сетапов, работающего сервиса и служебных таблиц pg-boss.
- Восстановить в чистый обычный PostgreSQL без TimescaleDB, сверить количества, значения, диапазоны, пропуски и идентичность инструментов. Старый писатель остановлен перед переключением на новый.
- Готово, когда независимый API-клиент работает после переноса, сохранённая история повторно не скачивается, источник истины и адрес нового API однозначны. После появления детектора добавить контрольный свежий replay, не подменённый cache hit.

### 5. Детектор и сквозной live/replay — pending

Зависимость: этап 3; тесты чистого алгоритма можно начать после этапа 1. Реализовать один TypeScript-модуль `price_volume_spike`, используемый обоими режимами, и его версию/параметры. Точные тесты покрывают рост >=12%, объём строго >3x хотя бы одной из полных баз 30/7 суток, включение текущих пяти минут и отсечку >=300 секунд.

- Платформа запрашивает у сервиса нужный прогрев; отсутствующие минуты не заполняются нулями, частичный результат объясняет непригодные интервалы.
- Replay работает в отдельном ограниченном worker-процессе, читает порции через API и сохраняет checkpoints. API остаётся отзывчивым; lease/heartbeat не превращаются в deadline всего прогона.
- Готово, когда одинаковый записанный вход/параметры/начальное состояние дают одинаковые сетапы live и свежего replay; проверены отмена, восстановление и отсутствие дублей при повторной попытке. Измерить retained RAM, не хранить все бары в неограниченных JS-объектах.

### 6. Кеш, UI и уведомления — pending

Зависимость: этап 5; UI по API-контракту разрабатывается параллельно этапам 2–5.

- Реализовать раздельные live/historical списки и CSV-импорт, загрузку/покрытие, конфигурации, запуски, ленту сетапов и экспорт Unix-секунд/close. React Redux не заменяет серверное персистентное состояние.
- Добавить кеш точных ключей по инструменту, bulk hits/misses и сортировку; версия алгоритма меняется после его изменения. Догрузка данных кеш не инвалидирует. Проверить старый partial/empty результат, очистку по бирже/инструменту или целиком и гонку очистки с активным worker. Показывать объём/происхождение; не удалять отдельную историю запусков.
- Добавить UI-настройку возраста уведомлений default 60 секунд, Web Push для подтверждённых окружений и опциональный закрытый Telegram. Проверить отказ разрешения, истечение, повторную доставку и restart без обновления возраста; replay не рассылает историю.
- Готово, когда ключевой пользовательский путь проходит Playwright на desktop/mobile, библиотеки/стили проходят guard-проверки, сбои сервиса отличены от пустых данных, кеш и уведомления соблюдают PRD.

### 7. Пилот и ресурсные ограничения — pending

Зависимости: этапы 4–6. Постепенно расширять реальные инструменты/диапазон, сначала один replay одновременно с live. Не считать гипотезу 4–8 CPU / 8–16 GB доказанной достаточностью.

- Измерить row/index bytes обычного PostgreSQL, WAL/temp/backup, чтение через API, API latency, CPU и RAM workers, длительность restore. Оценки колонночного сжатия не применять к выбранной БД.
- Проверить bursts закрытия минут, background backfill и холодный/тёплый кеш без потери live-приоритета. Настроить пулы, порции, очереди, retention служебных записей; ценные ряды не удалять автоматически.
- Готово, когда целевой live-набор около 500 пар устойчиво работает при согласованных ресурсах и фоне replay. При нехватке ресурсов сначала ограничить параллелизм/исправить горячий путь; увеличение ресурсов или существенная смена технологий обсуждается по измерениям, не предполагается заранее.

### 8. Подготовка и контролируемый запуск — pending

Зависимости: этапы 4, 6–7. Базовый сценарий — ранее предложенный Docker Compose: постоянное хранилище PostgreSQL, независимо запускаемые backend/worker-компоненты и production HTTP/HTTPS-раздача Vite build. Конкретный ingress, домен/TLS, пути дисков, версии и доступы задаются при подготовке сервера; dev server Vite в production не используется.

- Подготовить воспроизводимые сборки, настройки без секретов в Git, миграции, backup/restore, ограниченные журналы, health/readiness, служебный автозапуск Docker и согласованные restart policies. Не добавлять boot-команду, отменяющую намеренную административную остановку.
- На отдельном тестовом стенде выполнить reboot и аварийные завершения, задержать БД/сеть. Проверить восстановление включённого сбора/live, checkpoints и cooldown, отсутствие двойных писателей/сетапов, сохранение выключенного состояния и сроков уведомлений.
- Перед запуском сохранить проверенную резервную копию, проверить свободное место/доступы и готовность восстановления. Сначала минимальный набор инструментов, затем расширение. Изменение текущего хоста, внешнего доступа и reboot допускается только в согласованной среде, не в рамках подготовки этого плана.
- Откат: остановить запись, вернуть совместимую версию приложения; при несовместимой миграции использовать проверенный backup или контролируемую обратную миграцию, сохранив новые данные отдельно. Не накатывать старый код на новую схему и не удалять историю автоматически.
- Готово, когда сервисы поднимаются без ручного входа после reboot, основной сквозной путь работает по HTTPS, данные восстанавливаются независимо от платформы, документация API и запуска соответствует фактическим сборкам.

## Готовность и границы

Основной результат: независимый переносимый источник минутной истории и работающая платформа нейтральных сетапов с одинаковым live/replay, осознанно устаревающим кешем и ограниченными уведомлениями. Доказательства: целевые тесты, API/e2e сценарии, измерения пилота, отдельный restore и reboot-тест. Нельзя называть реализацию готовой по одному успешному build.

До начала разработки отсутствуют только конкретные версии/операционные параметры стенда, а не согласование основного стека. Они выбираются внутри выбранных технологий; сведения о production-хосте, доступах и внешнем адресе потребуются перед развёртыванием. Сейчас нет разрешения на покупку инфраструктуры, торговые операции, массовое скачивание истории или перезапуск текущего хоста. План не запускает автономный цикл и не является выполненной реализацией.

## Следующее решение

Основные вопросы закрыты: >=12% за W=5 минут AND объём >x3 среднего за 30 OR 7 суток; полные обе базы, текущие W минут включены; временная отсечка 300 секунд. Нагрузка: один алгоритм, около 500 live-пар, свой сервер, без предельного времени replay. Формулы/OR/строгое превышение/границы cooldown и 43 200 минут проверены отдельным арифметическим тестом, не runtime-тестом приложения.

PRD 0.3 открыт в MarkText, версия/дата подтверждены прямым снимком. В буфере редактора замечен лишний несохранённый префикс неизвестного происхождения; на диске его нет. Он не сохранялся и не удалялся автоматически. Канонический файл проверен отдельно; чужие возможные правки редактора не затронуты.

Остаточные вопросы закрыты: нейтральный всплеск, UI-настройка возраста уведомлений default 1 минута, Web Push там, где технически доступен. Принят кеш на алгоритм/версию/все параметры/биржу-инструмент/точный период; data gaps/revision не ключ и не автоматическая инвалидация. В 0.5 первая БД принадлежит сервису данных: самодостаточная рыночная часть и отдельно служебное состояние загрузчиков. Вторая БД принадлежит платформе сетапов, включая кеш. Удаление кеша не удаляет исходную историю или сохранённые результаты.

- `completed`: проверить официальные правила Bybit и Web Push; общая IP-квота 600/5s, подтверждённый IP-ban pause >=600s, публичные заголовки не гарантируются, WS future limit с 26 ноября отделён от текущего состояния.
