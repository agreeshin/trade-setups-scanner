# Рыночные данные и их загрузка

[К оглавлению PRD](PRD.md)

Статус PRD 0.7: рыночные данные принадлежат отдельному переносимому сервису на Node.js/TypeScript/Fastify с обычным PostgreSQL без TimescaleDB. Сохранены собственный API, загрузчики, документация, USDT perpetual, add-only запись и две БД. Источник MVP: минутные данные API Bybit; полнота всех рынков не гарантирована.

## 1. Источник и идентичность данных

Первый источник: непосредственно API Bybit, **линейные бессрочные USDT-контракты**. Spot, inverse, USDC, опционы и срочные контракты не входят в MVP. Проверяется тип контракта, а не только суффикс USDT в названии.

Непосредственно с биржей работает **сервис рыночных данных**. Платформа сетапов получает каталог, покрытие и свечи через его API и не дублирует биржевые загрузчики. Сервис хранит как ранее загруженную историю, так и новые закрытые минуты; его назначение не ограничено одноразовым историческим импортом.

Ключ инструмента включает биржу, категорию/тип контракта, биржевой символ и сведения о жизненном цикле. `BTCUSDT` на двух биржах не один источник данных. Замена/переименование контракта не должна незаметно склеивать два разных исторических ряда.

История и восстановление пропусков получают минутные свечи из API биржи. Live получает закрытые минутные свечи через REST либо WebSocket API; выбор транспорта не меняет контракт стратегии. Текущие незакрытые обновления не используются для сигналов. TradingView, сторонние поставщики, архивы сделок и секундные свечи не входят в источник MVP.

У каждой записи/партиции сохраняются источник, версия нормализации, момент получения и данные о проверке полноты. Существующие закрытые свечи при обычной загрузке **не перезаписываются**. Отличающееся значение из API фиксируется как конфликт, не как разрешение автоматически заменить историю.

**Требование расширяемости:** контракт источника охватывает каталог инструментов, получение минутной истории, обновление и восстановление. Лимиты, пагинация, единицы и окончательность данных конкретной биржи локализуются в её подключении, а стратегия/replay работают с нормализованными данными. Добавление второй биржи не требует переписывать детектор, CSV и управление заданиями. Это критерий будущей архитектуры, не требование реализовать несколько коннекторов сейчас.

Будущая торговля использует отдельный контракт исполнения и полномочия, не маскируется под загрузку данных. Идентификатор биржи/инструмента сохраняется в сетапах уже сейчас, но ордера и торговые ключи в MVP отсутствуют.

## 2. Что подтверждено для Bybit

| Данные | Подтверждённая возможность | Существенное ограничение |
|---|---|---|
| OHLCV | V5 kline: 1m, 3m, 5m, 15m, 30m, часы, D/W/M; до 1000 строк за запрос; start/end в ms | Нативных секундных klines в этом endpoint нет; незакрытый close является текущей ценой |
| Live свечи | `kline.{interval}.{symbol}`, признак `confirm` | Частота обновлений 1–60 секунд; не секундный источник для гарантированного first-cross |
| Метаданные | Список инструментов, параметры/статус | Линейных инструментов больше 500; требуется пагинация, текущий список не равен историческому universe |

Официальные источники: [kline](https://bybit-exchange.github.io/docs/v5/market/kline), [архив сделок](https://public.bybit.com/trading/), [recent trades](https://bybit-exchange.github.io/docs/v5/market/recent-trade), [trade WS](https://bybit-exchange.github.io/docs/v5/websocket/public/trade), [kline WS](https://bybit-exchange.github.io/docs/v5/websocket/public/kline), [инструменты](https://bybit-exchange.github.io/docs/v5/market/instrument), [WS connection](https://bybit-exchange.github.io/docs/v5/ws/connect).

В выборочных запросах BTCUSDT успешно получены минутки за март 2020, январь 2021, январь 2023 и октябрь 2026. Это подтверждает практическую возможность многолетней минутной истории для этой пары, но не универсальный минимальный срок хранения API.

## 3. Исследованные архивы: вне выбранного продукта

Наблюдения ниже сохранены как результаты исследования альтернатив, а не требования к загрузчикам MVP. После решения владельца продукта исходные данные загружаются только как минутные свечи через API Bybit; архивный и секундный пути не реализуются.

Для Bybit подтверждён каталог [суточных архивов сделок BTCUSDT](https://public.bybit.com/trading/BTCUSDT/). На дату проверки в листинге было 2408 ежедневных файлов от 2020-03-25 до 2026-10-27 без пропущенных имён дат. Содержимое всех файлов не проверялось, и это не доказательство отсутствия внутренних пропусков.

Публичный файл `BTCUSDT2026-10-26.csv.gz` имеет размер 58 435 866 байт, около 58,4 MB. HTTP Range поддерживается, но обычный gzip не даёт произвольного поиска по timestamp без состояния распаковки или внешнего индекса. Старые файлы также могут иметь другой порядок строк. План «скачать только две минуты из любого суточного gzip» не принимается как установленная возможность.

Для Bybit здесь не подтверждён столь же простой и полный массовый каталог свечей, аналогичный Binance. Первоначально рассматривалась детализация из архивов сделок, но этот путь отклонён. Каталог [Historical Market Data](https://www.bybit.com/en/derivative-activity/history-data) существует, но полная номенклатура/покрытие скачиваемых order-book данных в исследовании не получены: HTTP 403.

У [Binance Public Data](https://github.com/binance/binance-public-data) официально доступны daily/monthly архивы klines, trades и aggTrades для поддерживаемых рынков, включая USD-M/COIN-M futures, с checksum-файлами. Это прямой положительный ответ на вопрос «бывают ли большие готовые архивы свечей». Их наличие не означает, что данные Binance можно подставлять вместо Bybit: цены, объёмы и сигналы бирж различаются.

Наличие архивов не обязывает продукт их использовать. Доступность, дата начала, схема и права проверяются по выбранным API и инструментам.

## 4. Объём и единицы

Свеча содержит не только цену, но и объём. Для линейного USDT-контракта Bybit `volume` измеряется в базовой монете, `turnover` в USDT. Для inverse единицы обратные: volume в котируемой валюте, turnover в базовой. Нельзя сравнивать поля разных категорий как одно число без нормализации.

MVP сохраняет минутные volume и turnover из той же свечной записи API, не восстанавливая их по сделкам. Выбор показателя для конкретного алгоритма задаётся явно; дополнительные trade-only признаки, такие как taker volume, не подразумеваются автоматически.

Нулевая активность и отсутствие данных различаются. Полученная от источника закрытая минута с нулевым объёмом не равна отсутствующей записи. При разрыве источника нельзя создавать «пустые» свечи и делать вид, что рынок стоял. Пропуск показывается и восстанавливается через API; алгоритм допускает к оценке только минуты с полным требуемым контекстом, остальные помечаются как пропущенные.

Результаты исследовательской реконструкции секундных объёмов и сверки одной минуты сохранены в [исследовании](research.md). Они не используются как основание добавлять trade-парсер в MVP.

## 5. Расширение состава данных

В MVP из таблицы ниже загружаются только минутные OHLCV, объём и оборот. Возможность позже добавить funding, open interest, mark/index price и long/short ratio является утверждённым требованием к расширяемости. Для будущих рядов должны различаться тип данных, инструмент/биржа, единицы, время наблюдения, время доступности и качество. Их нельзя заранее свести к необязательным «секундным» полям каждой свечи.

Конкретные таблицы/схемы и механизмы загрузки выбираются позже. Не требуются пустые таблицы на каждый возможный показатель, работающие фоновые загрузчики или дополнительная история уже в MVP. Добавление ряда не должно менять смысл старых свечей и сетапов.

| Тип | Для чего полезен | Что известно о Bybit | Приоритет |
|---|---|---|---|
| Last-price OHLCV, base volume, quote turnover | Базовый детектор, ATR/RSI/объём | Многолетняя история проверена выборочно | MVP |
| Mark/index price | Отклонение торговой цены от reference, фьючерсные фильтры | Исторические 1m endpoints; январь 2021 проверен для BTCUSDT | Расширение по стратегии |
| Funding | Контекст перегрева perpetual | История, до 200 записей; интервал зависит от инструмента | Расширение |
| Open interest | Изменение открытого интереса | История 5min/15min/30min/1h/4h/1d; январь 2021 проверен | Расширение |
| Long/short account ratio | Перекос числа участников | Исторический endpoint; в docs начало 2020-07-20 | Расширение, не путать с объёмом покупок/продаж |
| Premium index | Фьючерсная премия | Исторический endpoint существует; покрытие нужно проверять | Расширение |
| Ликвидации | Вынужденный поток и рыночные каскады | Live `allLiquidation`; полная старая история здесь не подтверждена | Не обещать в историческом MVP |
| Bid/ask, spread, order book | Исполнимость, дисбаланс, ликвидность | Текущие REST snapshots и WS deltas; история отдельным источником | Не MVP без конкретной стратегии |
| RSI, ATR, EMA, реализованная волатильность | Производные признаки | Рассчитываются из исходных рядов | По алгоритму, не обязательно хранить постоянно |

Ни funding, ни OI, ни account ratio нельзя интерполировать до минутной частоты и выдавать за реально наблюдавшиеся минутные значения. При будущей интеграции допустимо использовать последнее уже опубликованное значение с указанием возраста, если это определено стратегией.

## 6. Жизненный цикл данных

Администратор отдельно управляет первичной загрузкой, постоянным обновлением, live-сканером и replay. Выключение Telegram не выключает аналитику; остановка сканера не обязана останавливать накопление. Остановка сбора делает зависимые live-алгоритмы stale/paused, а не оставляет зелёный статус без данных.

Пользователь запускает историческую загрузку из UI, выбирая инструменты, дату начала и дату окончания. Предлагаемое отображение: обе даты включительно в UTC; внутренний диапазон `[00:00 первой даты, 00:00 дня после последней даты)`, явно показанный перед стартом. Будущие/ещё незакрытые минуты не считаются готовыми историческими свечами.

Система сначала определяет уже имеющиеся интервалы и пробелы, затем запрашивает недостающие данные. Она дополняет начало, конец и внутренние разрывы ряда; наличие min/max дат не означает сплошного покрытия. Повторная загрузка не меняет имеющиеся закрытые записи. Перекрытие API-страниц допустимо, но запись добавляет только отсутствующие ключи `(биржа, инструмент, 1m, начало минуты)` без дублей и upsert-перезаписи. Одновременные live/REST-записи соблюдают ту же уникальность.

Загрузка возобновляема и идемпотентна: прогресс по инструменту/диапазону, лимиты источника, backoff, ограниченная очередь, проверка границ и видимые ошибки. Пустой ответ не превращается в нулевую свечу. Исправление сохранённой истории может быть отдельной контролируемой операцией в будущем, но не скрытым поведением обычной догрузки.

### Адаптивная частота запросов Bybit

Все REST-запросы к Bybit, включая историю, восстановление live и ретраи, выполняются сервисом данных через общий контроль допуска с учётом общего исходящего IP. Все его API-клиенты используют этот общий бюджет. Нельзя выдавать каждому клиенту, инструменту или worker отдельную полную квоту. Другие процессы за тем же NAT могут расходовать лимит вне видимости сервиса; поэтому нужен запас, а отсутствие бана не гарантируется абсолютно.

На 1 ноября 2026 Bybit документирует **600 HTTP-запросов за 5 секунд на IP по умолчанию** и не рекомендует работать на границе. Это не 600 запросов/с и не обещанная скорость публичного kline endpoint. Лимиты per UID/per endpoint и заголовки `X-Bapi-*` являются отдельным механизмом, не измерением остатка общей IP-квоты.

Загрузчик начинает с консервативной частоты, плавно уменьшает интервал между запросами после устойчивого успешного периода и останавливает ускорение на настраиваемом безопасном потолке ниже опубликованных ограничений. При throttling интервал увеличивается. Например, небольшое аддитивное увеличение допустимой частоты и её кратное уменьшение после ограничения могут стать реализацией; коэффициенты выбираются в пилоте, это не требование Bybit. Намеренно ускоряться до бана или считать мягкое предупреждение обязательным нельзя.

| Ответ/состояние | Требуемое поведение |
|---|---|
| Валидный явный срок ожидания, включая `Retry-After`, если он действительно передан | Не отправлять запрос раньше срока. Учитывать секунды либо HTTP-date по формату поля; выбирать наиболее поздний из применимых сроков |
| JSON `retCode=10006` | API rate limit: снизить частоту, применить backoff и достоверный reset при наличии; не считать автоматически десятиминутным IP-баном |
| HTTP `429` | Частотная защита системного уровня: выдержать срок/backoff и снизить частоту; различать HTTP-статус и JSON-коды других API |
| HTTP `403` с `access too frequent` | Остановить HTTP-запросы приложения в затронутой общей IP-области, закрыть HTTP-сессии и ждать **не менее 600 секунд**, либо дольше по указанию сервера |
| Другой/неоднозначный `403` | Остановить агрессивные ретраи, показать диагностический статус: возможны ограничения доступа/географии или ошибочный GET с JSON-body, а не временная квота |
| Сетевой сбой/5xx | Отдельная ограниченная политика повторов; не объявлять всякий сбой rate limit и не уходить в tight loop |

Наличие `Retry-After` и `X-Bapi-*` у публичных kline-ответов **не гарантируется**. `X-Bapi-Limit`/`Status` относятся к соответствующему endpoint; `X-Bapi-Limit-Reset-Timestamp` после превышения сообщает reset, а в здоровом ответе может быть просто текущим временем. Его нельзя всегда интерпретировать как конец квоты. Биржевые timestamps в миллисекундах преобразуются в единую внутреннюю шкалу явно.

Cooldown имеет общий срок `not_before`: новый worker, другая загрузка и рестарт приложения не должны обходить ожидание. Во время подтверждённого IP-бана запрещены и «проверочные» HTTP-запросы до срока. После паузы разрешается осторожное восстановление с пониженной частотой, не залповый выпуск очереди. Дополнительный jitter может только продлить обязательное ожидание. Смена IP, ключей, прокси или доменов для обхода ограничений не является частью продукта.

Управляются и частота в окне, и мгновенные всплески, и число одновременных запросов; одной средней скорости недостаточно. Ретраи SDK не должны умножать запросы мимо общего допуска. Очереди ограничены, прогресс персистентен, отдельные запросы имеют timeout; исчерпание повторов переводит задачу в видимое ожидание/ошибку без потери записанных данных. Это не вводит обязательный deadline на весь исторический replay.

В UI видны причина `waiting_rate_limit`, время возможного продолжения, прогресс и текущий интервал/частота. Логи сохраняют начало/исход паузы и сводки повторов, не каждую успешную свечу. Проверки используют синтетические ответы и часы: явные 600 секунд, отсутствие заголовков, различие 403/429/10006, рестарт во время ожидания, конкурирующие задачи и плавное восстановление. Преднамеренно вызывать бан реального API для проверки не требуется.

### Эффективное получение без лишних запросов

Использовать `GET /v5/market/kline`, `category=linear`, `interval=1`, query-параметры без JSON-body и страницы до **1000 свечей** вместо default 200, когда диапазон это допускает. API возвращает обратный порядок по startTime; пагинация обязана продвигаться и дедуплицировать границы. Только отсутствующие диапазоны загружаются повторно; пустая/короткая страница не равна throttling.

Для новых закрытий предпочтителен WebSocket `kline.1.{symbol}` с `confirm=true`, а REST обслуживает историю/пропуски. Окончательный transport выбирается на архитектурном этапе. При REST-опросе около 500 пар запросы распределяются во времени, а не отправляются все в один момент закрытия минуты; live-восстановлению оставляется часть общего бюджета. Connection pooling в здоровом режиме экономит соединения, но не уменьшает число учитываемых запросов.

WS тоже имеет лимиты: избегать частых reconnect, не превышать 500 установлений соединений за 5 минут, соблюдать лимиты подписок/длины args и heartbeat. Документация уже анонсирует **100 futures args на соединение с 26 ноября 2026**; для 500 тем минутных свечей нужен план минимум пяти соединений с проверкой успешной подписки. Это объявленное будущее ограничение, не выданное за уже действующее на дату исследования.

Основания: [Bybit rate limits](https://bybit-exchange.github.io/docs/v5/rate-limit), [коды ошибок](https://bybit-exchange.github.io/docs/v5/error), [kline](https://bybit-exchange.github.io/docs/v5/market/kline), [WS connection](https://bybit-exchange.github.io/docs/v5/ws/connect), [WS kline](https://bybit-exchange.github.io/docs/v5/websocket/public/kline), [FAQ](https://bybit-exchange.github.io/docs/faq). Исследование и границы подтверждения: [research.md](research.md#7-уточнение-bybit-и-web-push-от-1-ноября-2026).

Карта покрытия содержит не только min/max timestamp, но и непрерывные интервалы/пропуски, разрешение, статус полноты, источник и дату проверки. Статусы как минимум: `complete`, `partial`, `missing`, `not_listed`, `unsupported`, `insufficient_warmup`. Для каждого алгоритма дополнительно рассчитывается «достаточно ли этих данных».

В UI предусмотрена отдельная страница **«Исторические данные»**: список инструментов, сгруппированный/фильтруемый по биржам, тип данных и гранулярность, дата начала/окончания имеющейся истории, число записей и индикатор пропусков с деталями диапазонов. Для MVP тип данных фиксирован как минутные OHLCV; будущие типы не показываются как уже загруженные.

Индикатор различает «пропуски есть», «проверено, пропусков нет», «покрытие не проверено» и «данных нет». Начало/конец ряда сами по себе не дают зелёного статуса. Ожидаемые интервалы учитывают границы выбранного периода и известный жизненный цикл инструмента; время до листинга не объявляется нулевыми свечами. Интерфейс показывает период и свежесть проверки. Фактическое покрытие БД и полнота старого кешированного replay могут различаться и отображаются отдельно.

В live свежие закрытые минуты продолжают сохраняться одновременно с догрузкой необходимой предыстории. При старте, reconnect, добавлении пары и изменении параметров система получает требования активного модуля, проверяет соответствующее окно и автоматически загружает недостающие интервалы. Для первой конфигурации требуется полный ряд последних 30 суток. Это разрешённое поведение запуска live, а не отдельное подтверждение каждого отсутствующего бара.

Пока контекст неполон, выбранная пара имеет `loading_history`/`insufficient_history` и не генерирует сетапы. Остальные готовые пары продолжают работу. После догрузки пригодность пересчитывается автоматически. Если инструмент моложе требуемого окна либо API не предоставляет период, причина видна; непрерывные бесполезные повторы запрещены. При дальнейших закрытиях проверка готовности продолжается.

Повторное получение закрытой свечи не порождает новый сетап и не перезаписывает запись. Пропуск остаётся значимым для последующих минут, пока попадает в требуемое окно. Предыстория служит прогреву, а не автоматической рассылке старых сигналов; политика уведомлений при догоняющей обработке после разрыва оговорена отдельно.

## 7. Раздельные списки инструментов

Списки historical и live независимы. Изменение одного не меняет другой. Различаются выбранные инструменты и те, которые пригодны для алгоритма в данный момент. Фильтрация по данным не удаляет выбор пользователя навсегда.

### 7.1. Исторический список

- По умолчанию: все инструменты выбранной биржи и категории, представленные в БД.
- Команда «все из БД» заново формирует такой список; в метаданных запуска фиксируется snapshot.
- CSV: одна колонка **без заголовка**, одна строка на symbol, например `BTCUSDT`. В итог попадают только инструменты БД выбранной биржи/категории. Неизвестные исключаются с видимым отчётом; дубли схлопываются.
- Ручное добавление из каталога БД и удаление из текущего списка.
- Текущий листинг биржи не фильтрует historical: делистнутый инструмент с сохранёнными данными обязательно обрабатывается на пригодных интервалах.

Все инструменты списка попадают в отчёт запуска, включая те, где нет пригодных минут. Внутри каждого ряда проверяется контекст каждой сигнальной минуты. Отсутствие полного окна не равно «по инструменту не было сигналов». Наличие пары в БД не гарантирует покрытие запрошенных дат.

Такой список не обещает полного исторического universe: инструменты, данные которых никогда не попадали в БД, сами не появятся. Удалять сохранённую историю при делистинге нельзя.

### 7.2. Live-список

- Импорт всех **текущих торгуемых USDT perpetual** инструментов с биржи, с полной пагинацией.
- Ручное добавление/удаление; добавляемый инструмент проверяется по текущему листингу выбранной биржи/категории.
- CSV того же одноколоночного формата без заголовка; фильтр проверяет текущий листинг, а не наличие истории в БД.
- Импорт является действием пользователя, не скрытой подпиской на все будущие новые листинги.

Новая для нашей БД live-пара допустима: её выбирают и автоматически подгружают историю по требованиям модуля. Эффективный набор для выдачи сигналов равен пересечению выбранного списка, текущих торгуемых инструментов и готовых по данным пар. При делистинге выдача прекращается, причина видна, сохранённые данные остаются для replay.

### 7.3. Общий CSV-контракт

UTF-8, без заголовка, например две строки `BTCUSDT` и `ETHUSDT`. Пустые строки и внешние пробелы можно убрать; невалидная строка/лишние колонки показываются как ошибки, не угадываются. Итог сообщает исходное число, уникальные принятые символы и исключения с причинами. Одинаковые названия на разных биржах не подменяют друг друга.

### 7.4. Выбор инструментов для массовой догрузки истории

Форма явной догрузки истории содержит собственный редактируемый выбор инструментов; по умолчанию он пуст и не наследует список replay/live-запусков. Поддерживаются ручное добавление/удаление символов, импорт CSV по контракту 7.3 с проверкой по каталогу БД (включая делистнутые) и явный разовый импорт текущего листинга биржи: линейные бессрочные USDT-контракты со статусом Trading. Импорт листинга — действие пользователя, а не подписка на будущие листинги; отсутствующие в каталоге БД инструменты создаются при импорте и попадают в выбор. Загрузка запускается одним подтверждением для выбранного набора и дат; создаётся по одному заданию на инструмент, действуют обычные лимиты admission, и итог виден: сколько заданий создано и сколько отклонено с причиной.

Задания массовой догрузки принадлежат сервису данных и переживают перезагрузку UI. Сводка активных пользовательских загрузок (queued/running/cancel_requested) показывается отдельно от штатного ежеминутного сбора закрытых минут, чтобы было видно, идёт ли сейчас массовая догрузка.

## 8. Хранение и происхождение

Утверждены **две отдельные базы данных** с независимым переносом/резервированием: БД сервиса рыночных данных и БД платформы сетапов. Одних разных таблиц в одной неразделимой БД недостаточно. Один сервер/экземпляр СУБД для двух БД допустим при сохранении независимости владения, доступа и восстановления.

Для обеих выбран **обычный PostgreSQL**. TimescaleDB и его hypertables/columnstore не используются: владелец выбрал вариант B ради переносимости и повторного использования истории. Первоначально допустим один экземпляр PostgreSQL с двумя БД/ролями, но это не означает изоляцию CPU/I/O; нагрузка фоновых задач ограничивается. PostgreSQL и Node.js фиксируются в поддерживаемых совместимых версиях при подготовке каркаса.

Минутные свечи разбиваются нативным `RANGE` по времени, первоначально по месяцам UTC. Не создаются отдельные partitions на каждую пару. Уникальный ключ включает стабильный идентификатор инструмента и временной ключ разбиения, например `(instrument_id, open_time)`; время/биржа/категория определены однозначно. Сервис заранее создаёт секции для новых минут и проверяет наличие исторических секций перед backfill. Политика удаления старых секций автоматически не вводится.

Цены, base volume и quote turnover сохраняются как точные десятичные значения PostgreSQL `numeric` с проверяемой точностью/диапазонами. Ограничение scale не должно незаметно округлять вход. В JSON API десятичные значения передаются строками; timestamps остаются Unix-секундами. Backend и алгоритм не преобразуют финансовые поля молча в JavaScript `number`; правила арифметики и границы `>=12%`/`>3x` проверяются тестами.

node-postgres + Kysely используются с версионируемыми миграциями и явным SQL для горячих путей. Массовая запись выполняется порциями, например через staging и `INSERT ... ON CONFLICT DO NOTHING`; существующие строки не обновляются. Сам по себе `DO NOTHING` недостаточен: отличающиеся дубли должны попадать в диагностику конфликтов согласно add-only политике. Большие чтения постраничные/потоковые, без материализации всей истории в объектах JavaScript.

| База | Что хранится | Что не должно попадать |
|---|---|---|
| БД сервиса данных | Рыночная часть: закрытые 1m OHLCV, биржи, инструменты/контракты, единицы, временная семантика, происхождение, версия схемы и покрытие. Отдельно организованная служебная часть: задания загрузки, прогресс, конфигурация постоянного сбора и сроки cooldown | Торговые алгоритмы/настройки, сетапы, кеш replay, пользовательские уведомления и Web Push-подписки |
| БД платформы сетапов | Конфигурации алгоритмов, пользовательские списки, задания live/replay, результаты и сетапы, кеш historical replay, каналы доставки, Web Push-подписки; ссылки на задания сервиса данных | Единственная копия рыночной истории или авторитетное состояние биржевого загрузчика |

Служебные таблицы загрузчика уточняют прежнее правило «всё остальное в БД приложения»: они принадлежат сервису данных, иначе его нельзя перенести независимо. Их можно отделить схемой/пространством таблиц от рыночных рядов; третья обязательная БД не нужна. Ссылки/отображаемые статусы в платформе не создают второго владельца задания. Секреты доступа не включаются в переносимый публичный экспорт рыночных данных.

Кеш результатов находится во второй БД, а не в третьей специальной БД. Локальные вычислительные буферы/кэши признаков не превращаются в неограниченную RAM-историю; если они персистентны и зависят от алгоритма, относятся к приложению. Рыночная история не дублируется ради каждого алгоритма.

Рыночная часть БД должна быть **самодостаточной для другой системы**: определения инструментов и единиц, ключи, шкала времени и версия схемы находятся вместе с данными. Её интерпретация и восстановление не требуют БД платформы, торгового алгоритма или служебных заданий загрузчика. Наряду с API документируются схема/формат экспорта, чтобы использовать накопленные данные можно было без работающего сервиса. В штатном режиме только сервис владеет записью и предоставляет данные через API; поддерживаемый экспорт/восстановление не является скрытым прямым доступом платформы к его БД.

Идентичность рыночного ряда включает биржу, стабильную идентичность инструмента/категорию, тип данных и временной ключ/гранулярность. В MVP реализуются только минутные свечи Bybit. Позднее другие биржи и funding/OI/mark/index/long-short ratio добавляются совместимым расширением схемы, не переинтерпретируя старые ключи, единицы и строки. Новые таблицы/поля не должны требовать удаления или повторной API-загрузки уже накопленной истории.

Кэши чтения и признаки ограничены по объёму и очищаются. Принятые минутные записи и данные запуска сохраняются для повторяемости; обычная догрузка не меняет прежние значения. Без отдельной команды администратора история не удаляется ради освобождения кэша. Один hash без доступного исходного содержимого не обеспечивает повторяемость.

Пересчёт индикаторов обычно дешевле вечного хранения всех комбинаций параметров. Сначала сохраняются первичные данные и доказательства сетапов; постоянный кэш признаков вводится по измеренной необходимости.

Публичная доступность API/архива не равна разрешению на перепродажу raw data. Перед публичным каналом или SaaS отдельно проверяются условия источника, передача цен/производных сигналов и права получателей. У Binance лицензия кода репозитория и [условия набора данных](https://github.com/binance/binance-public-data/blob/master/TERMS_AND_CONDITIONS.md) являются разными документами.

## 9. Перенос базы между серверами

Перенос **одной БД рыночной истории** без БД приложения и без повторного скачивания является требованием MVP. Нужны поддерживаемый snapshot/backup и восстановление на другом сервере/в другой совместимой системе. Перенос охватывает свечи, метаданные инструментов (включая делистнутые), карту покрытия и версию схемы. БД платформы с результатами/кешем/конфигурациями резервируется отдельно; она нужна для переноса платформы сетапов, но не самостоятельного сервиса данных или использования самих рыночных рядов.

Простое копирование файлов работающей БД не считается универсальным безопасным способом. Базовый перенос обычного PostgreSQL выполняется согласованным `pg_dump`/`pg_restore` в поддерживаемую версию с проверкой восстановления; физические копии допустимы только штатной процедурой PostgreSQL. Переход на другую машину не требует API-backfill всей базы. Наличие TimescaleDB или другой time-series extension на целевом сервере не требуется.

Для использования в другом приложении предусмотрен отдельный экспорт рыночных рядов и обязательных метаданных по документированной схеме, например CSV с manifest единиц/времени/инструментов. Служебные таблицы pg-boss, задания и БД платформы для интерпретации такого экспорта не нужны. Перенос работающего сервиса, напротив, включает его служебное состояние. Совместимость дампа между версиями PostgreSQL и время восстановления проверяются, а не предполагаются неограниченными.

Проверка восстановления: количества записей/инструментов, диапазоны и пробелы покрытия, целостность копии и одинаковый результат **свежего** контрольного replay, не замаскированный cache hit. После запуска на новом узле API догружает только отсутствующие минуты. Токены Telegram, Web Push-подписки, серверные пути и секреты не входят в переносимый набор рыночных данных. Исходная копия не удаляется автоматически; данные не перезаписываются незаметно при восстановлении поверх другой БД.

Если БД приложения с готовыми кешами оставлена, а БД истории заменена/дополнена, кеш не сбрасывается автоматически: версия данных не входит в принятый ключ. UI может предупредить об этом и предложить явную очистку. Принятую владельцем возможность устаревшего результата нельзя молча заменить автоматической инвалидацией.

Перенос **работающего сервиса** включает совместимую версию программы/схемы, согласованный backup его БД, служебное состояние загрузчиков и несекретную конфигурацию источников/сбора. Доступы переносятся защищённым способом отдельно. Контейнер или исполняемый файл без постоянного хранилища не является переносом данных.

Для MVP допустим контролируемый перенос с остановкой записи: зафиксировать задания/ожидания, получить согласованную копию, восстановить и проверить её на новом узле, затем возобновить сбор и переключить адрес API платформы. Старый писатель не должен одновременно продолжать тот же сбор; исходная копия сохраняется. После запуска проверяется покрытие и заполняется только недостающее. Смена сервера не сбрасывает обязательные сроки ожидания биржи. Нулевая длительность простоя не является требованием MVP.

## 10. Самостоятельный сервис рыночных данных

### 10.1. Ответственность и размещение

Сервис независимо запускается, обновляется и переносится; может обслуживать платформу сетапов и другие авторизованные системы. Он владеет биржевыми адаптерами, нормализацией, записью/чтением рядов, покрытием, исторической догрузкой и постоянным сбором. Детектор, расчёт признаков стратегии, replay алгоритмов, их кеш и пользовательские уведомления остаются в платформе сетапов.

Платформа вычисляет требуемые диапазоны по параметрам алгоритма и передаёт их сервису. Сервис не знает, почему конкретному алгоритму нужны 30 суток; его задача получить указанные данные или явно сообщить об ограничениях источника. Автодогрузка при старте/reconnect live сохраняется: её инициирует платформа через API сервиса в рамках уже разрешённого запуска live, без нового подтверждения каждого бара. Историческая загрузка остаётся явной отдельной операцией.

Начальная реализация: два компактных backend-приложения на Node.js LTS + TypeScript strict + Fastify, которые могут работать на одном сервере пользователя. TypeBox задаёт доверенные схемы запросов/ответов, из них формируется OpenAPI; клиенты используют версионированный API, не импортируют внутренности другого сервиса. Конкретные версии и транспорт новых закрытий уточняются при реализации. Kubernetes, отдельный микросервис на каждую биржу и внешний брокер очередей не обязательны.

pg-boss хранит задания загрузки в БД сервиса данных; задания replay/доставки находятся в БД платформы. Очередь не заменяет доменное состояние покрытия, checkpoints, желаемое состояние сбора и Bybit cooldown. Рабочие операции идемпотентны, повторное выполнение не обещает exactly-once внешних эффектов. Сроки lease/heartbeat настраиваются без произвольного deadline всего replay; CPU-вычисления отделены от API и координатора очереди. История запусков хранится отдельно от очищаемых завершённых записей очереди, payload заданий не содержит массивы свечей.

### 10.2. Требования к API

| Операция | Контракт |
|---|---|
| Каталог бирж/инструментов | Стабильные идентификаторы, категории, известный жизненный цикл/листинг; MVP отдаёт реально поддерживаемые данные Bybit |
| Покрытие | Начало/конец, проверенные интервалы и пропуски, отсутствие данных/неизвестная полнота, время проверки; поддерживает список инструментов |
| Чтение свечей | Только уже сохранённые закрытые свечи плюс метаданные полноты; не инициирует скрытую биржевую загрузку |
| Пополнение диапазона | Явная асинхронная операция: вернуть идентификатор задания, не держать HTTP-соединение до окончания загрузки |
| Статус/отмена задания | Прогресс, причины пропусков, ошибки, ожидание квоты и время продолжения; отмена не удаляет уже сохранённые данные |
| Постоянный сбор | Отдельное включение/выключение выбранных инструментов; продолжает работу при остановке сканера сетапов |
| Состояние сервиса | Доступность, актуальность сбора и диагностируемые отказы; живой процесс не равен свежим данным |

Для чтения доступны пакетные запросы и постраничная/потоковая выдача диапазонов. Один HTTP-запрос на свечу и загрузка всей истории в RAM не являются допустимым основным способом replay. Порядок и курсоры стабильны и документированы; определено поведение чтения при параллельной догрузке. Размер страницы/ответа, очереди и параллелизм ограничены, отмена/разрыв клиента освобождают временные ресурсы.

Во внешнем API сервиса timestamps задаются в **Unix-секундах UTC**. Диапазон свечей `[start,end)` относится ко времени открытия минуты, время её закрытия передаётся/определяется однозначно. Период выдачи сетапов платформы относится ко времени закрытия; адаптер платформы учитывает это различие при запросе прогрева. Миллисекунды Bybit остаются внутри биржевого адаптера. Никакого неявного округления границ или подмены единиц.

Повтор запроса пополнения после потери ответа должен возвращать/связывать ту же логическую работу, а не умножать загрузчики. Пересекающиеся диапазоны разных клиентов используют общий сбор недостающего. Отмена запроса одного клиента не должна отменять работу, ещё нужную другим клиентам или постоянному сбору. Конкретный механизм идемпотентности выбирается при реализации и описывается в API.

### 10.3. Документация, версии и доступ

Сервис поставляется с собственной **OpenAPI-спецификацией**, доступной документацией методов и примерами. Документируются схема авторизации, разрешения, единицы/время, границы диапазонов, закрытость свечей, пагинация, полнота, асинхронные задания, повторы/отмена и структурированные ошибки. Отдельно описываются самостоятельный запуск, backup/restore, миграции и схема/формат экспорта рыночных данных. Эти материалы создаются вместе с реализацией, а не заменяются страницей с одними названиями методов.

API имеет версию и заявленную совместимость; несовместимые изменения времени/форматов не вводятся молча. Версия API не является версией торгового алгоритма и не добавляется в согласованный ключ кеша replay. При обновлении сервиса сохраняются значения и смысл уже загруженных данных.

«API наружу» означает API для **авторизованных клиентов**, не анонимный публичный endpoint. Разделяются права чтения, запуска загрузок и администрирования; доступы проверяются на каждой операции, параметры/объёмы ограничены. Биржевые адреса и адаптеры задаются конфигурацией сервиса, а не произвольным URL от клиента. Межсерверный доступ защищается HTTPS либо эквивалентным защищённым каналом, секреты не попадают в ответы, логи и рыночные экспорты.

### 10.4. Отказы и приёмка

Недоступность сервиса или несвежие данные явно видны в платформе. Зависимое новое вычисление live/replay приостанавливается/завершается диагностируемой ошибкой; ошибка связи не превращается в «свечей нет» или «сетапов нет». Уже полученный полный вход может быть обработан, но результат не объявляется свежим без проверки его временной границы. Старые сетапы и доступные кеши приложения остаются читаемыми с прежними отметками происхождения. Скрытого fallback на прямой доступ к БД/Bybit нет.

Приёмка: независимый клиент читает данные по документированному API; read не создаёт загрузку; явное пополнение возвращает задание; повтор/перекрытие не дублирует скачивание; общий cooldown соблюдается между клиентами. Сам сервис работает без запущенной платформы и её БД. После независимого переноса совпадают сохранённые записи/покрытие и свежий контрольный replay, старые диапазоны не скачиваются заново. Проверяются сетевой отказ, восстановление и отсутствие доступа у неавторизованного клиента.
