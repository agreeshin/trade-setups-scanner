# Администратор и интерфейсы

[К оглавлению PRD](PRD.md)

Статус: frontend-стек утверждён владельцем продукта; визуальный стиль и три режима темы уточнены 4 ноября 2026, состав UI-библиотеки и поэтапное обновление экранов — 8 ноября 2026 в разделе дизайн-системы ниже. Пользовательские сценарии и независимый сервис данных сохранены.

## 1. Роль и доступ

В MVP один администратор управляет конфигурациями, загрузкой данных, live-сканированием, историческими заданиями и доставкой. Это не означает анонимный веб-интерфейс с root-доступом.

CLI, API и web должны выражать одни и те же операции и статусы. Web размещается на том же сервере через защищённый origin с аутентификацией. Первоначально это собственный сервер пользователя, не обязательная арендованная VPS. Отдельный внутренний порт возможен, но другой порт сам по себе не защищает доступ. Для браузерных уведомлений нужен HTTPS (исключение localhost); приватная сеть сама по себе не заменяет secure context.

Остановить/запустить сбор, сканер и задания можно из приложения. Запуск приложения после полной остановки и управление самим сервером доступны через внешний административный CLI/service manager: выключенный backend не может сам обслужить кнопку своего запуска. Произвольный shell/root из браузера не предлагается. Начальный рабочий масштаб: около 500 live-инструментов и один алгоритм.

Права на управление ботом и локальными данными не означают права торговли на бирже. Торговые API keys в MVP не требуются и не запрашиваются.

## 2. Предлагаемые разделы web

| Инструменты | Раздельные исторический и live-списки, биржа/категория, импорт CSV, исключения, ручное добавление/удаление, листинг/делистинг |
| Данные | Historical DB: биржа → инструменты, минимальная/максимальная дата, индикатор/число/подробности пропусков, фильтр биржи и пользовательского диапазона, достаточность для стратегии, дозагрузка |
| Алгоритмы | Зарегистрированные версии, описание, параметры, требования к данным, назначение инструментов |

| Сетапы | Обязательная UI-лента, фильтры, причины, цена/время, качество данных, экспорт, независимые статусы каналов доставки |
| Кэш | Число записей и байты кэша, попадания/исходное время расчёта/частичность, очистка по бирже и инструменту либо глобально |
| Настройки | Подписка Web Push и её состояние, максимальный возраст уведомлений (по умолчанию 1 минута), опциональный закрытый Telegram-канал и тест доставки, лимиты задач/диска, часовой пояс отображения, безопасный экспорт конфигурации, независимый backup/restore двух БД |

### Граница сервиса данных

Независимый сервис рыночных данных владеет биржевыми коннекторами, адаптивными лимитами запросов, всей загрузкой/backfill и повторами, нормализацией, каталогом, данными и покрытием. Ему принадлежат задания загрузки, прогресс, отмена, cooldown источника и настройки постоянного сбора; он предоставляет собственный аутентифицированный API, OpenAPI-документацию и backup/restore. Платформа сигналов владеет версиями/параметрами алгоритмов, live/replay-расчётами, кэшем, сетапами, пользовательскими списками, уведомлениями и UI. Cooldown загрузки не является cooldown сигналов.

UI проксирует управление данными через API сервиса, без прямого доступа к его БД и без запасного обращения платформы к бирже. API требует аутентификации, прав `read` / `load` / `admin`, ограничений диапазонов/объёмов и квот; анонимного публичного API нет. Сервис можно переносить и развёртывать независимо, первоначально на том же собственном сервере. Достаточен один компактный сервис-приложение с внутренними workers: Kubernetes и отдельные микросервисы очередей не являются требованием.

Чтение возвращает уже имеющиеся данные и сведения о покрытии, **не запускает загрузку скрыто**. Явная команда заполнения интервалов создаёт асинхронное задание и возвращает job ID; UI получает прогресс, ошибки, ограничения источника и возможность отмены через API. Перекрывающиеся запросы клиентов разделяют работу: отмена одного запроса не останавливает загрузку, ещё необходимую другим. Платформа сохраняет ссылку на задание, но не становится вторым владельцем его состояния.

### Две БД и состояние истории

Ровно две логические БД резервируются и восстанавливаются независимо. **Service DB (market historical DB)** самодостаточно хранит рыночную историю, метаданные бирж/инструментов, каталог и покрытие, а также отдельно организованные операционные таблицы загрузок, прогресса, повторов и настроек сбора. **Platform DB (app DB)** содержит настройки платформы, выбранные списки, расчётные задания и ссылки на задания сервиса, результаты и историю запусков, кэш, статусы доставки и Web Push-подписки. Третьей БД кэша нет. Логическое разделение не предписывает конкретную СУБД или количество физических файлов.

Страница historical DB строится от биржи к инструментам, показывает минимальную и максимальную дату сохранённых минут, индикатор наличия разрывов, их число и раскрываемые интервалы/количество недостающих минут. Доступны фильтр биржи и выбранный пользователем диапазон; границы найденных данных и полнота покрытия запрошенного диапазона показаны раздельно. «Нет истории», «покрытие неизвестно/не проверено» и «проверено, разрывов нет» являются разными состояниями. Одна пара min/max не доказывает непрерывность; вне жизненного цикла инструмента нельзя обещать существование свечей. Детальные определения покрытия находятся в [data.md](data.md).

Раздел «История и сбор» сгруппирован во вкладки: «Загрузка истории» (редактируемый выбор инструментов, импорт CSV/листинга, даты; подтверждение создаёт сохраняемый план загрузки, сервер сам постепенно ставит задания в очередь, список планов с прогрессом и отменой), «Текущий сбор свечей» (обзорная таблица покрытия всех инструментов с датами и недостающими минутами, фильтром по символу и переключателем «только со свечами»; массовое управление сбором: импорт текущего листинга биржи, выбор инструментов чек-боксами с «выбрать все» и массовыми включением/выключением без лимита одного запуска, а также операция «проверка и ремонт пропусков» для выбранных инструментов — заполняет незагруженные пропуски и подтверждает минуты без торговли, с таблицей операций ремонта; цели сбора и детальное покрытие выбранного инструмента; при включении инструмента с историей сервер сначала дозаполняет хвост от последней свечи до текущей закрытой минуты, затем собирает поминутно) и «Задания загрузки» (список заданий, прогресс, отмена). Обзорная таблица показывает агрегаты сервера и не заменяет детальное покрытие: «нет свечей», «есть данные с пропусками» и «непрерывно» различаются. Сводка активных массовых загрузок видна на всех вкладках и после перезагрузки страницы: она отражает серверные задания, а не состояние открытой вкладки, и отличается от постоянного ежеминутного сбора. Во всех полях выбора временных интервалов (загрузка истории, исторические запуски) смена даты автоматически сбрасывает время к 00:00 UTC выбранной даты; в локальном отображении пользователя это время смещено на offset его часового пояса. После подстановки время можно изменить вручную — до следующей смены даты.

Страница состояния истории получает каталог и покрытие через API сервиса. «Сервис недоступен» не равнозначно пустой истории или отсутствию разрывов; ранее полученное покрытие показывается только с отметкой времени и устаревания. Исходная частичность сохранённого расчёта/кэша не подменяется текущим состоянием сервиса.

### Кэш исторических расчётов

Кэш хранится в app DB отдельно по каждому инструменту. Ключ включает биржево-квалифицированную идентичность инструмента, algorithm ID, неизменяемую версию алгоритма, каноническое представление **всех** параметров и точные начало/конец диапазона в Unix-секундах. При любом изменении алгоритма его версия обязательно повышается. Состав выбранного списка не входит в ключ; отдельный агрегатный ключ списка не требуется.

Ревизии данных, наличие данных, разрывы и качество источника **не входят в ключ**. Backfill и появление новых данных автоматически не инвалидируют результат: пользователь явно принимает возможность устаревшего кэша. UI показывает `cache hit`, исходное время расчёта и исходный статус частичности/пропущенные интервалы; ранее частичный результат не становится полным от появления новой истории. Сохранённая история запуска также не переписывается под текущее покрытие.

Для списка выполняется пакетный поиск по ключам инструментов, рассчитываются только промахи. Найденные и новые результаты объединяются в стабильном хронологическом порядке: время сигнала, биржа, инструмент, смысловой ключ. Новый запуск может содержать смесь попаданий и новых расчётов; происхождение и исходное время указываются по инструментам. Для явного пересчёта пользователь очищает нужную область кэша и повторяет запрос; это не молчаливая автоматическая инвалидизация.

Очистка доступна по бирже + инструменту сразу для всех версий/параметров/дат алгоритмов либо глобально. Перед подтверждением показываются область и число затрагиваемых записей. Она удаляет только кэш app DB, **не** market historical DB и **не** ранее сохранённую историю запусков/сигналы. Уже выполнявшиеся до очистки задания не могут незаметно восстановить очищенные записи; их результат может сохраниться в истории, но запись в очищенную область кэша должна быть предотвращена. Новые запросы после очистки вправе снова заполнять кэш.

UI отдельно показывает количество записей и объём кэшированных данных в байтах. Это не размер всего физического файла app DB. Удаление записей не обещает немедленное уменьшение физического файла или возврат места ОС; обслуживание хранения описывается отдельно от команды очистки.

### Раздельные списки инструментов

Исторический список по умолчанию содержит **все инструменты из БД** выбранной биржи/категории, включая делистнутые. Администратор может добавить инструмент из БД или удалить его из выбранного списка; удаление из списка не удаляет данные. CSV содержит одну колонку без заголовка, например одну строку `BTCUSDT` на инструмент. При импорте остаются только существующие в БД инструменты; неизвестные, дубли и исключения с причинами показываются до подтверждения. Текущий биржевой листинг не фильтрует исторический список. Количество инструментов одного исторического запуска не ограничено фиксированным лимитом выбора (решение от 2026-11-08): практическая граница — только вычислительные ресурсы сервера. Ресурсные проверки admission (очередь/объём работы/диск) остаются защитой от неразумных объёмов с запасом поверх масштаба каталога, а не лимитом выбора.

Live-список импортируется из текущего биржевого каталога бессрочных USDT-контрактов. Доступны ручное добавление/удаление и CSV того же формата без заголовка, но здесь принимаются только актуально листнутые инструменты выбранной биржи/категории. Изменение одного списка не меняет другой. Выбранный список сохраняется в снимке конфигурации/задания; принадлежность к списку не означает готовность к расчёту.

**Выбранные инструменты и допущенные к расчёту минуты различаются.** Недостаток 30 дней истории не исключает выбранный инструмент навсегда: UI показывает ожидание и автоматическую догрузку. Готовность на конкретной минуте требует полных непрерывных окон по контракту модуля, включая обе базы 7/30 дней первого алгоритма; проверки только самой ранней и поздней свечи недостаточно. У нового листинга, который ещё не накопил нужный возраст, показывается «ожидание истории / недоступно» и причина, без бесконечного повторения невозможной загрузки.

## 3. Основные пользовательские сценарии

### S-01. Первый запуск

Администратор открывает защищённый web, видит Bybit как единственную доступную биржу MVP и бессрочные USDT-контракты. Формирует раздельные списки по правилам выше. До подтверждения видит распознанные, неизвестные, повторные и неподдерживаемые элементы. Будущие биржи не отображаются как уже работающие. Ничего не подключается к торговому аккаунту; настройка Telegram не требуется.

В разделе загрузки выбирает начальную дату, конечную дату и пары; разрешение фиксировано как 1m OHLCV с оборотом USDT. UI читает доступность через API сервиса. После подтверждения явно запрашивает асинхронную загрузку у сервиса и показывает её job ID, прогресс, пропуски и ошибки по парам. Сервис вставляет только отсутствующие интервалы: существующие закрытые свечи не перезаписываются, повтор запроса не дублирует их. Постоянный сбор сервиса также дописывает историю. Дополнительные показатели пока не предлагаются как доступные для загрузки.

### S-02. Запуск алгоритма live

При запуске live пользователь разрешает автоматическую подготовку истории по требованиям выбранного модуля. Платформа вычисляет необходимые интервалы и явно запрашивает их заполнение у сервиса; сервис не знает алгоритмов и не вычисляет их прогрев сам. Описанная ниже автоматическая догрузка выполняется сервисом параллельно с его сбором свежих минут, а не вторым загрузчиком платформы.

Администратор выбирает зарегистрированный доверенный модуль/версию, параметры и live-список. В MVP один алгоритм: рост цены не менее 12% за настраиваемые последние 5 минут И оборот USDT строго больше 3x среднего, приведённого к тому же окну, по базе 30 дней ИЛИ 7 дней. Обе базы обязательны и включают недавнее окно; минутные формулы заданы в [strategies.md](strategies.md). Сигнал утверждён как нейтральное событие `price_volume_spike` / `WATCH`, не направление сделки и не открытый вопрос.

Частота решений фиксирована: после закрытия минуты. По каждому инструменту UI показывает необходимую историю, готовность, очередь догрузки или ожидание возраста листинга. Автоматическая загрузка недостающих интервалов по требованиям модуля идёт параллельно с приёмом свежих минут, не блокируя готовые инструменты. Состояние готовых инструментов переходит в `running`; отсутствие сетапов при здоровом feed отличается от `warming_up`, `stale`, `error` и недоступной истории. Cooldown 5 минут на инструмент и алгоритм является только временным ограничением: повтор разрешён через 300 секунд, даже если условия непрерывно истинны.

Сигналы появляются в обязательной UI-ленте. Web Push входит в MVP на поддерживаемых окружениях и может работать без открытой вкладки через Push API и service worker. Подписка запрашивается по явному действию пользователя, требует разрешения и secure context HTTPS (localhost является исключением). При отказе, отзыве разрешения или неподдерживаемом окружении остаётся лента. Для iOS/iPadOS 16.4+ нужны установка веб-приложения на Home Screen и разрешение; UI показывает эти шаги. Полное завершение/force-quit браузера, offline, настройки ОС и Focus могут препятствовать своевременной доставке: постоянная доставка не гарантируется. Telegram в закрытый канал подключается отдельно; отсутствие бота или ошибка доставки не блокируют сканер.

В Settings задаётся максимальный возраст уведомления, по умолчанию 1 минута. UI-toast, Web Push и Telegram допустимы при возрасте не более 60 секунд от **конца сигнальной минуты UTC**, а не от обнаружения или последней попытки. Перед каждой отправкой/повтором и показом toast возраст проверяется заново; просроченное уведомление пропускается с причиной, но сигнал остаётся в ленте/истории. Для push TTL равен не более оставшегося бюджета, service worker повторяет проверку перед показом; повтор не продлевает срок. Подробный контракт и официальные источники: [signals.md](signals.md#возраст-уведомления).

UI показывает состояние подписки и позволяет отписаться. Endpoints/ключи хранятся как чувствительные данные в app DB; отозванные/недействующие подписки очищаются, а не накапливаются. Результат отправки push-сервису не подписывается как доказанный показ или прочтение пользователем.

Изменение активной конфигурации проходит валидацию и становится новой ревизией с явным временем вступления в силу. Если нужен новый прогрев, это показывается; старые результаты не меняются.

### S-03. Исследование прошлого

Администратор задаёт диапазон, проверяет исторический список (по умолчанию все инструменты БД выбранной биржи/категории, включая делистнутые) и выбирает ту же версию/настройки алгоритма, что доступны live. Preflight показывает отсутствующие минуты и недостаток прогрева; можно запросить догрузку через API. Частичный результат разрешён: задание рассматривает **все выбранные инструменты**, но рассчитывает только пригодные минуты с полной непрерывной необходимой историей. Инструменты с пробелами не исчезают из отчёта. Приближённого режима, секундного уточнения и переключения гранулярности нет.

Во время работы доступны прогресс и отмена, фиксированного дедлайна выполнения нет. Исторический запуск с несколькими инструментами занимает **одну строку** в списке «Последние запуски»: сводный статус по инструментам (выполняется, пока хотя бы один активен; готово/ошибка с числом проблемных инструментов) и суммарное число сетапов; детальные результаты и единый CSV включают сетапы всех инструментов запуска с колонкой инструмента; отмена строковой операции останавливает все инструменты запуска. Запуск из одного инструмента отображается отдельной строкой как прежде. После завершения видны количество сигналов, фактически проверенные минуты/инструменты, пропущенные минуты и причины по каждой паре, а также CSV. «Нет пригодных данных» не показывается как успешный анализ с нулём сигналов. Отменённое задание сохраняет статус и границу реально обработанной части. Replay не рассылает массовые Telegram- или браузерные уведомления. На этом этапе интерфейс не изображает «прибыльность» или win rate. Операция «Очистить все прогоны» в списке запусков с двухшаговым подтверждением сама доводит очистку до конца одним нажатием: останавливает очередь (ожидающие → отменены), дожидается завершения активных прогонов повторами с интервалом и затем удаляет все прогоны с их результатами и границами обработки, интервалы качества и весь кэш исторических расчётов. Live-лента, настройки, списки инструментов и market historical DB не затрагиваются; это отдельная операция, обратная по охвату очистке кэша без удаления истории запусков (раздел «Кэш исторических расчётов»).

### S-04. Проверка отдельного сетапа

В карточке: биржа/пара, нейтральный тип `price_volume_spike` / `WATCH`, время конца сигнальной минуты, её close, версия/параметры, рост цены, оборот USDT, **оба отношения к базам 7 и 30 дней и выполненная ветвь OR**, состояние данных и отдельная история доставки каждого канала. CSV использует целые Unix-секунды (`signal_time_unix_s`); локальное время UI не меняет экспорт. Времена сохранения/доставки и задержка показываются отдельно от времени сигнала. Можно перейти к внешнему графику или открыть доступный локальный контекст. Полноценный торговый терминал/редактор графических индикаторов не обязателен для MVP.

### S-05. Остановка накопления

Администратор выключает постоянный сбор командой через API сервиса данных. История не удаляется. Live-стратегии, которым нужен этот источник, явно приостанавливаются или переходят в degraded по выбранной политике. Replay по сохранённым данным остаётся доступным через работающий API сервиса; результаты кэша доступны независимо от него. Возобновление показывает разрыв и явный запрос на его устранение, не скрытую загрузку при чтении.

### S-06. Сбой доставки или источника

Недоступность сервиса данных переводит интерфейс в degraded и приостанавливает зависимые свежие расчёты, которым нужны его данные. Старые сигналы, история запусков и результаты уже имеющегося кэша остаются доступны из platform DB с отметками происхождения, времени расчёта и исходного качества. Промах кэша, требующий недоступных данных, не маскируется пустым результатом. Ни чтение raw service DB, ни прямой запрос биржи не служат обходом сбоя. После восстановления чтение по-прежнему не запускает скрытый backfill; его запрашивают явно либо в рамках разрешённой live-подготовки.

При проблеме UI-соединения, браузерного уведомления или Telegram сетап остаётся в app DB; статусы каналов, попытки и задержка видны отдельно. Возврат в UI показывает сохранённую ленту без массового воспроизведения старых toast/push. Стабильный идентификатор предотвращает создание нового сигнала из-за повтора доставки; доставка не продлевает ни cooldown алгоритма, ни срок уведомления. При разрыве биржевого потока система не делает вывод об отсутствии торгов и не показывает себя исправной. После восстановления отмечаются закрытые/неустранимые пробелы. Запоздавшие сигналы сохраняются; уведомления после догрузки/сбоя проходят ту же проверку максимального возраста из Settings, по умолчанию 60 секунд от конца сигнальной минуты.

### S-07. Большой исторический запуск

Если задача превышает лимит диска/очереди/памяти, система отказывает до работы либо предлагает меньший диапазон, а не падает после нескольких часов. Эти ресурсные ограничения не являются лимитом длительности: длительный replay можно дождаться или отменить. Отмена освобождает временные ресурсы; уже загруженная полезная история не удаляется без причины.

### S-08. Перенос на другой сервер

UI вызывает операции резервирования/восстановления service DB через административный API самого сервиса и отдельно управляет копией platform DB. Переносятся также операционные данные загрузки; восстановление и возобновление заданий контролирует сервис. UI не требует совместного развёртывания двух компонентов и не открывает прямой доступ к service DB ради переноса.

Администратор создаёт независимые переносимые резервные копии service DB и platform DB и восстанавливает их на другом сервере. Рыночная история переносится без повторного получения через биржевой API; задания загрузки и настройки сбора принадлежат service DB, выбранные списки, конфигурации алгоритмов, расчётные задания, результаты, кэш и подписки принадлежат platform DB. После восстановления сервис по явному запросу догружает только действительно отсутствующие интервалы, без перезаписи существующих закрытых свечей. Перенос platform DB с подписками требует защиты чувствительных endpoints/ключей; действительность подписок зависит в том числе от сохранения origin и проверяется, а не обещается автоматически при смене адреса. Прочие секреты переносятся защищённым способом. Проверка восстановления и состав копий определены в общем контракте хранения; третья cache DB не создаётся. UI не связывает перенос с покупкой VPS.

## 4. CLI/API

Нужны операции: получить состояние, перечислить инструменты/алгоритмы/покрытие, импортировать список, создать/отменить загрузку, включить/выключить сбор, управлять live-конфигурацией, создать/отменить replay, получить результаты/CSV, проверить доставку, настроить возраст уведомлений и подписки, показать размер/число записей кэша и очистить подтверждённую область, независимо резервировать/восстанавливать две логические БД.

Названия маршрутов и CLI-команд здесь не фиксируются. Длительные операции возвращают идентификатор задания и наблюдаемый статус, а не держат один HTTP-запрос до завершения истории. Повторная отправка команды не должна случайно создавать одинаковые тяжёлые задачи.

## 5. Защита и управляемость

- Аутентификация администратора, защита state-changing запросов и журнал существенных действий.
- Секреты не попадают в логи, CSV, URL или экспорт конфигураций.
- Загружаемые списки имеют ограничение размера и проверку структуры; «импорт алгоритма» не равен выполнению недоверенного кода.
- Удаление истории/результатов требует явного диапазона, предварительного количества и подтверждения. Очистка кэша отделена от удаления ценных первичных данных.
- Экспорт CSV защищает табличные приложения от формул в произвольных текстовых полях; нормальные symbol/цены не изменяются скрыто.
- Запуск replay никогда по умолчанию не активирует торговлю и не рассылает тысячи исторических сообщений.
- Резервные копии и проверка восстановления охватывают две независимые логические БД без обязательного повторного API-fetch сохранённой истории. App DB содержит чувствительные данные push-подписок и защищается соответственно; прочие секреты резервируются отдельно с ограниченным доступом.

Позднейшее разделение ролей «администратор / автор стратегии / подписчик» возможно, но мультиарендность не реализуется заранее. Нельзя считать добавление поля user ID полноценной безопасной SaaS-изоляцией.

## 6. Утверждённый frontend-стек

| Область | Требование |
|---|---|
| Сборка | Vite; production отдаёт собранные статические файлы, не dev server |
| UI и язык | React + TypeScript со строгой проверкой типов, включая `strict` |
| Статический анализ | Строгий ESLint с type-aware правилами TypeScript; неявные обходы типов и unsafe-операции не маскируются приведениями/отключением правил |
| Стили | Tailwind CSS и единая система дизайн-токенов |
| Компоненты | Собственная библиотека shadcn/ui на Radix; альтернативная реализация на другой базе не подменяет выбранный Radix |
| Роутинг | React Router |
| Глобальное состояние | React Redux; локальное состояние конкретного компонента не требуется переносить в глобальное хранилище |
| Unit/component tests | Vitest |
| Browser/end-to-end tests | Playwright |
| Процесс разработки | TDD: сначала тест ожидаемого поведения, наблюдаемо падающий по нужной причине, затем минимальная реализация и рефакторинг при зелёных тестах |

Vite-сборка сама по себе не заменяет строгий typecheck. Проверка типов выполняется отдельным обязательным скриптом, наряду с lint, проверкой дизайн-системы, тестами и production build. Проверки запускаются локально и в CI; ошибки и нарушения не допускаются к слиянию/релизу. Конкретные версии пакетов фиксируются совместимым набором при создании проекта, а не плавающим `latest` при каждом запуске.

### Автоматические ограничения дизайн-системы

Дополнение владельца от 4 ноября 2026: интерфейс поддерживает светлую, тёмную и системную темы. Выбор доступен до и после входа, сохраняется локально в браузере; начальный режим — системный. Единственный переключаемый атрибут `data-theme="light|dark|system"` на `<html>` управляет палитрой через Tailwind `color-scheme` и парные токены `light-dark()`. Системный режим следует настройке ОС, явный выбор от неё не зависит. Предпочтение применяется до запуска приложения, отказ browser storage не блокирует вход или переключение темы. Тёмная палитра и интенсивность декоративного слоя сохраняются; светлая палитра использует те же компоненты и семантические токены.

Визуальное решение владельца от 4 ноября 2026: ориентир — присланный тёмный терминал Voltrex. Используем угольно-чёрную основу, тонкие нейтральные разделители, компактные контролы с умеренным скруглением, белый/серый текст и лавандовые выделения. Мягкие индиго-фиолетовые и розовые фоновые пятна должны быть примерно втрое слабее референса: единый коэффициент декоративного слоя `1/3`, без ослабления контраста текста, фокуса и контролов. Зелёный акцент допустим для подтверждающих действий, но цвет не заменяет текстовое состояние. Из референса переносится визуальный язык, не торговые функции, график, котировки или вымышленные показатели.

Изменения оформления выполняются через токены `@theme` Tailwind CSS v4 и локальную библиотеку `components/ui` на shadcn/ui/Radix. Не добавляем сырые CSS-селекторы, inline styles, стороннюю UI-библиотеку или индивидуальную тему страницы. Вне библиотеки допускается только подключение её компонентов вместо прежней разметки, без изменения поведения, API и бизнес-логики. Общий фон должен работать также на экране входа; навигация и формы остаются доступны на desktop/mobile и с клавиатуры.

В исходниках приложения запрещены произвольные inline-стили, CSS-in-JS, CSS Modules и самостоятельные stylesheet-файлы в обход Tailwind. Разрешённая системная точка CSS содержит Tailwind, тему/токены и необходимые базовые правила; это явная граница, не возможность прятать стили каждого экрана в общем файле. Произвольные значения вместо утверждённых токенов также проверяются как возможный обход системы.

Экраны используют интерактивные UI-компоненты через локальную библиотеку shadcn/ui. Запрещены другие библиотеки UI и самодельные button/input/dialog/select, обходящие её. Нативная семантическая разметка и layout-контейнеры не считаются второй библиотекой компонентов; primitives Radix и нативная реализация компонентов допустимы внутри контролируемого слоя библиотеки. Составные прикладные компоненты строятся из неё, а не запрещаются как таковые.

Проверки должны учитывать JSX и импорты/реэкспорты, а не только искать строку `style=`. Код зависимостей не переписывается под эти ограничения. Необходимые технические исключения для библиотечных механизмов допускаются только явно описанным узким allowlist внутри соответствующего адаптера; глобальное отключение правил или исключение всех экранов недопустимо. Специализированные графики, если потребуются, интегрируются через согласованный компонент библиотеки, не как неограниченное исключение для страницы.

Сами проверки имеют положительные/отрицательные fixtures: корректные компоненты/токены проходят, запрещённые импорты, сырые контролы и стили дают ошибку. TDD охватывает поведение компонентов и пользовательские сценарии; одних snapshot-тестов недостаточно. Browser tests проверяют ключевые действия, маршруты и состояния ошибок на desktop/mobile, не подменяя unit/component-проверки.

### Состав UI-библиотеки и поэтапное обновление экранов

Дополнение от 8 ноября 2026. Все экраны собираются только из локальной библиотеки `apps/web/src/components/ui` (shadcn/ui на Radix) и токенов Tailwind v4 из `apps/web/src/styles/global.css`; стилизация и самодельные контролы в обход библиотеки запрещены и проверяются автоматически. Базовый состав библиотеки расширяется: семейство Card (заголовок/описание/содержимое/подвал), PageHeader и SectionHeader, Badge с семантическими и статусными вариантами, Alert для ошибок и информационных сообщений, Field как единый паттерн «метка + поле + подсказка + ошибка», Checkbox и Switch на Radix-примитивах, семейство Table для списочных данных, Skeleton и Spinner для загрузки, EmptyState, Separator, Pagination, Collapsible и Tabs. Токены дополняются цветами warning/danger/info, шкалой радиусов, тенями и focus-ring; цвет никогда не является единственным носителем смысла — статус всегда продублирован текстом.

Типовые паттерны экранов: единый заголовок страницы с описанием и действиями; группы настроек как Card-секции; формы через Field; таблицы через семейство Table с tabular-nums для числовых колонок; состояния «загружается/ошибка/пусто» через Skeleton/Alert/EmptyState вместо текстовых заглушек; единый компонент пагинации. Обновление выполняется поэтапно и не меняет поведение, API, тексты и бизнес-логику: сначала токены и библиотека с тестами, затем пилотные экраны «Обзор» и «Сетапы» как контрольная точка владельца, затем остальные экраны, финальная проверка в светлой/тёмной темах на desktop/mobile и Playwright e2e. Визуальное направление от 4 ноября 2026 сохраняется.

### Brand-цвет и генерация палитры

Дополнение от 8 ноября 2026 по решению владельца. Brand-цветом платформы является лавандовый `primary` (светлая тема `#704593`), принятый вместе с референсом Voltrex 4 ноября. Все цветовые токены обеих тем генерируются из brand-цвета скриптом `scripts/generate-palette.mjs` (`npm run gen:palette`): фиолетовое семейство наследует hue brand, вторичный акцент rose и функциональные success/warning/danger/info имеют фиксированные hue и общую тональную сетку OKLCH. Сгенерированные значения записываются между маркерами `palette:begin/end` в `@theme` `apps/web/src/styles/global.css` и являются единственным источником цветов: компоненты и страницы используют только эти Tailwind-токены без сырых цветовых значений; правки палитры выполняются параметрами генератора и перегенерацией, а не ручным редактированием блока. Токены формы (радиусы, тень карточек, интенсивность декоративного слоя) также принадлежат генератору.

Тональные правки владельца от 8 ноября: в светлой теме все бордеры вдвое слабее прежних (светлота между фоном и прежним `input`); outline-кнопка при наведении меняет рамку и цвет текста на brand color, без заливки фона.

Полировка дизайн-системы от 8 ноября 2026 (Этап 4, в рамках одобренного направления Voltrex): карточки — сплошная подложка `bg-card`, радиус xl и мягкая тень `--shadow-card`; кнопки, поля ввода и селекты — `rounded-lg` на сплошном фоне; primary/success-кнопки с лёгкой тенью; заголовки таблиц — uppercase xs с letter-spacing; бейджи — пилюли (`rounded-full`); шапка приложения — sticky с фоновым blur; активный пункт навигации — фирменный tint (`primary/10` + `text-primary`). Палитра и тексты не менялись.

### Состояние и границы клиента

Лента live-сетапов загружается серверными страницами, без ограничения доступности последними 500 событиями. Поиск по инструменту, бирже и алгоритму применяется ко всей сохранённой ленте как буквальная подстрока без учёта регистра. Порядок — время закрытия по убыванию, затем ID по убыванию; UI загружает 25 записей, API допускает не более 500 за запрос. При листании сохраняется верхняя граница ID, полученная с первой страницей: новые записи с большим ID попадают в выдачу после «Обновить» или изменения фильтра, а не сдвигают уже открытые страницы. Это граница последовательности append-only ленты, не долгоживущая транзакция БД.

Live CSV — отдельная нефильтрованная выгрузка без ограничения числа строк, с верхней границей ID на момент начала. Сервер передаёт файл потоком, читает только экспортируемые поля ограниченными порциями и прекращает дальнейшее чтение после отключения клиента; возможный уже начатый запрос завершается без продолжения выгрузки. Файл передаётся менеджеру загрузок браузера без накопления полного Blob в памяти приложения; там же пользователь видит исход и отменяет загрузку. Требуются корректное CSV-экранирование, защита от формул и сохранение decimal-строк. Существующие восемь столбцов endpoint `GET /v1/export/setups.csv` сохраняются ради потребителей; снятие лимита не означает завершение расширенного архивного формата CSV v1 из `signals.md`.

React Redux хранит общее состояние интерфейса; он не заменяет серверную БД и не является единственным владельцем заданий, истории или настроек, которые должны переживать перезагрузку. Полученные данные и кеши клиента ограничены по объёму; большие истории/ленты загружаются страницами, подписки и запросы освобождаются при завершении области использования. В браузер не выдаются прямые доступы к БД или секреты серверных клиентов сервиса данных.
