# Принятые решения, вопросы и этапы

[К оглавлению PRD](PRD.md)

Версия 0.8. Решения 31 октября и 1 ноября дополнены выбором от 3 ноября 2026 года (backend-каркас, вариант B: обычный PostgreSQL без TimescaleDB ради переноса данных в другие приложения) и решением от 9 ноября 2026 года: вычислительный движок платформы сетапов переносится на Rust при неизменных сервисе рыночных данных, обеих БД и фронтенде. Решением от 10 ноября 2026 добавлен второй зеркальный алгоритм `price_drop_volume_spike` для лонг-сетапов. Уже полученные ответы не открываются повторно.

| Фоновые задания | Собственные очереди на таблицах заданий в БД соответствующего владельца (pg-boss не используется); сохранённое доменное состояние и идемпотентность остаются обязанностью приложения |

| Входные данные MVP | Только минутные OHLCV: цены, объём и оборот из API биржи |
| Момент сигнала | Только по закрытой минуте, одинаково в live и replay |
| Детализация | Не использовать секундные свечи, архивы сделок, тиковый поиск и выборочное уточнение сетапов |
| Первый источник | Непосредственно API Bybit; выбор REST/WS-механики остаётся архитектурной задачей |
| Другие биржи | Обязательная расширяемость идентичности инструментов, нормализации и подключения источников; вторую биржу в MVP не реализовывать |
| Дополнительные ряды | Предусмотреть возможность добавить funding, OI, mark/index price и long/short ratio; загрузку и применение отложить |
| Алгоритмы | Подключаемые доверенные модули, версии и параметры; без произвольного пользовательского кода/Pine |
| Оптимизация Plan A (10 ноября 2026) | Разрешено отдельное metadata-driven исследование в Rust: space-filling, multi-context sensitivity, multistart coarse-to-fine, single/pair/joint mutations и продолжающееся глобальное исследование; конечные домены, без обещания глобального оптимума. Score — равное среднее неокруглённых R всех фиксированных TP×SL-ячеек; minClosedPerCell default 1, неоценимая ячейка делает кандидата неоценимым |
| Владение исследованием | Сервер запускает работу асинхронно; browser reload/closure не отменяют, UI восстанавливает статус через GET; explicit Stop. При рестарте сервера незавершённые исследования failed, без автоматического возобновления. Одно активное исследование первоначально |
| Изоляция оптимизации | Отдельные metadata/status/progress/компактный победитель в app DB; raw и trials только на время исследования в bounded RAM/private temp. Нет обычных runs/batches, общих кешей или межисследовательской memoization; frozen свечи/пропуски, индивидуальный прогрев/cooldown, cleanup на всех исходах. Автоприменения в live нет; полный контракт в analytics.md §10 |
| Первый алгоритм | Рост цены >=12% за W=5 минут AND turnover этих минут строго >x3 среднего за 30 OR 7 дней, приведённого к W; окна/пороги параметризованы |
| Второй алгоритм | `price_drop_volume_spike` (решение от 10 ноября 2026): зеркало первого для лонг-сетапов — падение цены >=12% за те же W=5 минут AND идентичные объёмные условия; `price_drop_pct` вместо `price_growth_pct`, остальные параметры совпадают |
| Объёмные базы | Полные trailing 30/7 суток, среднее через суммарный объём и длительность; не медиана; обе базы обязательны, даже при OR |
| Повторы | Только временная отсечка 5 минут на пару/алгоритм, сброс условия не обязателен |
| Контракты | USDT perpetual |
| Historical-список | Все инструменты БД по умолчанию, включая делистнутые; CSV без заголовка с фильтром по БД; ручное добавление/удаление |
| Live-список | Импорт текущих торгуемых пар биржи, CSV с фильтром по текущему листингу, ручное добавление/удаление |
| Требования модуля | Вычисляемая из параметров глубина/полнота истории; для обоих алгоритмов 30 суток непрерывных минут на каждую оцениваемую минуту |
| Историческая загрузка | UI, даты от/до и пары; добавление только недостающих записей без перезаписи существующих |
| Live-автодогрузка | При запуске/разрыве/изменении требований недостающая история подтягивается одновременно со свежими данными; выбранная пара ждёт готовности |
| Частичный replay | Разрешён; рассматриваются все выбранные инструменты, оцениваются только пригодные минуты, пропуски объясняются |
| Цена и время | Close сигнальной минуты и время её окончания; Unix в секундах |
| Уведомления | UI и Web Push для поддерживаемых платформ, включая работу без открытой страницы; Telegram опционален, закрытый канал |
| Торговая интерпретация | Нейтральные события `price_volume_spike` / `price_drop_volume_spike` с меткой `WATCH`, не SHORT/LONG; шорт-/лонг-сторона — интерпретация владельца, не атрибут события |
| Возраст уведомления | Настройка UI, default 60 секунд от конца сигнальной минуты; повторные попытки не обновляют возраст, история/UI сохраняются |
| Масштаб/размещение | Два алгоритма (с 10 ноября 2026), около 500 live-пар, собственный сервер для первых тестов, без обязательного срока replay |
| Разделение БД | БД сервиса данных: рыночные ряды/метаданные и отдельно служебное состояние загрузчиков; БД платформы: алгоритмы, live/replay, сетапы, кеш и уведомления. Третья БД не обязательна |
| Сервис рыночных данных | Независимое приложение с биржевыми адаптерами, загрузками, постоянным сбором, каталогом, покрытием, собственными заданиями и API |
| API сервиса | Авторизованное чтение сохранённых данных отдельно от асинхронного пополнения; пакетное чтение, статусы/отмена, совместимые версии и OpenAPI с семантической документацией |
| Разделение ответственности | Платформа задаёт требуемые диапазоны по алгоритму; сервис не вычисляет сетапы/индикаторы стратегии и не хранит кеш replay. Прямого обхода API через БД/биржу нет |
| Развёртывание | Два приложения могут первоначально работать на одном сервере; компактный сервис с внутренними загрузчиками, без обязательных Kubernetes/отдельных биржевых микросервисов |
| Переносимость | Сервис переносится с совместимой программой, БД, состоянием загрузок и конфигурацией, без БД платформы и повторного API-fetch. Рыночная часть отдельно доступна через документированную схему/экспорт без работающего сервиса |
| Ключ кеша | Алгоритм+версия, все параметры, биржа/инструмент, точный период Unix-секунд; версия увеличивается после каждого изменения алгоритма |
| Принятая неточность кеша | Пропуски и версия рыночных данных не входят в ключ, догрузка не инвалидирует кеш; старый частичный результат может отличаться от нового расчёта |
| Bulk replay | Поиск отдельных ключей всех инструментов, вычисление misses, объединение и стабильная сортировка сетапов по времени |
| Очистка кеша | Из UI по бирже/инструменту для всех алгоритмов/версий/параметров/дат либо полная; размер/число записей видны, история рынка не удаляется |
| Состояние истории | UI-страница инструментов по биржам, начало/конец, проверенные пропуски; «нет данных» и «не проверено» не выдаются за полноту |
| Частота Bybit | Общий адаптивный допуск запросов, обязательное ожидание указанных сроков, замедление при throttling и ограниченное ускорение; обход/провоцирование бана исключены |
| Перенос движка на Rust | Платформа переписывается на Rust с побитовым паритетом сетапов/отчётов качества против эталонных фикстур TypeScript-реализации; эквивалентный перенос не меняет версию алгоритма и ключи кеша |
| Этапы перехода и откат | Каркас и паритет → полный порт → теневой пересчёт на tv с диффом против TS-движка → переключение прокси `/v1` → выдержка на реальной нагрузке; TS-движок сохраняется в репозитории и как мгновенный откат до конца приёмки, удаление — отдельное решение владельца |
| Распределение вычислений (задел) | Очередь в PostgreSQL (`FOR UPDATE SKIP LOCKED`) позволяет горизонтально добавлять воркеры; API stateless — реплики за балансировщиком; при появлении второй реплики сессии переезжают в таблицу БД аддитивной миграцией |
| Email-авторизация (задел) | Отложена решением от 9 ноября 2026; будущая реализация — аддитивные таблицы users/токены подтверждения по ссылке и роли, без ломки текущих API-ключей и cookie-сессий |

Внутриминутные пересечения вне контракта обоих режимов. Это сознательно выбранная гранулярность, не погрешность, которую затем исправляют секундными данными. Пропуски, исправления истории, прогрев и состояние по-прежнему проверяются.

Будущая торговля на разных биржах учитывается как направление расширения, но execution, ключи и ордера не входят в текущий продукт. Frontend, backend и обе PostgreSQL-БД выбраны. Параметры конкретного сервера и эксплуатационная конфигурация уточняются в плане запуска.

## 2. Закрытые уточнения и границы проверки

Основные вопросы версии 0.2 закрыты. Глубину загрузки выбирает пользователь в UI, поэтому единую фиксированную дату начала не требуется согласовывать заранее. История не удаляется автоматически, делистнутые пары сохраняются. Покупка VPS и предельное время replay сейчас не требуются.

| ID | Уточнение | Принятое решение |
|---|---|---|
| Q-01 | Торговая интерпретация | Закрыто: нейтральный всплеск, без LONG/SHORT |
| Q-07 | Запоздалые уведомления | Закрыто: настраиваемый возраст, default 1 минута; просроченные остаются в UI, но не отправляются как свежие |
| Q-11 | Доставка без открытого клиента | Закрыто: Web Push входит в MVP там, где технически поддерживается; force-quit/offline/запрет ОС не дают гарантии доставки |

Продуктовые уточнения и выбор frontend/backend/БД закрыты. На этапе реализации проверяются совместимость Web Push с политикой истечения, реальные квоты/ответы Bybit, пригодность ресурсов и независимое восстановление обычного PostgreSQL. Эти проверки не открывают заново принятые решения без конкретных новых оснований.

Формулы явно уточняют пограничные случаи: цена `>=12%` (для второго алгоритма — падение `>=12%`), объём `>3x`, OR баз, общее W=5 для цены/объёма; базы `[t-D,t)` включают текущие W минут согласно буквальному «за последние D дней». Повтор возможен ровно через 300 секунд. Эти определения доступны в `strategies.md`, а не спрятаны в реализации.

Детали экранов, packaging модулей, REST/WS и параметры PostgreSQL/backup уточняются при реализации и измерении сервера. Они не требуют заново спрашивать о выбранном поведении; обычный PostgreSQL не заменяется TimescaleDB без нового решения владельца.

## 3. Этапы работы

### Этап 0. Исследование и продуктовый PRD

Текущий результат: требования, источники, минутный контракт и точная формула первого алгоритма, сценарии списков/догрузки, уведомлений и переноса БД. Исследованные альтернативы сохранены в `research.md` как контекст, не как поддерживаемые режимы. Приложение ещё не реализовано.

### Этап 1. Утверждение продуктового контракта

Продуктовый контракт определён, включая нейтральное событие, возраст уведомлений, кеш и две БД. Проверить эталонные последовательности OR/строгого порога/отсечки и кеширования; согласованные решения не открываются повторно.

### Этап 2. Архитектурные гипотезы и ограниченный пилот

Основные технологии выбраны. Подготовить совместимые версии и минимальный каркас двух приложений/двух БД. Проверить сервис данных отдельным API-клиентом, пакетное чтение, add-only запись, общие загрузки/лимиты и независимый перенос обычного PostgreSQL. Проверить платформу live/replay с кешем и Web Push на сервере пользователя. Арендовать VPS не требуется; подробная последовательность находится в PLAN.md.

Этот этап начинается после обсуждения продукта. Сейчас не создаются backend, инфраструктура или торговый runtime.

### Этап 3. Вертикальный срез MVP

Одна версия алгоритма проходит весь путь: адаптивная UI-загрузка, страница покрытия/автодогрузка, нейтральный live-сетап, сохранение, возраст уведомления/Web Push, опциональный Telegram, replay, cache hit/miss/bulk/очистка и CSV в секундах. Управление доступно через CLI/API и web; проверяется независимый перенос БД истории без повторного скачивания.

Критерий: правильный и воспроизводимый пользовательский результат, а не наличие всех внутренних компонентов отдельно.

### Этап 4. Масштаб и эксплуатация

Расширить на целевой список инструментов, проверить одновременный replay/live, ошибки источников, рестарты, лимиты диска, отмену и восстановление. Подтвердить SLO и достаточность VPS. Оптимизировать обработку минутного ряда без пропуска событий или изменения семантики; секундную детализацию не добавлять.

### После MVP

Дополнительные алгоритмы и биржи, funding/OI/mark/index/long-short ratio, внешняя оценка стратегии. Возможный конструктор правил, ликвидации/стакан и другие функции обсуждаются при появлении потребности. Многопользовательский сервис и автоматическая торговля являются отдельными этапами с собственными рисками, полномочиями и требованиями. Наличие сигнальной платформы не означает автоматическую готовность к управлению деньгами.

## 4. Что ещё не утверждено

- Конкретные совместимые версии Node.js, Rust-тулчейна, крейтов, PostgreSQL и библиотек, размеры пулов/страниц и ресурсы сервера. Стек сервиса данных (Fastify/TypeScript), Rust-движок платформы и обычный PostgreSQL утверждены.
- Конкретные manifests/параметры развёртывания, предельные значения параллелизма воркеров и транспорт новых закрытий. Базовый сценарий плана использует предложенный Docker Compose; разделение на два приложения уже утверждено.
- Собственный Rust-движок платформы утверждён решением от 9 ноября 2026; адаптация существующих движков не выбиралась.
- Конкретная библиотека графиков и финальный дизайн web.
- Любая торговля, API keys, execution, плечо и управление капиталом.

PRD задаёт свойства продукта, допускает инженерные гипотезы и фиксирует их ограничения. Эти пункты обсуждаются после продуктовых решений, а не подменяют их.

Последовательность реализации и запуска с зависимостями и критериями готовности находится в [PLAN.md](../../PLAN.md). Backend и БД согласованы; план включает TDD/CI, вертикальный срез, перенос данных, восстановление после reboot и постепенное расширение до 500 пар. Само согласование стека не означает, что реализация или развёртывание уже выполнены.
