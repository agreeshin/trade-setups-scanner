# Принятые решения, вопросы и этапы

[К оглавлению PRD](PRD.md)

Базовая версия 0.8. Решения 31 октября и 1 ноября дополнены выбором от 3 ноября 2026 года (backend-каркас, вариант B: обычный PostgreSQL без TimescaleDB ради переноса данных в другие приложения) и решением от 9 ноября 2026 года: вычислительный движок платформы сетапов переносится на Rust при неизменных сервисе рыночных данных, обеих БД и фронтенде. Решением от 10 ноября 2026 добавлен второй зеркальный алгоритм `price_drop_volume_spike` для лонг-сетапов. Дополнение от 12 ноября 2026 утверждает stage 2 непрерывного адаптивного режима; решение от 13 ноября добавляет общий per-algorithm черновик настроек оптимизации и отдельный измеренный production-бюджет continuous snapshot. Подтверждённое владельцем решение от 14 ноября заменяет прежнее требование frozen/revalidated-префикса для live независимой инициализацией по текущим закрытым свечам без автоматической перепроверки завершённого победителя. Frozen-доказательство исходной исследовательской цепочки и уже сохранённое историческое происхождение не меняются. Исторические даты решений не меняются, уже полученные ответы не открываются повторно.

Score — равное среднее неокруглённых R всех фиксированных TP×SL-ячеек; minClosedPerCell default 1, неоценимая ячейка делает кандидата неоценимым |
| Владение разовым исследованием (10 ноября 2026) | Сервер запускает работу асинхронно; browser reload/closure не отменяют, UI восстанавливает статус через GET; explicit Stop. Незавершённый RAM-only поиск при рестарте failed, без crash-resume. Первоначально одно активное исследование во всей платформе; глобальная сериализация заменяется моделью stage 2 ниже, а не ожиданием завершения непрерывного процесса |
| Общая research FIFO и durable manual Pause (23 ноября 2026, решение 47) | Имеет приоритет над прежними строками о manual parallel/RAM-only/singleton: per-owner полная continuous-цепочка завершается, затем manual FIFO, затем прежний continuous cursor; live/replay/actual независимы. Несколько queued manual сохраняются после restart; queued DELETE атомарен с claim. Pause сохраняет тот же ID/frozen input/RNG/frontier/incumbent/original ledger и освобождает lane; Play ставит тот же ID в FIFO tail. Явные pause/queue не расходуют maxSeconds, acquisition/compute расходуют, бюджет не сбрасывается. Stop terminal/nonresumable с полностью оценённым partial result; DELETE только queued или terminal. Приватные артефакты bounded и освобождаются после terminal/drain. PRD commit до кода, после реализации commit/push без deploy; полный контракт analytics.md §10.4.1 |
| Изоляция разовой оптимизации | Отдельные metadata/status/progress/компактный победитель в app DB; raw и trials только на время исследования в bounded RAM/private temp. Нет обычных runs/batches, общих кешей или межисследовательской memoization; frozen свечи/пропуски, индивидуальный прогрев/cooldown, cleanup на всех исходах. Разовое исследование не применяет победителя в live. Обязательные служебные replay/аналитика и автоприменение stage 2 не распространяют эти побочные эффекты на разовый режим; контракт в analytics.md §10 |
| Непрерывная очередь (stage 2, 12 ноября 2026) | Последовательная на одного пользователя очередь комбинаций «алгоритм × независимый порог minSetupsPerDay». Между пользователями допускается параллельная работа; между алгоритмами/порогами требуется справедливость. Это не один глобальный последовательный исполнитель |
| Доступность ручных вычислений | Непрерывный процесс не блокирует ручные исследования, replay и аналитику, в том числе во время Stop/cleanup. Общий resource admission предусматривает зарезервированную/независимую ограниченную интерактивную ёмкость; ручная работа может исполняться при активной непрерывной, не только после конца её maxSeconds. Неограниченные пулы/очереди запрещены; существующие singleton DB/runtime/admission требуют переработки. Бюджеты — capacity.md |
| Владение непрерывным режимом | Durable desired state, ревизии конфигурации, пороговые слоты, поколения, дочерние задания и checkpoints принадлежат логическому пользователю. Leases/fencing запрещают записи/очистку устаревшего исполнителя; поздний pass не воскрешает остановленный профиль, поздний nonpass не выключает новое принятое поколение |
| Безопасные continuous-обновления (14 ноября 2026, подтверждено владельцем) | Только continuous получает приватные durable frozen input/search checkpoints в PostgreSQL и resume тех же study/generation/start/cutoff с исходным wall-clock deadline; manual one-shot остаётся RAM-only. Joined-batch checkpoint сохраняет RNG/frontier/counters/incumbent, не public result и не архив trials. Version/hash/owner/revision/lease fences, bounded chunks/storage и terminal/orphan cleanup обязательны; corrupt/incompatible state даёт видимую техническую ошибку без подмены input. Персистентный maintenance drain на пользователя закрывает новый admission, сохраняет heartbeat и полное завершение допущенных цепочек/live; resume не равен Start и не сбрасывает retries. Контракт — analytics.md §11.1.1; production rollout отдельно, №19 нельзя прерывать до полного post-chain/finalize, допускается только последующее однократное прерывание начавшегося №20. В этом историческом срезе Telegram был отложен, remote HTTP relay не включал локального publisher именно в тот этап; новый срез описан отдельной строкой ниже |
| Окно непрерывного исследования | Последние N дней от фактического начала исполнения каждого отдельного исследования, не от очереди/включения. Без maturation lag; точные frozen-даты переходят в служебный replay, сохранённый набор сетапов и сетку аналитики, без пересчёта на старте следующей стадии |
| Видимые стадии поколения | Непрерывные исследования, включая активные, входят в существующий список недавних исследований со структурированным origin/owner/generation. Для кандидата обязательны служебный replay в недавних прогонах, персистентный набор сетапов и последующая аналитика по нему. Переиспользование снимка/примитивов разрешено; матрица поиска не заменяет эти стадии |
| Допуск и рекомендация | Gate по полному среднему матрицы, default 0.15 R; рекомендация TP×SL-ячейки — median-capped 3×3, не замена gate. При включённой кластеризации maturity=0; unclosed исключены из performance R. Точные формулы и сохранённый частотный контракт — analytics.md |
| Автоприменение адаптивного поколения (уточнение 14 ноября 2026) | После исходных frozen research/replay/аналитики и gate live независимо прогревается по доступным текущим закрытым свечам с неизменяемыми настройками/universe кандидата. Равенство префиксу/состоянию исследования не требуется; автоматической revalidation/повторной оптимизации старого победителя нет, новые рекомендации — только из следующего полного round-robin-исследования. До готовности кандидата действует прежнее принятое поколение; fenced-замена атомарна на явном watermark (старое обрабатывает закрытия до него включительно, новое — после), проверяет owner/revision/lease. Stop/nonpass сохраняют деактивацию; ручные live-параметры и enabled не переписываются |
| Качественный и технический исходы | Завершение без подходящего победителя/непройденный gate останавливают соответствующий адаптивный профиль, но дальнейшее планирование продолжается. Техническая ошибка сохраняет прежний принятый профиль и явно показывает сбой; неполное поколение не применяется. Эти исходы не равны ручному Stop |
| Общий Stop непрерывного процесса | Один Stop по алгоритму, без построчного Stop дочерних непрерывных исследований. Прекращает планирование, деактивирует собственные адаптивные профили, отменяет/дренирует все свои незавершённые стадии; не затрагивает fixed live, ручные работы, другие алгоритмы/пользователей. После Stop нет сиротских продолжающихся расчётов |
| Очистка и история | До cleanup ставится fencing; удаляются идемпотентно только собственные незавершённые артефакты. Завершённые исследования/прогоны сохраняются, даже если следующий этап поколения не завершён; каскадное удаление готовой истории запрещено. Ручные линии доступны во время cleanup. Будущая retention не может молча удалять успешную историю |
| Явная очистка continuous-истории (13 ноября 2026, подтверждено владельцем) | Отдельная кнопка с модальным подтверждением удаляет прошлые continuous-исследования/поколения/runtime-состояние всех алгоритмов текущего пользователя только после полной остановки/drain. Сохраняются все runs/batches/quality, кеши и аналитические расчёты (включая post-chain), опубликованная live-история и её adaptive identity, конфигурация/черновик, manual/чужие данные. Происхождение/аналитика отделяются от удаляемого поколения; полные tombstones не создаются. Активность/сменившаяся preview отклоняют действие без частичной очистки. Построчное подтверждённое удаление терминальных оставшихся исследований и исторических запусков разрешено после снятия действующих ссылок; это не глобальная очистка кешей |
| Имя и неизменяемость сетапа | Редактируемое пользователем отображаемое имя алгоритма отделено от стабильных служебных id/name. Настройки поколения/рекомендации фиксируются в каждом выданном сетапе и не меняются вслед за очередным победителем или переименованием |
| Обогащённая рекомендация и график (15 ноября 2026, подтверждено владельцем) | Аддитивный версионированный снимок своего исследования/профиля: выбранные mean R/win rate, fitted end-minus-start, прогноз на raw signal close и прежнее полное среднее матрицы с новой подписью. Владелец явно подтвердил UTC-календарные дни raw-сигналов и единую календарную ось графика/динамики/прогноза, **включая изменение прежнего local/index-графика в «Аналитике»**. Равновесный по конечным дневным средним OLS, пропущенные даты не нули, first/last finite UTC endpoints, дробная координата raw-close относительно фиксированного UTC-midnight origin. Динамический frozen-период, без scientific rewrite/rerun/revalidation/old resend и без выдумывания недоступных метрик. Тёмный study-PNG «Динамика матожидания» 900×320 целиком с заголовком и обоими fitted endpoint labels; точный шаблон/порядок, два жирных заголовка, моноширинные symbol/числа с точкой, время без даты. Study ID только в приложении. Параллельные v1/v2, literal UTF-16 entities и bounded inline PNG, relay-first, старые queued/unfrozen jobs v1, новые явно v2; один photo+caption либо заранее один полный text-only fallback с видимой причиной, без усечения/второй публикации. HMAC/SSRF/private keys/TTL/dedupe/pending bytes неизменны. Формулы — analytics.md §11.5.1; шаблон, лимиты и совместимость — signals.md. Production этим срезом не разрешён |
| Исторический производный пересчёт действующих профилей (дополнение 15 ноября 2026, подтверждено владельцем) | Выполнить сейчас только для действующих legacy-профилей без дневного ряда: исходные raw replay-сетапы и доступные исторические свечи в исходных границах/cutoff, исходные TP/SL, направление и причинные effective analytics. Данные могут отличаться от frozen: отдельная производная версия/ревизия и фактическое происхождение обязательны, без подмены исходной оценки. Сверка counts/mean и причинного отбора с сохранённой ячейкой; расхождение явно фиксируется для решения, конфликтующие метрики не публикуются молча. Без новых research/replay/gate, изменения науки/истории, старых рекомендаций/delivery bytes или resend. Идемпотентное bounded-исполнение и проверка актуального active-профиля; новая ревизия только для последующих новых сетапов, без включения заменённых/остановленных профилей. Будущие поколения сохраняют штатный native capture; выполняющаяся цепочка №21/исследование №25 не перезапускается. Это разрешение на фактический ограниченный пересчёт, не только startup-функцию; контракт — [analytics.md §11.5.1](analytics.md#1151-обогащение-рекомендации-и-динамика-матожидания-15-ноября-2026) |
| Единый вероятностный прогноз Telegram (17 ноября 2026, подтверждено владельцем) | Новая производная ревизия заменяет только перспективно OLS-caption и отдельный spline/blend-PNG решений 15–16 ноября: decay-weighted TP-вероятность по закрытым TP/SL с shrinkage к независимому историческому либо явно эвристическому gross-break-even prior; `expectedR = (1 + TP/SL) × p − 1`. Caption и raw-close-маркер PNG используют одну frozen модель; cutoff, ретроспективная история и плоское продолжение обозначены, period mean отдельный. Per-setup overlay имеет новую версию/cache identity и bounded cleanup; старые рекомендации/артефакты/PNG/outbox bytes не меняются. Нет глобальных факторов/BTC, costs или damped-тренда первой версии; optimizer objective/gate/winner неизменны. `H`, `κ` и политика prior — ещё не калиброванные инженерные настройки, не произвольно утверждённые defaults и не вопрос выбора чисел владельцем. Сейчас только PRD и отчёт до кода. Исторические строки решений выше сохраняются; приоритет новой ревизии и точный контракт — [analytics.md §11.5.1](analytics.md#единый-вероятностный-прогноз-telegram-решение-от-17-ноября-2026), [signals.md](signals.md#единый-прогноз-в-тексте-и-png-решение-от-17-ноября-2026) |
| Общий forecast всей системы (последующее обобщение 17 ноября 2026, подтверждено владельцем) | Имеет приоритет над Telegram-only scope предыдущей строки: один численный модуль/versioned recipe для матриц/кривой ручной «Аналитики», manual/continuous и Telegram. Режимы mean/forecast/blend и default mean сохранены; основной forecast-метод новых рецептов — decayed probability, старое отсутствие method означает legacy trend, не новый default. Mean/F/decisionR различны, смесь двухкомпонентная, λ сохраняет 0.05..0.95/шаг0.01/default0.7. Общие TP/SL-only формулы, prior по q и UTC/frozen C; нет prior-only нуля, отдельного декоративного spline или Telegram-настроек. Новые score/ranking/robust pair и возможный admission намеренно меняются, но mean >= minMeanExpectancy и forecast/blend > minForecastExpectancy прежние, без дополнительного mean-gate; реальные evidence/frequency minima сохранены. H/κ/prior/λ фиксируются до исследования, не ищутся на том же train. Старые results/checkpoints/PNG/outbox bytes не переписываются; новые identities фиксируют рецепт. Паритет pure forecast требует одинаковых inputs/популяции/q/recipe/C, не означает равенства blend и caption. История ретроспективна, вероятность за C плоская. Defaults модели выбираются/версионируются/проверяются до активации; fit не доказывает качество, улучшение optimizer требует train-select/test-next. ## 2. Закрытые уточнения и границы проверки

Основные вопросы версии 0.2 закрыты. Глубину загрузки выбирает пользователь в UI, поэтому единую фиксированную дату начала не требуется согласовывать заранее. История не удаляется автоматически, делистнутые пары сохраняются. Покупка VPS и предельное время replay сейчас не требуются.

| ID | Уточнение | Принятое решение |
|---|---|---|
| Q-01 | Торговая интерпретация | Закрыто: нейтральный всплеск, без LONG/SHORT |
| Q-07 | Запоздалые уведомления | Закрыто: настраиваемый возраст, default 1 минута; просроченные остаются в UI, но не отправляются как свежие |
| Q-11 | Доставка без открытого клиента | Закрыто: Web Push входит в MVP там, где технически поддерживается; force-quit/offline/запрет ОС не дают гарантии доставки |

Продуктовые уточнения и выбор frontend/backend/БД закрыты. На этапе реализации проверяются совместимость Web Push с политикой истечения, реальные квоты/ответы Bybit, пригодность ресурсов и независимое восстановление обычного PostgreSQL. Эти проверки не открывают заново принятые решения без конкретных новых оснований. Для stage 2 также закрыты привязка окна к фактическому началу каждого исследования, отсутствие maturation lag/отложенного подтверждения, независимость ручных вычислений, различие качественного nonpass/технической ошибки/общего Stop и сохранность готовых дочерних результатов. Они не остаются вариантами на выбор при реализации.

Формулы явно уточняют пограничные случаи: цена `>=12%` (для второго алгоритма — падение `>=12%`), объём `>3x`, OR баз, общее W=5 для цены/объёма; базы `[t-D,t)` включают текущие W минут согласно буквальному «за последние D дней». Повтор возможен ровно через 300 секунд. Эти определения доступны в `strategies.md`, а не спрятаны в реализации.

Детали экранов, packaging модулей, параметры WS-подписок/timed REST fallback и PostgreSQL/backup уточняются при реализации и измерении сервера; выбор WS-first и независимой fresh lane уже утверждён 13 ноября. Они не требуют заново спрашивать о выбранном поведении; обычный PostgreSQL не заменяется TimescaleDB без нового решения владельца.

## 3. Этапы работы

### Этап 0. Исследование и продуктовый PRD

Исходный результат этапа: требования, источники, минутный контракт и точная формула первого алгоритма, сценарии списков/догрузки, уведомлений и переноса БД. Исследованные альтернативы сохранены в `research.md` как контекст, не как поддерживаемые режимы. Реализация приложения не входила в этот исходный этап; это не сводка текущего развёртывания.

### Этап 1. Утверждение продуктового контракта

Продуктовый контракт определён, включая нейтральное событие, возраст уведомлений, кеш и две БД. Проверить эталонные последовательности OR/строгого порога/отсечки и кеширования; согласованные решения не открываются повторно.

### Этап 2. Архитектурные гипотезы и ограниченный пилот

Основные технологии выбраны. Подготовить совместимые версии и минимальный каркас двух приложений/двух БД. Проверить сервис данных отдельным API-клиентом, пакетное чтение, add-only запись, общие загрузки/лимиты и независимый перенос обычного PostgreSQL. Проверить платформу live/replay с кешем и Web Push на сервере пользователя. Арендовать VPS не требуется; подробная последовательность находится в PLAN.md.

Этот этап начинается после обсуждения продукта. Его описание само по себе не разрешает изменения production или создание торгового runtime.

### Этап 3. Вертикальный срез MVP

Одна версия алгоритма проходит весь путь: адаптивная UI-загрузка, страница покрытия/автодогрузка, нейтральный live-сетап, сохранение, возраст уведомления/Web Push, опциональный Telegram, replay, cache hit/miss/bulk/очистка и CSV в секундах. Управление доступно через CLI/API и web; проверяется независимый перенос БД истории без повторного скачивания.

Критерий: правильный и воспроизводимый пользовательский результат, а не наличие всех внутренних компонентов отдельно.

### Этап 4. Масштаб и эксплуатация

Расширить на целевой список инструментов, проверить одновременный replay/live, ошибки источников, рестарты, лимиты диска, отмену и восстановление. Подтвердить SLO и достаточность VPS. ### Следующий срез: stage 2 адаптивного режима (12 ноября 2026)

Утверждён продуктовый контракт непрерывной очереди на пользователя и полного поколения «исследование → служебный replay → сохранённый набор → аналитика → gate → адаптивный live». До реализации требуется согласованная переработка singleton admission/runtime, tenant-владения, leases/fencing, видимости стадий и атомарного включения. Приёмка проверяет ручные вычисления при активной непрерывной работе и cleanup, stale pass/nonpass, рестарт, отсутствие сиротских расчётов и сохранность готовых/чужих результатов. Изолированный разовый Plan A и fixed live сохраняются; кластерное развёртывание и биржевые ордера не входят в этот срез. Подробные бюджеты и recovery — [capacity.md](capacity.md), семантика аналитики — [analytics.md](analytics.md), экранный контракт — [ux.md](ux.md).

Дополнение от 13 ноября разрешает реализацию оптимизации live после фиксации этого контракта в PRD: независимый WS-first fresh lane с timed REST fallback, shared bounded history и точным rolling-паритетом, прогрев кандидата с сохранением прежнего поколения до fenced watermark-переключения, durable-доставка вне детектора и follow-live refresh. Сначала проверяются паритет/границы смены поколения и основной путь, затем ёмкость 820 символов с явно посчитанными слотами и предварительные latency-цели; данные измерений ещё предстоит получить. Это разрешение на реализацию, не отдельное разрешение на production-деплой или покупку инфраструктуры.

Уточнение владельца от 14 ноября разрешает после изменения PRD заменить связь live с research-префиксом независимой инициализацией текущего состояния по закрытым свечам. Frozen-паритет обязателен только внутри исходных исследования, служебного replay и аналитики; итоговые параметры/рекомендации и прошлое происхождение неизменяемы. Ограниченное восстановление live-слота не удерживает очередь и не повторяет оценку старого победителя. Политика качественного nonpass, общий Stop, readiness, leases/fencing и дедупликация сохраняются; отдельного разрешения на production-деплой это уточнение не даёт.

## 4. Что ещё не утверждено

- Конкретные совместимые версии Node.js, Rust-тулчейна, крейтов, PostgreSQL и библиотек, размеры пулов/страниц и ресурсы сервера. Стек сервиса данных (Fastify/TypeScript), Rust-движок платформы и обычный PostgreSQL утверждены.
- Конкретные manifests/параметры развёртывания, предельные значения параллелизма воркеров, сроки REST fallback, объём bounded repair и конфигурация WS-соединений. WS-first fresh lane, независимая от backfill, с общими паузами уже утверждена; сверх действующих профилей допускается один replacement warmup. Базовый сценарий плана использует предложенный Docker Compose; разделение на два приложения уже утверждено.
- Численные CPU/RAM/I/O-квоты stage 2, размеры интерактивного резерва, параметры fairness/admission, retry/backoff и будущая конфигурация вычислительных кластеров. Последовательность непрерывной очереди на пользователя, доступность ручного исполнения при её активности и равномерное capacity-aware распределение будущих tenants уже утверждены; конкретные лимиты не подменяют эти свойства.
- Отдельная будущая retention-политика завершённых исследований/служебных прогонов и результатов. Stop и ресурсный дефицит не разрешают молча удалять успешную историю; граница удаления только своих незавершённых артефактов уже утверждена.
- Собственный Rust-движок платформы утверждён решением от 9 ноября 2026; адаптация существующих движков не выбиралась.
- Конкретная библиотека графиков и финальный дизайн web.
- Биржевая торговля, биржевые API keys, execution, плечо и управление капиталом. Разрешённое автоприменение аналитического профиля в адаптивном live не является разрешением размещать ордера.

PRD задаёт свойства продукта, допускает инженерные гипотезы и фиксирует их ограничения. Эти пункты обсуждаются после продуктовых решений, а не подменяют их.

Последовательность реализации и запуска с зависимостями и критериями готовности находится в [PLAN.md](../../PLAN.md). Backend и БД согласованы; исходный план расширения до 500 пар дополнен новым live-сценарием 820 символов с подсчётом профильных слотов. TDD/CI, вертикальный срез, перенос данных и восстановление после reboot сохраняются. Само согласование стека и latency-целей не означает, что реализация, измерение или развёртывание уже выполнены.
