# PRD: платформа торговых сетапов криптофьючерсов

Версия: 0.7, решение от 3 ноября 2026 года: утверждён backend-стек и вариант B для истории, обычный PostgreSQL без TimescaleDB. Приоритет выбора: независимый перенос и использование данных другими приложениями. Frontend и автозапуск из 0.6 сохранены. Исходное исследование: 28 октября 2026 года.

**Статус:** реализованы и развёрнуты два приложения со своими PostgreSQL-БД; дорабатываются пользовательские сценарии Web UI. Актуальные результаты, проверки и оставшиеся обязательства находятся в [PLAN.md](../../PLAN.md). Полная готовность всех функций PRD не заявляется. Инвентаризация изменений серверов ведётся локально в `docs/invent/` (исключена из Git); правила сопровождения находятся в корневом `AGENTS.md`.

Уточнение владельца от 4 ноября 2026: параметры алгоритма общие для истории и live и сохраняются в БД платформы. UI группирует их по алгоритмам; даты вводятся в часовом поясе браузера, API использует Unix seconds. Допускаются пропуски в окне: по умолчанию не более 1%, не более 5 подряд и обязательные последние 10 минут без пропусков. Все три ограничения настраиваемые; это уточнение заменяет прежнее требование абсолютной непрерывности.

## 1. Что за продукт

Система наблюдает за криптовалютными USDT perpetual и выпускает нейтральные события ценового/объёмного всплеска. Они доступны в UI; уведомления поддерживают Web Push на совместимых платформах, закрытый Telegram-канал опционален. Тот же алгоритм воспроизводится на истории либо возвращает ранее рассчитанный кешированный результат для внешнего анализа.

Рыночные данные предоставляет самостоятельный сервис: он подключается к биржам, хранит/пополняет историю и предоставляет авторизованным клиентам документированный API. Платформа сетапов использует этот API и не дублирует загрузчики. Сервис переносится отдельно и может использоваться другими системами без потери ранее загруженных данных.

Продукт состоит из трёх равно необходимых возможностей:

1. **Live-сканирование:** отслеживать выбранные инструменты, объяснять условия срабатывания, сохранять и отправлять сетапы.
2. **Историческое воспроизведение:** пройти выбранный период и список инструментов так, чтобы алгоритм не видел будущего, и получить воспроизводимый список сетапов.
3. **Рыночные данные:** загружать историю, непрерывно пополнять её при включённом сборе, показывать покрытие, пропуски, происхождение и точность данных.

Сетап здесь означает обнаруженное торговое условие по завершённой минуте, а не выполненную сделку. Его опорная цена не гарантирует возможность исполнения по этой цене.

## 3. Принятые решения

1. **Только минутные свечи и минутные объёмы.** Это единственная загружаемая свечная гранулярность MVP; исходные сделки и секундные свечи не загружаются. Длинные окна индикаторов рассчитываются по минутному ряду без требования отдельных рядов других таймфреймов.
2. **Сетапы только по закрытой минуте.** Live и replay используют `closed_bar_1m`, одинаковые правила, прогрев и состояние. Незакрытая свеча не порождает сигнал. Внутриминутные пересечения не восстанавливаются ни в одном режиме.
3. **Без выборочной детализации.** Нет цепочки 15m → 1m → 1s, архивов сделок для уточнения и отдельного приближённого режима поиска. Исторический запуск последовательно обрабатывает нужный минутный ряд. См. [воспроизведение](replay.md).
4. **Источник MVP: непосредственно API Bybit.** История и восстановление через API свечей; механизм live-получения закрытых свечей выбирается на архитектурном этапе между возможностями REST/WebSocket API. TradingView и сторонние поставщики не являются источниками MVP.
5. **Другие биржи предусмотрены как расширение.** Идентичность инструмента, единицы данных, контракт стратегии и формат результата не зависят только от Bybit. Подключение новой биржи не должно требовать переписывания алгоритмов и replay; реализация второго подключения сейчас не требуется.
6. **Funding, OI, mark/index price и long/short ratio предусмотрены на будущее.** Контракт хранения должен допускать дополнительные типизированные ряды и их собственную частоту/время доступности. Их загрузка, хранение реальных рядов и использование стратегиями не входят в MVP.
7. **Алгоритмы: подключаемые доверенные модули.** Выбор версии и редактируемые параметры, без произвольных скриптов/Pine из браузера. Начальная реализация на TypeScript, одинаковый модуль для live/replay; механизм регистрации/упаковки уточняется при реализации.
8. **Первый алгоритм:** рост close за последние W=5 минут не менее 12% **AND** объём этих минут строго больше x3 среднего за 30 **OR** 7 дней, приведённого к W минутам. Полная история обеих баз обязательна; объём измеряется оборотом USDT. Все пороги/окна заданы параметрами. Формулы: [алгоритмы](strategies.md).
9. **Два независимых списка инструментов.** Historical: все из БД по умолчанию, CSV/ручное редактирование, включая делистнутые. Live: текущие пары биржи, CSV/ручное редактирование, затем проверка пригодности по требованиям модуля.
10. **Данные дополняются, не перезаписываются.** UI-загрузка по датам и инструментам заполняет только недостающее. Live автоматически догружает требуемую предысторию параллельно свежим свечам; выбранная пара ждёт готовности, а не исчезает из списка.
11. **Частичный replay разрешён.** Рассматриваются все выбранные инструменты, оцениваются только минуты с нужной непрерывной предысторией. Непригодные интервалы и причины видны.
12. **Цена/время и повторы.** Цена сетапа равна close сигнальной минуты, время её окончанию; Unix в секундах. Для одной пары и алгоритма новый сетап возможен не раньше чем через пять минут, без обязательного сброса условия.
13. **Свой сервер и переносимая БД.** Первые тесты проводятся на сервере пользователя; аренда VPS не нужна. Исторический прогон не ограничен по времени. Базу можно перенести на другой сервер без повторной загрузки сохранённых данных через API.
14. **Нейтральное событие и доставка.** SHORT/LONG не назначаются. Максимальный возраст уведомления настраивается в UI, по умолчанию 60 секунд от окончания сигнальной минуты; старые сетапы остаются в истории/UI, но не рассылаются как свежие. Web Push включён для технически поддерживаемых окружений без обещания безусловной доставки при выключенном/принудительно закрытом клиенте.
15. **Кеш по инструменту.** Ключ: алгоритм и версия, все параметры, инструмент с биржей, точные start/end в Unix-секундах. Каждое изменение алгоритма увеличивает версию. Пропуски/ревизия рыночных данных не входят в ключ и не вызывают автоматический сброс; возможное расхождение с новым расчётом принято. Для списка выполняются bulk hits/misses и хронологический merge.
16. **Две БД с разными владельцами.** Сервис данных владеет самодостаточными рыночными рядами/метаданными и отдельно организованным служебным состоянием загрузки. Платформа владеет алгоритмами/настройками, live/replay-заданиями, сетапами, кешем и уведомлениями. Рыночная история переносима без платформы и расширяется под другие биржи/виды данных без повреждения старых рядов.
17. **Управление данными в UI.** Очистка кеша по бирже/инструменту для всех версий/параметров/дат либо целиком; отображение размера. Отдельная страница истории показывает инструменты по биржам, начало/конец данных и проверяемый индикатор пропусков.
18. **Адаптивная загрузка Bybit.** Общий контроль частоты и опубликованных квот, обязательное ожидание предписанного срока, замедление после ограничения и постепенное ускорение при стабильной работе. Ускорение ограничено безопасным потолком, не нацелено на намеренное получение бана.
19. **Самостоятельный сервис данных в MVP.** Биржевые адаптеры, квоты, загрузки, постоянный сбор, каталог и покрытие находятся внутри него. Чтение API возвращает сохранённые данные без скрытой загрузки; пополнение запускается отдельным асинхронным заданием. Есть пакетное чтение, статусы/отмена, версия API и собственная OpenAPI-документация.
20. **Независимость и защищённый доступ.** Сервис работает без платформы и переносится с БД/состоянием/конфигурацией. API предназначен авторизованным системам, не анонимному публичному использованию. При отказе платформе видна недоступность, а не ложное отсутствие данных; прямого fallback в чужую БД/биржу нет. На первом этапе оба приложения могут работать на одном сервере без обязательных Kubernetes или отдельного сервиса на каждую биржу.

Совпадение live со **свежим** replay проверяется при одинаковых закрытых свечах, версиях и начальном состоянии. Возврат кеша не обещает актуальности относительно догруженной истории; источник/время исходного расчёта видны. Минутная модель не устраняет пропуски и задержки доставки. Число сетапов не является показателем прибыльности.

## 4. Предлагаемые границы MVP

**Утверждённый frontend:** Vite, React + strict TypeScript, строгий type-aware ESLint, Tailwind CSS, shadcn/ui на Radix, React Router, React Redux, Vitest и Playwright с TDD. Обязательны скрипты проверки типов/стилей/компонентов, не допускающие обхода выбранной дизайн-системы. Подробный контракт: [frontend](ux.md#6-утверждённый-frontend-стек).

**Утверждённый backend обоих приложений:** поддерживаемая Node.js LTS, TypeScript strict, Fastify, TypeBox и OpenAPI; доступ к БД через node-postgres + Kysely с явным SQL для массовых операций. Фоновые задания выполняются через pg-boss в БД своего владельца, исторические вычисления изолированы от API в ограниченном пуле worker-процессов.

**Утверждённые БД:** обычный PostgreSQL для сервиса данных и для платформы, две независимые БД с раздельными доступами/миграциями/backup. Минутная история использует нативное разбиение по времени, начальная схема с месячными partitions. TimescaleDB не требуется и не включается в зависимости: независимое использование данных важнее ожидаемой выгоды его сжатия. Численные цены/объёмы сохраняются точно, без скрытого преобразования в binary float. Подробности: [хранение](data.md#8-хранение-и-происхождение).

**Обязательная эксплуатация:** включённые серверные компоненты автоматически запускаются после reboot и восстанавливают персистентное состояние/работу с сохранением ограничений биржи. Механизм развёртывания пока не выбран. Подробности: [автозапуск](capacity.md#9-автозапуск-и-восстановление-после-reboot).

MVP: Bybit USDT perpetual, один администратор, один доверенный алгоритм `price_volume_spike` и примерно 500 live-пар. Тип события нейтральный, не торговое направление SHORT/LONG. Добавление следующего модуля не должно требовать переделки платформы.

В MVP включаются отдельные списки historical/live, минутные OHLCV, адаптивная UI-загрузка/live-автодогрузка, страница покрытия, сканирование закрытых минут, частичный replay с кешем и его очисткой, CSV в Unix-секундах, UI/Web Push, опциональный Telegram и перенос отдельной БД истории. Принятые границы собраны в [решениях](decisions.md).

За пределами MVP: дополнительные биржи и рыночные ряды в рабочей эксплуатации, реальные ордера, ключи торговых аккаунтов, управление позициями, PnL/TP/SL-симулятор, оптимизация параметров, маркетплейс стратегий, биллинг, многопользовательская изоляция и недоверенные скрипты. Секундные свечи и детализация исключены из выбранного продукта, а не обязательны для следующего этапа. Будущая торговля на разных биржах остаётся отдельным расширением и не меняет смысл сохранённых сетапов.

## 5. Критерии готовности продукта

- Администратор выбирает инструменты, версию алгоритма и параметры; точность фиксирована как `closed_bar_1m`. До запуска система показывает достаточность минутной истории и стоимость догрузки.
- Ни live, ни replay не используют незакрытые свечи или секундные данные для выдачи сетапов.
- Live выдаёт объяснимый сохранённый сетап в UI без обязательной настройки Telegram. Отказ разрешения браузерных уведомлений или Telegram не теряет результат.
- Replay не использует будущие данные; одинаковые входные события, версии и начальное состояние дают одинаковые смысловые сетапы.
- Результат включает CSV и описание запуска с версией, разрешением, происхождением и ограничениями данных.
- Нехватка истории, пропуск данных и отсутствие торгов не подменяются друг другом или выводом «сигналов нет».
- Остановка/возобновление сбора и повторная загрузка не повреждают историю и не создают дублей рыночных записей.
- Администратор видит состояние системы, активные задачи, покрытие, ошибки и бюджет хранилища.
- Исторический запуск рассматривает делистнутые пары из БД; live-список проверяется по текущему листингу. CSV списков одноколоночный, без заголовка; исключения видны.
- Повторная/перекрывающаяся загрузка не перезаписывает закрытые свечи; live-автодогрузка восстанавливает нужный алгоритму контекст.
- После переноса БД на другой сервер сохранены покрытие и результат контрольного replay, полная повторная API-загрузка не требуется.
- БД истории восстанавливается без БД приложения; добавление других источников/типов не меняет смысл старых данных.
- Сервис данных запускается отдельно, обслуживает независимого авторизованного API-клиента и переносится без БД платформы. Задания загрузки и сроки ожидания не теряются, заполненные диапазоны повторно не скачиваются.
- Read API не инициирует загрузку; повторные/пересекающиеся запросы пополнения используют общую работу. Недоступность сервиса явно отличается от пустого ряда; документация API соответствует реализации.
- Одинаковый ключ получает кеш, изменённые версия/параметр/инструмент/период требуют расчёта; догрузка пропусков сама кеш не сбрасывает. Очистка не затрагивает историю рынка.
- Просроченное уведомление не отправляется повторно и не исчезает из UI-истории; Web Push проверен на согласованном поддерживаемом окружении.
- Загрузчик соблюдает явные сроки ожидания/квоты; throttling не вызывает цикл частых ретраев, увеличение параллелизма или обход блокировки.
- Ресурсные показатели измерены на сервере пользователя при одном алгоритме и примерно 500 парах; оценки из PRD не выданы за результаты benchmark. Обязательный срок replay не задаётся.
