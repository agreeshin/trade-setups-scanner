# PRD: платформа торговых сетапов криптофьючерсов

Версия: 0.9, решения владельца от 12–13 ноября 2026 года: согласованы непрерывные исследования и адаптивные live-сетапы с торговыми рекомендациями, а также общий сохраняемый черновик настроек ручной и непрерывной оптимизации для каждого алгоритма. Решения 0.8 от 9 ноября (Rust-движок), 0.7 от 3 ноября (две обычные PostgreSQL-БД без TimescaleDB), frontend и автозапуск из 0.6 сохраняются для неизменяемых частей. Приоритет независимого переноса и использования рыночных данных другими приложениями не меняется. Исходное исследование: 28 октября 2026 года.

**Статус:** реализованы и развёрнуты два приложения со своими PostgreSQL-БД; дорабатываются пользовательские сценарии Web UI. Актуальные результаты, проверки и оставшиеся обязательства находятся в [PLAN.md](../../PLAN.md). Полная готовность всех функций PRD не заявляется. Инвентаризация изменений серверов ведётся локально в `docs/invent/` (исключена из Git); правила сопровождения находятся в корневом `AGENTS.md`.

Уточнение владельца от 4 ноября 2026: постоянные параметры алгоритма общие для ручной истории и фиксированного live и сохраняются в БД платформы. Адаптивные профили по решению от 12 ноября хранят отдельные снимки и не перезаписывают эти настройки. UI группирует параметры по алгоритмам; API использует Unix seconds, отображение дат определяется контрактом интерфейса. Допускаются пропуски в окне: по умолчанию не более 1%, не более 5 подряд и обязательные последние 10 минут без пропусков. Все три ограничения настраиваемые; это уточнение заменяет прежнее требование абсолютной непрерывности.

## 1. Что за продукт

Система наблюдает за криптовалютными USDT perpetual и выпускает события ценового/объёмного всплеска. Постоянный live сохраняет нейтральные WATCH-события; согласованный адаптивный режим добавляет направление SHORT/LONG и условный план сделки на основе непрерывных исследований. Сетапы доступны в UI; уведомления поддерживают Web Push на совместимых платформах, закрытый Telegram-канал опционален. Тот же алгоритм воспроизводится на истории либо возвращает ранее рассчитанный кешированный результат для внешнего анализа.

Рыночные данные предоставляет самостоятельный сервис: он подключается к биржам, хранит/пополняет историю и предоставляет авторизованным клиентам документированный API. Платформа сетапов использует этот API и не дублирует загрузчики. Сервис переносится отдельно и может использоваться другими системами без потери ранее загруженных данных.

Основные возможности продукта:

1. **Live-сканирование:** отслеживать выбранные инструменты, объяснять условия срабатывания, сохранять и отправлять сетапы.
2. **Историческое воспроизведение:** пройти выбранный период и список инструментов так, чтобы алгоритм не видел будущего, и получить воспроизводимый список сетапов.
3. **Рыночные данные:** загружать историю, непрерывно пополнять её при включённом сборе, показывать покрытие, пропуски, происхождение и точность данных.
4. **Непрерывные исследования и адаптивные рекомендации:** исследовать скользящий период, проверять найденные параметры и обновлять независимые live-профили с понятными условными планами сделки; это согласованный следующий этап.

Сетап здесь означает обнаруженное торговое условие по завершённой минуте, а не выполненную сделку. Его опорная цена не гарантирует возможность исполнения по этой цене.

## 3. Принятые решения

1. **Только минутные свечи и минутные объёмы.** Это единственная загружаемая свечная гранулярность MVP; исходные сделки и секундные свечи не загружаются. Длинные окна индикаторов рассчитываются по минутному ряду без требования отдельных рядов других таймфреймов.
2. **Сетапы только по закрытой минуте.** Live и replay используют `closed_bar_1m`, одинаковые правила, прогрев и состояние. Незакрытая свеча не порождает сигнал. Внутриминутные пересечения не восстанавливаются ни в одном режиме.
3. **Без выборочной детализации.** Нет цепочки 15m → 1m → 1s, архивов сделок для уточнения и отдельного приближённого режима поиска. Исторический запуск последовательно обрабатывает нужный минутный ряд. См. [воспроизведение](replay.md).
4. **Источник MVP: непосредственно API Bybit.** История и восстановление через API свечей; механизм live-получения закрытых свечей выбирается на архитектурном этапе между возможностями REST/WebSocket API. TradingView и сторонние поставщики не являются источниками MVP.
5. **Другие биржи предусмотрены как расширение.** Идентичность инструмента, единицы данных, контракт стратегии и формат результата не зависят только от Bybit. Подключение новой биржи не должно требовать переписывания алгоритмов и replay; реализация второго подключения сейчас не требуется.
6. **Funding, OI, mark/index price и long/short ratio предусмотрены на будущее.** Контракт хранения должен допускать дополнительные типизированные ряды и их собственную частоту/время доступности. Их загрузка, хранение реальных рядов и использование стратегиями не входят в MVP.
7. **Алгоритмы: подключаемые доверенные модули.** Выбор версии и редактируемые параметры, без произвольных скриптов/Pine из браузера. Одинаковый модуль для live/replay; реализация доверенных модулей — Rust-компоненты с версионированным реестром (решение от 9 ноября 2026, до завершения перехода действует TypeScript-реализация как эталон паритета).
8. **Первый алгоритм:** рост close за последние W=5 минут не менее 12% **AND** объём этих минут строго больше x3 среднего за 30 **OR** 7 дней, приведённого к W минутам. Полная история обеих баз обязательна; объём измеряется оборотом USDT. Все пороги/окна заданы параметрами. Формулы: [алгоритмы](strategies.md). **Второй алгоритм (решение от 10 ноября 2026):** `price_drop_volume_spike`, зеркало первого для лонг-сетапов — падение close за те же W=5 минут не менее 12% **AND** идентичные объёмные условия; параметр `price_drop_pct` вместо `price_growth_pct`, остальные параметры совпадают.
9. **Два независимых списка инструментов.** Historical: все из БД по умолчанию, CSV/ручное редактирование, включая делистнутые. Live: текущие пары биржи, CSV/ручное редактирование, затем проверка пригодности по требованиям модуля.
10. **Данные дополняются, не перезаписываются.** UI-загрузка по датам и инструментам заполняет только недостающее. Live автоматически догружает требуемую предысторию параллельно свежим свечам; выбранная пара ждёт готовности, а не исчезает из списка.
11. **Частичный replay разрешён.** Рассматриваются все выбранные инструменты, оцениваются только минуты с нужной непрерывной предысторией. Непригодные интервалы и причины видны.
12. **Цена/время и повторы.** Цена сетапа равна close сигнальной минуты, время её окончанию; Unix в секундах. Начальный cooldown алгоритмов — пять минут, без обязательного сброса условия; эффективное значение задаётся параметрами. Для адаптивного режима состояние и дедупликация независимы по профилям пользователя/алгоритма/порога частоты, а смена поколения не создаёт повтор того же события.
13. **Свой сервер и переносимая БД.** Первые тесты проводятся на сервере пользователя; аренда VPS не нужна. Исторический прогон не ограничен по времени. Базу можно перенести на другой сервер без повторной загрузки сохранённых данных через API.
14. **Событие, рекомендация и доставка.** Постоянные и старые события сохраняют WATCH; адаптивные получают SHORT/LONG из конфигурации исследования и условный план, не факт сделки. Выдача происходит сразу после распознавания закрытой сигнальной минуты, без ожидания time-shift или проверки будущей цены: рекомендуемый вход равен времени сигнала плюс time-shift, решение принимает пользователь. Максимальный возраст уведомления настраивается в UI, по умолчанию 60 секунд от окончания исходной сигнальной минуты; time-shift этот срок не продлевает. Старые сетапы остаются в истории/UI, но не рассылаются как свежие. Web Push не обещает безусловной доставки при выключенном/принудительно закрытом клиенте.
15. **Кеш по инструменту.** Ключ: алгоритм и версия, все параметры, инструмент с биржей, точные start/end в Unix-секундах. Каждое изменение алгоритма увеличивает версию. Пропуски/ревизия рыночных данных не входят в ключ и не вызывают автоматический сброс; возможное расхождение с новым расчётом принято. Для списка выполняются bulk hits/misses и хронологический merge.
16. **Две БД с разными владельцами.** Сервис данных владеет самодостаточными рыночными рядами/метаданными и отдельно организованным служебным состоянием загрузки. Платформа владеет алгоритмами/настройками, live/replay-заданиями, сетапами, кешем и уведомлениями. Рыночная история переносима без платформы и расширяется под другие биржи/виды данных без повреждения старых рядов.
17. **Управление данными в UI.** Очистка кеша по бирже/инструменту для всех версий/параметров/дат либо целиком; отображение размера. Отдельная страница истории показывает инструменты по биржам, начало/конец данных и проверяемый индикатор пропусков.
18. **Адаптивная загрузка Bybit.** Общий контроль частоты и опубликованных квот, обязательное ожидание предписанного срока, замедление после ограничения и постепенное ускорение при стабильной работе. Ускорение ограничено безопасным потолком, не нацелено на намеренное получение бана.
19. **Самостоятельный сервис данных в MVP.** Биржевые адаптеры, квоты, загрузки, постоянный сбор, каталог и покрытие находятся внутри него. Чтение API возвращает сохранённые данные без скрытой загрузки; пополнение запускается отдельным асинхронным заданием. Есть пакетное чтение, статусы/отмена, версия API и собственная OpenAPI-документация.
20. **Независимость и защищённый доступ.** Сервис работает без платформы и переносится с БД/состоянием/конфигурацией. API предназначен авторизованным системам, не анонимному публичному использованию. При отказе платформе видна недоступность, а не ложное отсутствие данных; прямого fallback в чужую БД/биржу нет. На первом этапе оба приложения могут работать на одном сервере без обязательных Kubernetes или отдельного сервиса на каждую биржу.
21. **Перенос вычислительного движка платформы на Rust (решение от 9 ноября 2026).** Сервис рыночных данных, обе БД PostgreSQL (схемы и миграции) и фронтенд не меняются; платформа сетапов переписывается на Rust с сохранением HTTP-контракта `/v1`, OpenAPI, ключей кеша и семантики алгоритмов. Эквивалентный перенос побитово воспроизводит сетапы и отчёты качества на эталонных фикстурах TypeScript-реализации, поэтому версия алгоритма и существующий кеш не инвалидируются. Переход поэтапный: каркас и паритет → полный порт → теневой пересчёт на tv с диффом против прежнего движка → переключение прокси `/v1` → выдержка на реальной нагрузке. Прежний TypeScript-движок сохраняется в репозитории и как мгновенный откат до завершения приёмки; удаление — отдельное явное решение владельца. Задел на будущее: горизонтальное масштабирование воркеров очереди, stateless API-реплики за балансировщиком, email-авторизация с подтверждением по ссылке (отложена, добавляется аддитивно). Подробности: [решения](decisions.md), [воспроизведение](replay.md), [ресурсы](capacity.md).

22. **Непрерывное исследование и адаптивные профили (12 ноября 2026).** Каждая пара алгоритм × порог «Минимум сетапов в день» имеет независимый профиль; пороги задаются отдельным списком. В момент фактического старта очередного исследования фиксируются последние N суток без отступа на горизонт сделки; эти же даты и снимок входных данных используются служебным replay и аналитикой сохранённого набора. Незакрытые сделки не участвуют в матожидании; ограничение выборки по уже закрывшимся сделкам явно показывается. Кластеризация адаптивного режима, когда включена, всегда выбирает первый сигнал (`maturity=0`). Гейт — неокруглённое среднее всей TP×SL-матрицы, default `0.15 R`; выбор устойчивой ячейки отделён от гейта. В сетапе показывается исходное R выбранной ячейки, а не её оценка устойчивости. Полный контракт: [аналитика](analytics.md), [сетапы](signals.md).
23. **Очереди, история и остановка (12 ноября 2026).** Непрерывные исследования идут последовательно по алгоритмам и порогам одного пользователя, но не занимают всю вычислительную ёмкость: ручные исследования, исторические запуски и аналитика могут выполняться, пока непрерывная задача работает. Будущие пользователи работают параллельно с равномерным распределением нагрузки с учётом ёмкости кластеров. Активные и завершённые исследования видны в общей истории с признаком происхождения; остановка непрерывных доступна только общим действием по алгоритму. Остановка отменяет работу, исключает позднюю активацию и очищает только принадлежащие ей незавершённые артефакты; завершённые исследования и запуски сохраняются. Внешнее редактируемое имя алгоритма отделено от служебного имени и идентификатора. Подробнее: [интерфейсы](ux.md), [ресурсы](capacity.md).
24. **Общий черновик оптимизации (13 ноября 2026).** Для каждого алгоритма платформа хранит один пользовательский черновик в своей PostgreSQL-БД, а не в БД рыночной истории и не только в browser storage. Общие поля scope, baseline и поисковых доменов загружаются одинаково в ручную и непрерывную формы; календарный период ручного режима и `lookbackDays`/пороговые профили непрерывного режима сохраняются в том же документе как режимные поля и применяются только соответствующей форме. Открытие любой формы сначала загружает черновик, а потеря фокуса редактируемого поля сохраняет актуальный bounded-документ. Это не запускает расчёт, не меняет активную работу и не переписывает снимки истории.

Совпадение live со **свежим** replay проверяется при одинаковых закрытых свечах, версиях и начальном состоянии. Для адаптивного режима сравниваются raw-сигналы и причинный выбор первого в кластере: будущий ценовой фильтр оценивается ретроспективно в аналитике, но остаётся условием для пользователя в немедленном уведомлении. Возврат обычного кеша не обещает актуальности относительно догруженной истории; источник/время исходного расчёта видны. Такой кеш без проверки входов не является основанием автоматической активации адаптивного профиля. Минутная модель не устраняет пропуски и задержки доставки. Число сетапов не является показателем прибыльности.

## 4. Предлагаемые границы MVP

**Утверждённый frontend:** Vite, React + strict TypeScript, строгий type-aware ESLint, Tailwind CSS, shadcn/ui на Radix, React Router, React Redux, Vitest и Playwright с TDD. Обязательны скрипты проверки типов/стилей/компонентов, не допускающие обхода выбранной дизайн-системы. Подробный контракт: [frontend](ux.md#6-утверждённый-frontend-стек).

**Утверждённый backend (обновление 0.8 от 9 ноября 2026):** сервис рыночных данных — поддерживаемая Node.js LTS, TypeScript strict, Fastify, TypeBox и OpenAPI; доступ к БД через node-postgres + Kysely с явным SQL для массовых операций, без изменений при переносе движка. Вычислительный движок платформы сетапов — Rust (axum/tokio для API, sqlx для PostgreSQL) с теми же схемами/миграциями обеих БД, тем же JSON-контрактом `/v1` и OpenAPI. Фоновые задания каждого приложения — собственные очереди на таблицах в БД своего владельца (pg-boss не используется); исторические вычисления изолированы от API в воркерах с явно ограниченным и настраиваемым параллелизмом. До завершения переноса действует прежняя TypeScript-реализация платформы; этапы перехода и отката — в [решениях](decisions.md).

**Утверждённые БД:** обычный PostgreSQL для сервиса данных и для платформы, две независимые БД с раздельными доступами/миграциями/backup. Минутная история использует нативное разбиение по времени, начальная схема с месячными partitions. TimescaleDB не требуется и не включается в зависимости: независимое использование данных важнее ожидаемой выгоды его сжатия. Численные цены/объёмы сохраняются точно, без скрытого преобразования в binary float. Подробности: [хранение](data.md#8-хранение-и-происхождение).

**Обязательная эксплуатация:** включённые серверные компоненты автоматически запускаются после reboot и восстанавливают персистентное состояние/работу с сохранением ограничений биржи. Механизм развёртывания пока не выбран. Подробности: [автозапуск](capacity.md#9-автозапуск-и-восстановление-после-reboot).

Исходный MVP: Bybit USDT perpetual, один администратор, два доверенных алгоритма (`price_volume_spike` и `price_drop_volume_spike`) и примерно 500 live-пар. Постоянный live сохраняет нейтральный тип события; согласованное расширение добавляет адаптивные рекомендации SHORT/LONG. Добавление следующего модуля не должно требовать переделки платформы.

В MVP включаются отдельные списки historical/live, минутные OHLCV, адаптивная UI-загрузка/live-автодогрузка, страница покрытия, сканирование закрытых минут, частичный replay с кешем и его очисткой, CSV в Unix-секундах, UI/Web Push, опциональный Telegram и перенос отдельной БД истории. Принятые границы собраны в [решениях](decisions.md).

За пределами текущего этапа: дополнительные биржи и рыночные ряды в рабочей эксплуатации, реальные ордера, ключи торговых аккаунтов, управление позициями, полноценный симулятор исполнения/PnL, маркетплейс стратегий, биллинг и недоверенные скрипты. Многопользовательский запуск и развёртывание нескольких вычислительных кластеров — будущий этап, но принадлежность задач пользователю, независимость очередей и возможность балансировки закладываются сейчас. Диагностические TP/SL-расчёты разрешены контрактом [аналитики](analytics.md). Секундные свечи и детализация исключены из выбранного продукта, а не обязательны для следующего этапа. Будущая автоматическая торговля через API бирж предусмотрена как расширение; этот PRD-этап разрешает автоматическое применение результата к адаптивным рекомендациям, но не размещение ордеров.

Решения владельца от 10 и 12 ноября 2026: разрешены отдельное ретроспективное исследование алгоритма по Plan A и непрерывная последовательность исследований. Серверный Rust-оптимизатор ищет лучший проверенный вариант в конечных пользовательских доменах, без обещания глобального оптимума или будущей доходности. Оценка — равновесное среднее неокруглённых R по фиксированной выбранной TP×SL-матрице; неоценимые ячейки не исключаются из среднего. Работа продолжается после закрытия/перезагрузки браузера, статус восстанавливается через API. Ручное одноразовое исследование само не запускает replay и не меняет live. Прежний общий запрет автоприменения снят: непрерывный процесс создаёт явно помеченный служебный replay, сохраняет набор, рассчитывает аналитику и только после полной проверки атомарно заменяет свой адаптивный профиль. Обычные настройки и исторические сетапы не перезаписываются. Полный контракт, включая хранение и ограничения воспроизводимости: [аналитика](analytics.md).

## 5. Критерии готовности продукта

- Администратор выбирает инструменты, версию алгоритма и параметры; точность фиксирована как `closed_bar_1m`. До запуска система показывает достаточность минутной истории и стоимость догрузки.
- Ни live, ни replay не используют незакрытые свечи или секундные данные для выдачи сетапов.
- Live выдаёт объяснимый сохранённый сетап в UI без обязательной настройки Telegram. Отказ разрешения браузерных уведомлений или Telegram не теряет результат.
- Replay не использует будущие данные; одинаковые входные события, версии и начальное состояние дают одинаковые смысловые сетапы.
- Результат включает CSV и описание запуска с версией, разрешением, происхождением и ограничениями данных.
- Нехватка истории, пропуск данных и отсутствие торгов не подменяются друг другом или выводом «сигналов нет».
- Остановка/возобновление сбора и повторная загрузка не повреждают историю и не создают дублей рыночных записей.
- Администратор видит состояние системы, активные задачи, покрытие, ошибки и бюджет хранилища.
- Исторический запуск рассматривает делистнутые пары из БД; live-список проверяется по текущему листингу. CSV списков одноколоночный, без заголовка; исключения видны.
- Повторная/перекрывающаяся загрузка не перезаписывает закрытые свечи; live-автодогрузка восстанавливает нужный алгоритму контекст.
- После переноса БД на другой сервер сохранены покрытие и результат контрольного replay, полная повторная API-загрузка не требуется.
- БД истории восстанавливается без БД приложения; добавление других источников/типов не меняет смысл старых данных.
- Сервис данных запускается отдельно, обслуживает независимого авторизованного API-клиента и переносится без БД платформы. Задания загрузки и сроки ожидания не теряются, заполненные диапазоны повторно не скачиваются.
- Read API не инициирует загрузку; повторные/пересекающиеся запросы пополнения используют общую работу. Недоступность сервиса явно отличается от пустого ряда; документация API соответствует реализации.
- Одинаковый ключ получает кеш, изменённые версия/параметр/инструмент/период требуют расчёта; догрузка пропусков сама кеш не сбрасывает. Очистка не затрагивает историю рынка.
- Просроченное уведомление не отправляется повторно и не исчезает из UI-истории; Web Push проверен на согласованном поддерживаемом окружении.
- Загрузчик соблюдает явные сроки ожидания/квоты; throttling не вызывает цикл частых ретраев, увеличение параллелизма или обход блокировки.
- Ресурсные показатели измерены на сервере пользователя при одном алгоритме и примерно 500 парах; оценки из PRD не выданы за результаты benchmark. Обязательный срок replay не задаётся.
- Непрерывный процесс последовательно обслуживает пороги/алгоритмы пользователя, восстанавливается после reload/restart и не блокирует выполнение ручных исследований, replay и аналитики. Развёртывание будущих кластеров не выдаётся за текущую возможность.
- Каждое поколение сохраняет фактические границы последних N суток, входы и параметры всей цепочки. При замене сохраняется неизменяемое происхождение уже выданных рекомендаций; неуспешная старая попытка не может выключить более новый профиль.
- Матрица и выбранная TP/SL-пара проходят согласованные проверки; незакрытые сделки не попадают в R. Немедленное уведомление не утверждает выполнения будущего условия входа и использует внешнее имя алгоритма.
- Общая остановка непрерывного процесса по алгоритму прекращает его работу и удаляет только его незавершённые артефакты. Завершённые исследования/запуски, ручные задачи и данные других пользователей сохранены; у непрерывного исследования нет отдельной кнопки остановки.
