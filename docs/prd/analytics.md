## 1. Назначение и границы

Аналитика выполняет ретроспективный backtest накопленных наборов сетапов: моделирует TP/SL-сделки от каждого сетапа, считает матожидание в матрицах TP×SL и построчные закрытия. Это диагностический инструмент, а не торговый симулятор: комиссии, funding, проскальзывание, размер позиции и реальное исполнение ордеров не моделируются.

Вне границ: автоматическая торговля, прогнозы доходности, walk-forward-оценки. Оптимизация параметров отдельно разрешена решением владельца от 10 ноября 2026 по разделу 10; это не меняет обычные наборы и кеши разделов 2–9. Аналитика ничего не пишет в сервис данных и не запускает загрузку истории.

## 2. Источник сетапов — наборы из исторических запусков

Набор обычной аналитики — завершённый исторический запуск: мультиинструментный batch (`replay_batches`) или одиночный запуск (`replay_runs`) со статусом `done`. Селектор набора показывает подпись вида `#4 · Имя запуска`: номер набора и имя запуска (правка от 10 ноября 2026; ранее — `#4 - Имя алгоритма · версия`). Имя запуска по умолчанию равно имени алгоритма и редактируется в списке «Последние запуски» (см. [replay](replay.md), «Имя запуска»); алгоритм и версия остаются доступны в снимке параметров набора. Исследования оптимизации не являются такими наборами и в этот селектор не попадают.

- Сетап внутри набора идентифицируется четвёркой `exchange, category, symbol, closeTimeUnix`.
- Время сетапа — `closeTimeUnix` (окончание сигнальной минуты), цена сетапа — `closePrice` (close сигнальной свечи); см. [strategies](strategies.md).
- Свечи для моделирования сделок читаются через read API сервиса данных; отсутствие свечей не инициирует загрузку и различается с «нет торговли».

## 3. Моделирование сделки

Вход определяется до уровней и один и тот же для всех разделов:

1. `time_shift_minutes` — целое число минут ≥ 0. Цена входа = close свечи, отстоящей от сигнальной на N минут (`openTime == setupOpenTime + N×60`); при N=0 это close сигнальной свечи, то есть цена сетапа. Секундных свечей и интерполяций нет — система всегда располагает минутным рядом.
2. Нет свечи входа → статус `no_data`.
3. Горизонт сделки — параметр `horizon_minutes`, по умолчанию 10080 (7 дней). Просмотр всегда идёт по минутным свечам: каскад более широких таймфреймов, как в референсе, не нужен и не используется.
4. Уровни: SHORT `TP = entry×(1−tp/100)`, `SL = entry×(1+sl/100)`; LONG зеркально.
5. Поиск касания перебирает минутные свечи от момента входа (закрытие свечи входа, т.е. следующая свеча) до конца горизонта. Касание: SHORT — `low ≤ TP` либо `high ≥ SL`; LONG — `high ≥ TP` либо `low ≤ SL`. Если одна свеча касается обеих границ, результат — SL.
6. Исходы: `tp` (+tp_pct), `sl` (−sl_pct), `unclosed` (нет касания за горизонт), `no_data`. Время закрытия — openTime свечи касания.
7. `risk_return` строки: TP → `tp_pct/sl_pct`; SL → `−1`; `unclosed`/`no_data` → null.

## 4. Входные параметры

| Параметр | Значения | Примечание |
|---|---|---|
| `direction` | `short` / `long` | направление моделируемой сделки |
| `tp_pct`, `sl_pct` | >0, ≤100, шаг 0.01 | уровни в % от цены входа |
| `time_shift_minutes` | целое ≥ 0 | вход через N минут после сетапа |
| `horizon_minutes` | по умолчанию 10080 | горизонт поиска касаний |
| `setup_maturity` | 0.0..1.0, шаг 0.1 | зрелость сетапа в кластере; только при включённой кластеризации |
| `cluster_gap_hours` | число часов, по умолчанию 8 | максимальный разрыв между сигналами одного кластера; только при включённой кластеризации |
| `month` | «Всё время» или `YYYY-MM` | UTC-месяц времени сигнала; горизонт сделки концом месяца не обрезается; исключён при заданном диапазоне дат |
| `from_day`, `to_day` | `YYYY-MM-DD`, только вместе | произвольный диапазон UTC-дней времени сигнала (от начала from_day до конца to_day); приоритетнее месяца |
| `acceptable_price_change_pct` | null или число | гейт смещения цены, см. ниже |
| `set_id` | id набора | выбранный набор сетапов |

Гейт смещения цены сравнивает цену входа с ценой исходного сетапа: SHORT заходим только при `shifted ≥ setup_close×(1+pct/100)`, LONG — только при `shifted ≤ setup_close×(1−pct/100)`. Значение `0` для SHORT допускает равную или выросшую цену; отрицательное значение разрешает заданное снижение; положительное требует рост. Отсутствующий параметр (null) полностью отключает гейт и кешируется отдельно от числовых режимов. Непрошедшие сетапы получают статус `price_change_filtered`, кешируются как обработанные и не попадают в таблицы и агрегаты.

## 5. Кластеризация зрелости

Кластеризация воспроизводит референс: сетапы группируются по инструменту, сортируются по времени сигнала; соседние сигналы с разрывом ≤ `cluster_gap_hours` часов (по умолчанию 8) образуют один кластер. Из кластера берётся сетап, ближайший к `start + maturity×(end−start)`; при равной близости — более ранний. Месячный режим фильтрует исходные сетапы по UTC-месяцу до кластеризации.

Метрики отбора описывают выбранных представителей: средний порядковый номер в кластере (с 1) и среднее время от первого сигнала кластера до выбранного. Фильтр знает полный состав кластера, включая будущие сигналы, — это ретроспективная выборка, а не online-стратегия.

Режим без кластеризации (решение владельца от 9 ноября 2026): кластеризация не выполняется, зрелость не учитывается, в расчёте участвуют все сетапы набора после временного фильтра. Кластерные метрики (порядковый номер, задержка, число кластеров) не вычисляются и возвращаются как null. Результаты этого режима кешируются так же, как результаты с кластеризацией, — с сентинелом «нет» по зрелости и разрыву. Настройки кластеризации глобальны (v0.4): задаются один раз в карточке селектора набора и применяются одновременно ко всем разделам SHORT и LONG.

## 6. Разделы вкладки «Аналитика»

Вкладка делится на три подраздела-вкладки: **SHORT**, **LONG** и **Кеш**. В каждом торговом подразделе два одноимённых раздела: матрица **«Среднее матожидание сетапов»** и список **«Матожидание по сетапам»**.

1. **«Среднее матожидание сетапов»** (SHORT): матрица TP×SL с сеткой 4..30 с шагом 2; параметры — зрелость, месяц («Всё время»/конкретный), time-shift, порог смещения цены. Ячейка — среднее движение по закрытым сделкам `avg_move_pct` и матожидание в единицах риска `R = avg_move_pct/sl_pct`; агрегаты считаются только по закрытым TP/SL-сделкам. Перед матрицей показываются метрики кластеризации.
2. **«Матожидание по сетапам»** (SHORT): построчный список сделок по сетапам с выбранными TP/SL, зрелостью, time-shift, порогом смещения и диапазоном дат отображения. Колонки: инструмент, время сетапа, цена входа, цена TP, цена SL, время закрытия, результат (`risk_return`). Незакрытые сделки оставляют уровни/время пустыми. Рядом — win rate и матожидание в R по закрытым строкам, под ними — график дневного матожидания.
3. **«Среднее матожидание сетапов»** (LONG): LONG-матрица с асимметричной сеткой референса — строки TP `1, 2, 3, 4..30 (шаг 2), 35, 40, 45, 50, 60`, столбцы SL `0.1, 0.25, 0.5, 1, 2, 3, 4..30 (шаг 2), 35, 40, 45, 50, 60`; режим «Всё время»/месяц и time-shift; гейт смещения применяется зеркально.
4. **«Матожидание по сетапам»** (LONG): построчный список закрытий с TP/SL, time-shift и диапазоном дат отображения; колонки, агрегаты и график — как в разделе 2.

Общие правила UI: никакие расчёты не запускаются при загрузке страницы или смене параметров — матрицы и списки считаются только по нажатию кнопки «Рассчитать» (решение владельца от 9 ноября 2026). Настройки кластеризации (v0.4) вынесены в карточку селектора набора: галочка «Кластеризовать сетапы» (по умолчанию включена), ползунок «Зрелость сетапа в кластере» и поле «Разрыв кластера, ч» (по умолчанию 8, только при включённой галочке); при выключенной галочке ползунок недоступен (disabled), зрелость и разрыв не отправляются с запросом — в расчёт входят все сетапы. Настройки действуют одновременно на все разделы SHORT и LONG. Выбор времени (v0.4) во всех разделах — связка «селектор месяца + два селектора дат»: выбор месяца («Всё время»/конкретный) автоматически подставляет границы в селекторы дат (для «Всё время» — границы набора); ручное изменение даты переводит селектор месяца в прочерк «—» (произвольный диапазон дней UTC, передаётся как `fromDay`/`toDay`). Ячейка матрицы, вычисляемая в данный момент, показывает лоадер; кнопка «Рассчитать» на время расчёта заменяется на «Остановить» — остановка прекращает дальнейший досчёт, при этом уже показанные ячейки и записи серверного кеша сохраняются, а продолжение возможно только новым нажатием «Рассчитать» (правило от 9 ноября 2026). Фон ячеек матрицы не окрашивается; цвет жирного текста значения интерполируется от красного к зелёному между двумя порогами, задаваемыми ползунками «Красный при ≤» и «Зелёный при ≥» (диапазон −1..1 с шагом 0.05; дефолты SHORT 0.05/0.2, LONG 0.05/0.5, как в референсе). Опустевшие ячейки (`avg_move_pct: null`) отличаются от ошибок запроса; отменённый расчёт останавливает новые запросы логически, серверный досчёт выполняющегося запроса и запись его результата в кеш не прерываются.

Пользовательские настройки вкладки (v0.5–v0.6, решения владельца от 9 ноября 2026) хранятся в таблице `settings` платформы под ключом `web-analytics`: выбранный набор, глобальные настройки кластеризации (галочка, зрелость, разрыв в часах), признак «Авторасчёт матриц» и параметры каждого раздела/матрицы отдельно (период «месяц + даты», time-shift, галочка и порог смещения цены, TP/SL списков, пороги градиента матриц). При открытии вкладки сохранённые значения восстанавливаются как начальные. Настройки сохраняются автоматически при каждом изменении: селекты и галочки — сразу по смене значения, текстовые поля и селекторы дат — по потере фокуса, ползунки — по фиксации значения (pointerup/blur); все сохранения проходят через общий debounce 800 мс, поэтому движение ползунка не порождает потока запросов. Кнопка сохранения отсутствует; при ошибке автосохранения показывается «Не удалось сохранить настройки». Отсутствие записи или пустой объект означают значения по умолчанию.

Галочка «Авторасчёт матриц» (v0.6, по умолчанию выключена, хранится в настройках): при включении матрицы SHORT и LONG автоматически рассчитываются при входе во вкладку и после матрично-релевантных изменений настроек — выбор набора, глобальные настройки кластеризации, параметры самих матричных секций и переключение галочки (те же триггеры и debounce, что у автосохранения). Изменения параметров секций списков («Матожидание по сетапам»: TP/SL, период, time-shift, смещение цены) автосохраняются, но матрицы не пересчитывают; списки сделок автоматически не рассчитываются никогда и считаются только по кнопке «Рассчитать». При выключенной галочке матрицы тоже считаются только по кнопке. Расчёты при восстановлении настроек при входе не запускаются, если «Авторасчёт матриц» выключен.

График списка сделок — «Дневное матожидание в рисках» (как в референсе): точки по локальным дням сетапов, значение — средний `risk_return` закрытых сделок дня, линия тренда — линейная регрессия; всплывающие подсказки точки содержат день, R, число закрытых, TP/SL и долю строк из кеша. До первого расчёта и при отсутствии дней с закрытыми сделками график показывает пояснение вместо данных.

## 7. Кеш аналитики

Кеш результатов хранится в БД платформы (app DB), рядом с сетапами и настройками, — не в БД сервиса данных. Отдельные таблицы: ячейки матриц, построчные закрытия, выборки зрелости.

Ключ включает: идентификатор и отпечаток набора (число сетапов, первый/последний сигнал, последняя доступная свеча окна последнего сетапа), `direction`, зрелость (или «нет»), разрыв кластеризации в минутах (или «нет» при выключенной кластеризации; по умолчанию 8 ч = 480 мин), временной фильтр — месяц (или `all`) либо закодированный диапазон дней `d:FROM:TO`, TP, SL, горизонт, time-shift, нормализованный до миллионных долей процента порог смещения цены и версию расчётного алгоритма. Ответы содержат признак `cached`. Для матриц предусмотрен cache-only bulk-запрос готовых ячеек; недостающие ячейки досчитываются по одной. Выборка зрелости кешируется отдельно от сделок. Существующие записи кеша, посчитанные с кластеризацией, переносятся миграцией со значением разрыва 480 минут (прежняя константа 8 ч).

Догрузка истории и появление новых свечей автоматически не инвалидируют кеш — как у кеша replay; для пересчёта пользователь очищает кеш и повторяет запрос. Правки свечей внутри неизменного диапазона отпечатка не детектируются (ограничение референса сохраняется честно).

Очистка кеша аналитики — отдельная операция: сводка (число записей по таблицам) и удаление только таблиц кеша аналитики. Исходные сетапы, запуски, кеш replay, рыночные данные и настройки не затрагиваются. Выполнявшиеся до очистки расчёты могут создать новые записи после неё.

Вычислительное ядро вправе считать несколько ячеек/строк за один проход по свечам окна и заполнять кеш заранее (уточнение от 9 ноября 2026, реализуется в Rust-движке); контракт маршрутов, ответов, признак `cached` и режим «расчёт только по кнопке» от этого не меняются.

## 8. API

Все маршруты платформы требуют авторизации, как остальные `/v1`:

| Маршрут | Назначение |
|---|---|
| `GET /v1/analytics/sets` | список наборов для селектора (id, имя, алгоритм, версия, число сетапов, диапазон) |
| `GET /v1/analytics/months` | UTC-месяцы, в которых есть сетапы набора |
| `GET /v1/analytics/matrix-cells` | cache-only bulk-чтение ячеек матрицы для scope |
| `GET /v1/analytics/matrix-cell` | расчёт/чтение одной ячейки TP/SL |
| `GET /v1/analytics/trades` | cache-only bulk-чтение построчных закрытий |
| `GET /v1/analytics/trades/:symbol/:closeTimeUnix` | расчёт/чтение одной строки |
| `GET /v1/analytics/cache/summary` | сводка кеша аналитики |
| `DELETE /v1/analytics/cache` | очистка кеша аналитики |
| `GET /v1/settings/web-analytics` | сохранённые пользовательские настройки аналитики (пустой объект — нет записи) |
| `PUT /v1/settings/web-analytics` | сохранение настроек аналитики (произвольный JSON-объект) |

Месяц и направление входят в параметры, а не в путь. Параметр `clusterGapHours` (число часов, по умолчанию 8, диапазон 0.01..168) принимается всеми расчётными маршрутами; отсутствие `setupMaturity` означает режим без кластеризации, при котором разрыв не учитывается. Произвольный диапазон дат задаётся парой `fromDay`/`toDay` (`YYYY-MM-DD`, только вместе, приоритетнее `month`) и кешируется отдельно от месячных режимов. Контракт валидируется TypeBox и отражается в OpenAPI платформы.

## 9. Критерии готовности

- Расчёты воспроизводят принципы референса: в матрицах — среднее матожидание только по закрытым сделкам; в списках сетапов — закрытие по цене Take Profit или Stop Loss; спорная свеча считается SL; месячный фильтр не обрезает горизонт.
- Повторный запрос с теми же параметрами возвращает `cached: true` без пересчёта; изменение любой компоненты ключа даёт новый расчёт.
- Очистка удаляет только кеш аналитики и показывает число удалённых записей; после очистки повторный запрос считает заново.
- Отсутствие свечей (`no_data`), незакрытие за горизонт (`unclosed`) и фильтр смещения цены различаются и не смешиваются.
- Покрыто тестами: кластеризация и выбор зрелости, гейт смещения в обоих направлениях, приоритет SL при двойном касании, месячная фильтрация до кластеризации, кеш hit/miss/очистка, пустые ячейки.

## 10. Оптимизация параметров алгоритма (Plan A)

Решение владельца от 10 ноября 2026, согласовано до реализации. Это отдельное серверное исследование, запускаемое из карточки алгоритма, а не серия пользовательских replay-запусков. Направление SHORT/LONG относится к моделированию сделки; исходные события остаются нейтральными WATCH. Комиссии, funding, проскальзывание и исполнение не добавляются.

### 10.1. Фиксированный контекст и оценка

- При создании фиксируются алгоритм/версия, полный снимок текущих параметров как baseline, пользовательский historical-список инструментов (включая делистнутые), период по времени **закрытия сигнала** `[fromUnix,toUnix)`, направление, seed и бюджет поиска. Исторический список не заменяется live-листингом и не меняется вслед за редактированием настроек.
- Зрелость фиксирована для всего исследования, default 0 (первый сетап кластера), диапазон 0..1 с шагом 0.1; **никогда не является поисковой координатой**. При отключённой кластеризации зрелость и разрыв игнорируются. Горизонт фиксирован, default 10080 минут; горизонт сделки не обрезается концом периода сигналов.
- Оси TP и SL выбираются независимо, default каждой `4,6,8,10,12,14,16,18,20` процентов. Это начальная сетка, не запрет других допустимых уровней. Каждая ось содержит 1..64 уникальных конечных числовых уровней `0 < level <= 100`; произведение не больше 4096 ячеек и неизменно для всех кандидатов.
- Score — простое арифметическое среднее **сырых неокруглённых `riskExpectancy` (R)** всех выбранных ячеек с равным весом каждой ячейки, без взвешивания числом сделок, выбора лучшей ячейки или скрытого штрафа за малую выборку. Внутри ячейки действует прежняя формула по закрытым TP/SL: `R = avgMovePct / slPct`.
- Необязательный `minClosedPerCell` — положительное целое, default 1. Если хотя бы в одной выбранной ячейке закрытых сделок меньше порога или R не определён, **весь кандидат неоценим**, `score: null`; пустые ячейки нельзя удалять из знаменателя. Числа закрытых, TP/SL, no_data, unclosed и отфильтрованных сделок показываются явно, малые выборки не скрываются.
- Решение владельца от 11 ноября 2026: необязательный фиксированный `minSetupsPerDay` — конечное неотрицательное число, default 4; это **не поисковая координата**. Числитель — суммарный по выбранным инструментам `selectedSetupCount`: сетапы кандидата после детектора, фильтра времени закрытия `[fromUnix,toUnix)` и кластеризации/отбора зрелости, но **до** определения входа, `no_data`, гейта смещения цены и исходов TP/SL. Без кластеризации это все сетапы выбранного периода. Знаменатель — вся точная длительность выбранного периода сигналов, включая дробные дни и интервалы без сигналов/свечей, а не число торговых дней и не промежуток между первым и последним сетапом: `durationSeconds = toUnix - fromUnix`, `avgSetupsPerDay = selectedSetupCount × 86400 / durationSeconds`.
- Частотный допуск проверяется без округления среднего и без epsilon: **`selectedSetupCount × 86400 >= minSetupsPerDay × durationSeconds`**. Для сравнения порог берётся из кратчайшей десятичной записи нормализованного числового `minSetupsPerDay` в `spec`; десятичные множители сравниваются точно, без промежуточного binary-float произведения/деления. Равенство допускается: 6 выбранных сетапов за 10 дней дают 0.6/сутки, поэтому default 4 отклоняет кандидата, а порог 0.6 допускает. При нарушении частотного допуска `score: null` независимо от величины R. Значение 0 отключает только частотный допуск; `minClosedPerCell` и определённость всех ячеек остаются обязательными. Вес ячеек и формула целевой функции не меняются.
- Эквивалентный целочисленный минимум — `requiredSetupCount = ceil(minSetupsPerDay × durationSeconds / 86400)`, с тем же точным десятичным вычислением. Например, для диапазона 864060 секунд и порога 4 требуется 41 выбранный сетап; 6 сетапов дают примерно 0.599958/сутки и не проходят допуск. Порог не округляет длительность до целых дней.
- Совместимость: default 4 применяется к **новым** исследованиям, включая новый POST без поля; новая форма явно отправляет 4, а явный 0 отключает допуск. У ранее сохранённого исследования, чей исходный `spec` не содержит `minSetupsPerDay`, частотный допуск не применялся. Такой JSON/result не переписывается, не пересчитывается и не объявляется прошедшим новый порог. UI показывает отсутствие исторического допуска как legacy/«не применялся», не подставляя 4 при просмотре старой записи; отсутствие новых support-метрик означает «не сохранено», не 0. Serde-default нового вычислительного запроса не является основанием менять смысл старого персистентного результата.

### 10.2. Поиск и применимость

Plan A реализуется нативно в Rust: начальное покрывающее исследование пространства (space-filling), чувствительность параметров в нескольких контекстах, несколько стартовых точек и уточнение от крупного к мелкому шагу (multistart coarse-to-fine), одиночные, парные и совместные мутации с продолжающимся глобальным исследованием. Чувствительность в одной точке не считается основанием навсегда исключить параметр. Результат — лучший полностью проверенный кандидат в пределах бюджета, **не доказанный глобальный оптимум**.

Все домены конечны и зафиксированы пользователем до старта. UI строит параметры по метаданным выбранного модуля; числовые границы допустимости не подменяют разумные поисковые диапазоны. Текущая конфигурация служит baseline; параметры качества данных по умолчанию фиксированы, но доступны для осознанного включения в подбор. Составные ограничения проверяются общей валидацией модуля. Исследование не меняет текущую конфигурацию. Полный baseline алгоритма и аналитики обязательно оценивается как trial 0, даже если его значения не входят в поисковые массивы, и входит в общий бюджет. Поисковая структура алгоритма — generic map реальных field keys, не hardcoded AlgorithmSpace с переименованными координатами.

В аналитике варьируются кластеризация (bool), разрыв кластера, time-shift и гейт цены (отключён или числовой порог). Неактивные координаты канонизируются: без кластеризации нет измерений зрелости/разрыва; без гейта нет порога. Отключённый гейт отличается от порога 0. Разрыв приводится к минутам, эквивалентные значения не создают отдельные кандидаты. Неприменимые поля другого алгоритма, зрелость и `minSetupsPerDay` как поисковые поля отклоняются. Фиксированные параметры, включая направление, период, горизонт, оси и частотный порог, не мутируют.

Seed, версия оптимизатора, стабильный порядок кандидатов и детерминированные пакеты оценки обеспечивают повторимость при одинаковых входных данных и бюджете завершённых оценок; скорость параллельных задач не задаёт порядок обновления поиска. Ограничение по реальному времени и ручная остановка могут дать разное число законченных пакетов. Равные score разрешаются стабильным порядком, а не порядком завершения потоков.

### 10.3. Данные и изоляция

Перед сравнением кандидатов фиксируются фактически прочитанные свечи **и пропуски** для всех инструментов: максимальный прогрев по доменам, период сигналов, максимальный time-shift и фиксированный горизонт сделок. Все оценки используют один неизменный снимок; новые свечи/догрузки во время поиска его не меняют. Сетевой сбой, неверный ответ или незавершённая пагинация чтения являются ошибкой исследования, а не отсутствующими свечами или нулём сигналов. Чтение не запускает backfill.

Общий расширенный снимок не меняет семантику детектора: каждый кандидат получает собственное начало прогрева и начальное состояние cooldown, идентичные отдельному свежему replay с его параметрами. Сигналы фильтруются по `[fromUnix,toUnix)` **до** кластеризации; метрики не включают сигналы общего максимального прогрева.

В app DB отдельно сохраняются метаданные исследования, статус, прогресс, ограниченный список крупных событий/выводов и компактный итог. Запрещено создавать обычные `replay_runs`/`replay_batches` и читать/заполнять общие replay/analytics-кеши ради исследования. Первая реализация держит raw-снимок и промежуточные данные только в RAM исследования с явным настраиваемым byte cap; превышение лимита — явная ошибка, не усечение входов. Ограниченный приватный временный каталог допускается как последующее расширение, но не является критерием приёмки первой версии. Нет постоянного архива trials и memoization результатов между исследованиями; из результатов кандидатов сохраняется только победитель, не коллекция матриц. Завершение, отмена, ошибка и startup-cleanup освобождают временные данные.

Сохраняемый победитель содержит полный набор параметров, фиксированный входной scope, матрицу и счётчики, seed/версию поиска, происхождение/хеши реально использованных данных и ограниченные главные выводы. Во время работы персистентны только progress.bestScore и ограниченные события вместе с метаданными/статусом; полный лучший кандидат удерживается в RAM до завершения, затем сохраняется в result. Промежуточные incumbent-снимки в БД запрещены. В победителя допускаются только полностью законченные оценки всех выбранных ячеек/инструментов. При остановке сохраняется лучший завершённый результат с явной пометкой частичности; при отсутствии оценимых кандидатов победитель отсутствует. При аварийной потере процесса RAM-победитель теряется, по одному bestScore он не восстанавливается. Raw-снимок удаляется: хеши позволяют обнаружить несовпадение входов при повторе, но **не гарантируют точное воспроизведение позже**. Автоприменения в live или пользовательские настройки нет.

### 10.4. Серверный жизненный цикл и API

Владелец работы — сервер, не браузерный цикл запросов. Состояния: `queued`, `running`, `cancel_requested`, `completed`, `cancelled`, `failed`. Создание возвращает 202 после персистентной регистрации; разрыв HTTP, закрытие диалога/страницы или обновление браузера не отменяют работу. UI после загрузки обнаруживает исследования через список и восстанавливает отображение через GET деталей; polling только наблюдает. На первом этапе во всей платформе разрешено одно активное исследование (`queued/running/cancel_requested`).

Явная отмена кооперативна: прекратить допуск новых вычислений, остановить/дождаться текущих задач, сохранить только полностью проверенный incumbent, очистить временные данные, затем `cancelled`. Повторная отмена идемпотентна; терминальный статус не переписывается. При рестарте серверного процесса прерванное незавершённое исследование получает `failed` с причиной `interrupted_by_restart`, сиротские временные каталоги очищаются. Автоматическое возобновление вычислений после падения сервера **не обещается**; восстановление UI после reload обязательно.

| Маршрут | Контракт |
|---|---|
| `GET /v1/algorithms` | Существующие поля + аддитивные hints оптимизации по разделу strategies; отдельный `/optimization-options` не нужен |
| `POST /v1/optimization-studies` | Создать исследование, 202 с записью исследования напрямую; не синхронный расчёт |
| `GET /v1/optimization-studies?algorithmId=&limit=&offset=` | Постраничный `{studies:[summaries],total,limit,offset}`; default limit 20, максимум 100; активное исследование первым, затем новые; фильтр algorithmId необязателен. Summary содержит spec/progress/status и итоговый `bestScore`, но не тяжёлые matrix/events; полная запись читается отдельным GET |
| `GET /v1/optimization-studies/{id}` | Запись исследования напрямую: spec, progress, result, error и метаданные |
| `POST /v1/optimization-studies/{id}/cancel` | Запись исследования напрямую: 202 для принятой отмены, 200 для уже терминального состояния |
| `DELETE /v1/optimization-studies/{id}` | Удалить только терминальное исследование (`completed/cancelled/failed`); 200 `{deleted:true,id}`, активное — 409, неизвестное — 404 |

Применяются существующие авторизация и browser mutation guards. Некорректный домен/составные параметры — 400; неизвестное исследование — 404; активное исследование или сменившаяся версия алгоритма — 409 (ответ busy содержит activeStudyId); превышение ресурсного допуска — 429 с ресурсом/лимитом. Список и детали не запускают вычисления.

Решение владельца от 11 ноября 2026: в карточке каждого алгоритма под кнопками управления показывается постраничная таблица всей истории его исследований. Колонки: ID, диапазон закрытия сигналов `[fromUnix,toUnix)`, фиксированный `minSetupsPerDay` (для legacy-записи без поля — «гейт не применялся»), итоговый лучший score в R и «Действия». ID открывает ту же подробную модалку результата, что и прежняя кнопка «Статус / результат оптимизации», с загрузкой полной записи по ID. Для `queued/running` доступна остановка; `cancel_requested` показывает принятый запрос без повторной команды. Для терминальных исследований доступна корзина с подтверждением удаления. Удаление затрагивает только строку исследования и сохранённый компактный результат, не raw-снимок (он уже освобождён), обычные прогоны, analytics/replay-кеши, настройки или market-data. После остановки/удаления таблица и глобальный active-state обновляются без reload страницы.

```json
  "algorithmSearch": {"priceGrowthPct":["8","12","16"],"windowMinutes":[3,5,10]},
  "analyticsParams": {"clusterEnabled":true,"clusterGapMinutes":480,"timeShiftMinutes":0,"priceChangePct":null},
  "analyticsSearch": {"clusterEnabled":[false,true],"clusterGapMinutes":[240,480],"timeShiftMinutes":[0,5],"priceChangePct":[null,0,1]},
  "seed": 42,
  "maxTrials": 256,
  "maxSeconds": 3600
}
```

`algorithmParams` и `analyticsParams` — полные baseline-объекты. `algorithmSearch` и `analyticsSearch` — maps непустых конечных массивов; UI может принимать min/max/step, но разворачивает bounded диапазоны в значения перед отправкой. Отсутствующие в search поля фиксированы в соответствующем baseline; неизвестные ключи запрещены. Decimal-поля алгоритма сохраняют строковый тип; analytics использует bool/integer/number/null. `clusterGapMinutes` — целое 1..10080, `timeShiftMinutes` — целое 0..43200, `priceChangePct` — null либо конечное число −100..1000. UI может показывать разрыв в часах, wire всегда в минутах. Начальные значения формы analytics: true/480/0/null; maturity и horizon находятся только в фиксированном scope, не в search. Плоские поля бюджета: `maxTrials` — 1..4096 (default 256) полных совместных trials, `maxSeconds` — 1..86400 (default 3600); baseline trial 0 учитывается. Размеры доменов/запроса ограничиваются ресурсным допуском. Сервер возвращает нормализованный полный request, включая применённые defaults и фактический бюджет; бюджет не повышается скрыто.

Запись API имеет точную форму `{id,status,spec,progress,result,error,createdAt,updatedAt,events}`, id — целое число. `spec` — нормализованный полный `StudyRequest` в camelCase по примеру выше, включая algorithmId, scope, baseline и поисковые домены; дублирующего поля request нет. `progress` — текущий снимок `{phase,evaluatedCandidates,scorableCandidates,maxTrials,elapsedSeconds,bestScore}`; `bestScore` всегда присутствует, null до первого оценимого кандидата. Подготовка входов обозначается `progress.phase = acquiring`, не отдельным lifecycle-статусом. Дальнейшие фазы различают начальное исследование, чувствительность, уточнение и очистку. Статусы записи остаются `queued/running/cancel_requested/completed/cancelled/failed`.

`result` — null во время работы, после завершения null либо `StudyOutcome` формы `{progress,best,reason}`. `reason` принимает `trial_budget`, `time_budget`, `space_exhausted`, `cancelled`; ошибка исследования выражается через status/error, не вымышленной причиной успешного завершения. `error` — null либо `{code,message}` без секретов. `best` — null, если оценимого победителя нет, либо `{score,partial,params,analytics,matrix,provenance,conclusions}`. `params` содержит полный алгоритмический набор; `analytics` — эффективные clusterEnabled/clusterGapMinutes/timeShiftMinutes/priceChangePct (неактивный разрыв null); фиксированные maturity/horizon берутся из `spec`, maturity не применяется при clusterEnabled=false. При `best: null` UI явно объясняет отсутствие кандидата, удовлетворившего одновременно частотному допуску `minSetupsPerDay` и требованиям всех ячеек/`minClosedPerCell`; нулевой score не подставляется. Незавершённый trial не публикуется как результат; после аварийной потери RAM result остаётся null.

`matrix` содержит все выбранные `{tpPct,slPct,riskExpectancy,avgMovePct,closedCount,tpCount,slCount,unclosedCount,noDataCount,priceChangeFilteredCount}`. `provenance` содержит `{optimizerVersion,seed,snapshotHash,capturedAt}`; точный scope и домены находятся в `spec`. `partial` true для частичного итога отмены, false только при штатном завершении выбранного бюджета/поиска; даже false не означает доказанный глобальный оптимум. `events` — ограниченные крупные события `{at,kind,message}`, без payload промежуточных кандидатов или архива trials; `conclusions` победителя ограничены по числу и размеру. Baseline score/counts для сравнения допустимы как компактная сводка, не вторая сохранённая матрица кандидата. `TrialSummary` в `result.baseline` и `result.best.support` дополнительно содержит фактический `avgSetupsPerDay` и целочисленный `requiredSetupCount`; для нового завершённого кандидата среднее всегда число. Для старого сохранённого результата без этих метрик допускается null; `requiredSetupCount` также null, если конечный порог требует числа сетапов за пределами представимого целого счётчика — такой кандидат не проходит допуск. Показанное среднее не используется вместо точного сравнения допуска. В выводах победителя кратко указываются отобранное число, фактическая частота и требуемый минимум. История отдельных trials не добавляется. При `best: null` пояснение UI учитывает также невыполнение `minSetupsPerDay`, а не только требования ячеек.

### 10.5. Приёмка

- При закрытом браузере сервер продвигает работу; после reload UI обнаруживает то же исследование и его результат без повторного POST. Закрытие модалки не равно Stop.
- Explicit Stop, ошибка чтения и рестарт сервера дают честный терминальный статус; временные данные освобождены, незавершённый trial не становится победителем.
- Score проверен на неравных числах сделок по ячейкам: равные веса ячеек, отсутствие округления до усреднения, вся матрица неоценима при одной пустой ячейке/нарушенном minClosedPerCell.
- Частотный допуск проверен на 6 выбранных сетапах за 10 дней (неоценимы при default 4), равенстве порогу, дробной длительности периода и отключении порогом 0. Используется именно число после кластеризации/зрелости и до гейта цены/`no_data`; высокий R не обходит допуск, а отключение частотного порога не отменяет `minClosedPerCell`.
- Все кандидаты используют одинаковый frozen input; сравнение со свежим replay подтверждает прогрев/cooldown и close-time границы, включая разные длины прогрева и пропуски.
- Кластеризация off и гейт off не порождают дубликаты из неактивных координат; maturity не изменяется поиском. Оба зарегистрированных алгоритма работают через metadata, без отдельных форм.
- До/после исследования списки обычных запусков и общие кеши не меняются; настройки live/аналитики не изменены. Финальный snapshot переживает reload, raw/trials не переживают завершение.
