## 1. Назначение и границы

Аналитика выполняет ретроспективный backtest накопленных наборов сетапов: моделирует TP/SL-сделки от каждого сетапа, считает матожидание в матрицах TP×SL и построчные закрытия. Это диагностический инструмент, а не торговый симулятор: комиссии, funding, проскальзывание, размер позиции и реальное исполнение ордеров не моделируются.

Вне границ: автоматическая торговля на бирже и полноценные прогнозы доходности/PnL. Последующим решением владельца от 17 ноября 2026 утверждён общий gross-прогноз по вероятности закрытого TP/SL для ручной «Аналитики», ручных/непрерывных исследований и Telegram (§6.2): это расширяет первоначальный Telegram-only срез §11.5.1 и намеренно меняет метрику новых forecast/blend-рецептов, но не старые результаты. Предусмотрена ограниченная хронологическая проверка predictor и отдельно всей процедуры выбора, без обещания доказанного преимущества или разрешения новой production-кампании/сбора факторов. Текущая фаза — PRD, commit и уведомление владельца до кода. Ручная оптимизация параметров отдельно разрешена решением от 10 ноября по разделу 10 и изолирована от обычных наборов и кешей. Непрерывная цепочка replay/аналитики и применение рекомендаций описаны в разделе 11; это не разрешение выставлять ордера. Аналитика ничего не пишет в сервис данных и не запускает загрузку истории.

## 2. Источник сетапов — наборы из исторических запусков

Набор обычной аналитики — завершённый исторический запуск: мультиинструментный batch (`replay_batches`) или одиночный запуск (`replay_runs`) со статусом `done`. Селектор набора показывает подпись вида `#4 · Имя запуска`: номер набора и имя запуска (правка от 10 ноября 2026; ранее — `#4 - Имя алгоритма · версия`). Имя запуска по умолчанию равно имени алгоритма и редактируется в списке «Последние запуски» (см. [replay](replay.md), «Имя запуска»); алгоритм и версия остаются доступны в снимке параметров набора. Исследования оптимизации не являются такими наборами и в этот селектор не попадают.

В этапе 2 завершённый служебный replay непрерывного исследования создаёт отдельный сохраняемый набор с явной меткой continuous/«служебный» и ссылкой на исследование. Само исследование набором не становится. Происхождение и принадлежность набора не определяются его редактируемым именем.

- Сетап внутри набора идентифицируется четвёркой `exchange, category, symbol, closeTimeUnix`.
- Время сетапа — `closeTimeUnix` (окончание сигнальной минуты), цена сетапа — `closePrice` (close сигнальной свечи); см. [strategies](strategies.md).
- Свечи для моделирования сделок читаются через read API сервиса данных; отсутствие свечей не инициирует загрузку и различается с «нет торговли».

## 3. Моделирование сделки

Вход определяется до уровней и один и тот же для всех разделов:

1. `time_shift_minutes` — целое число минут ≥ 0. Цена входа = close свечи, отстоящей от сигнальной на N минут (`openTime == setupOpenTime + N×60`); при N=0 это close сигнальной свечи, то есть цена сетапа. Секундных свечей и интерполяций нет — система всегда располагает минутным рядом.
2. Нет свечи входа → статус `no_data`.
3. Горизонт сделки — параметр `horizon_minutes`, по умолчанию 10080 (7 дней). Просмотр всегда идёт по минутным свечам: каскад более широких таймфреймов, как в референсе, не нужен и не используется.
4. Уровни: SHORT `TP = entry×(1−tp/100)`, `SL = entry×(1+sl/100)`; LONG зеркально.
5. Поиск касания перебирает минутные свечи от момента входа (закрытие свечи входа, т.е. следующая свеча) до конца горизонта. Касание: SHORT — `low ≤ TP` либо `high ≥ SL`; LONG — `high ≥ TP` либо `low ≤ SL`. Если одна свеча касается обеих границ, результат — SL.
6. Исходы: `tp` (+tp_pct), `sl` (−sl_pct), `unclosed` (нет касания за горизонт), `no_data`. Время закрытия — openTime свечи касания.
7. `risk_return` строки: TP → `tp_pct/sl_pct`; SL → `−1`; `unclosed`/`no_data` → null.

## 4. Входные параметры

| Параметр | Значения | Примечание |
|---|---|---|
| `direction` | `short` / `long` | направление моделируемой сделки |
| `tp_pct`, `sl_pct` | >0, ≤100, шаг 0.01 | уровни в % от цены входа |
| `time_shift_minutes` | целое ≥ 0 | вход через N минут после сетапа |
| `horizon_minutes` | по умолчанию 10080 | горизонт поиска касаний |
| `setup_maturity` | 0.0..1.0, шаг 0.1 | зрелость сетапа в кластере; только при включённой кластеризации |
| `cluster_gap_hours` | число часов, по умолчанию 8 | максимальный разрыв между сигналами одного кластера; только при включённой кластеризации |
| `month` | «Всё время» или `YYYY-MM` | UTC-месяц времени сигнала; горизонт сделки концом месяца не обрезается; исключён при заданном диапазоне дат |
| `from_day`, `to_day` | `YYYY-MM-DD`, только вместе | произвольный диапазон UTC-дней времени сигнала (от начала from_day до конца to_day); приоритетнее месяца |
| `acceptable_price_change_pct` | null или число | гейт смещения цены, см. ниже |
| `set_id` | id набора | выбранный набор сетапов |

Гейт смещения цены сравнивает цену входа с ценой исходного сетапа: SHORT заходим только при `shifted ≥ setup_close×(1+pct/100)`, LONG — только при `shifted ≤ setup_close×(1−pct/100)`. Значение `0` для SHORT допускает равную или выросшую цену; отрицательное значение разрешает заданное снижение; положительное требует рост. Отсутствующий параметр (null) полностью отключает гейт и кешируется отдельно от числовых режимов. Непрошедшие сетапы получают статус `price_change_filtered`, кешируются как обработанные и не попадают в таблицы и агрегаты.

## 5. Кластеризация зрелости

Кластеризация воспроизводит референс: сетапы группируются по инструменту, сортируются по времени сигнала; соседние сигналы с разрывом ≤ `cluster_gap_hours` часов (по умолчанию 8) образуют один кластер. Из кластера берётся сетап, ближайший к `start + maturity×(end−start)`; при равной близости — более ранний. Месячный режим фильтрует исходные сетапы по UTC-месяцу до кластеризации.

Метрики отбора описывают выбранных представителей: средний порядковый номер в кластере (с 1) и среднее время от первого сигнала кластера до выбранного. Фильтр знает полный состав кластера, включая будущие сигналы, — это ретроспективная выборка, а не online-стратегия.

Произвольная зрелость сохраняется для ручной ретроспективной аналитики. В непрерывном режиме раздела 11 при включённой кластеризации зрелость всегда 0 и недоступна для редактирования: выбирается первый raw-сигнал кластера с причинной инициализацией состояния. Старые ручные расчёты, настройки и результаты автоматически под этот режим не переводятся.

Режим без кластеризации (решение владельца от 9 ноября 2026): кластеризация не выполняется, зрелость не учитывается, в расчёте участвуют все сетапы набора после временного фильтра. Кластерные метрики (порядковый номер, задержка, число кластеров) не вычисляются и возвращаются как null. Результаты этого режима кешируются так же, как результаты с кластеризацией, — с сентинелом «нет» по зрелости и разрыву. Настройки кластеризации глобальны (v0.4): задаются один раз в карточке селектора набора и применяются одновременно ко всем разделам SHORT и LONG.

## 6. Разделы вкладки «Аналитика»

Правила этой вкладки, её ручного расчёта и пользовательского авторасчёта не управляют серверной служебной цепочкой continuous из раздела 11.

Вкладка делится на три подраздела: **SHORT**, **LONG** и **Кеш**. С 12 ноября 2026 они выбираются общим правым сайдбаром страницы; на узком экране список выбора расположен перед содержимым. Панели остаются смонтированными и скрываются через `hidden`, поэтому настройки, результаты и начатые расчёты сохраняются. Вложенные декоративные Card-обёртки заменяются смысловыми секциями на одной основной поверхности; правила расчётов и автосохранения не меняются. В каждом торговом подразделе два одноимённых раздела: матрица **«Среднее матожидание сетапов»** и список **«Матожидание по сетапам»**.

1. **«Среднее матожидание сетапов»** (SHORT): матрица TP×SL с сеткой 4..30 с шагом 2; параметры — зрелость, месяц («Всё время»/конкретный), time-shift, порог смещения цены. Ячейка — среднее движение по закрытым сделкам `avg_move_pct` и матожидание в единицах риска `R = avg_move_pct/sl_pct`; агрегаты считаются только по закрытым TP/SL-сделкам. Перед матрицей показываются метрики кластеризации.
2. **«Матожидание по сетапам»** (SHORT): построчный список сделок по сетапам с выбранными TP/SL, зрелостью, time-shift, порогом смещения и диапазоном дат отображения. Колонки: инструмент, время сетапа, цена входа, цена TP, цена SL, время закрытия, результат (`risk_return`). Незакрытые сделки оставляют уровни/время пустыми. Рядом — win rate и матожидание в R по закрытым строкам, под ними — график дневного матожидания.
3. **«Среднее матожидание сетапов»** (LONG): LONG-матрица с асимметричной сеткой референса — строки TP `1, 2, 3, 4..30 (шаг 2), 35, 40, 45, 50, 60`, столбцы SL `0.1, 0.25, 0.5, 1, 2, 3, 4..30 (шаг 2), 35, 40, 45, 50, 60`; режим «Всё время»/месяц и time-shift; гейт смещения применяется зеркально.
4. **«Матожидание по сетапам»** (LONG): построчный список закрытий с TP/SL, time-shift и диапазоном дат отображения; колонки, агрегаты и график — как в разделе 2.

Общие правила UI: никакие расчёты не запускаются при загрузке страницы или смене параметров — матрицы и списки считаются только по нажатию кнопки «Рассчитать» (решение владельца от 9 ноября 2026). Настройки кластеризации (v0.4) вынесены в карточку селектора набора: галочка «Кластеризовать сетапы» (по умолчанию включена), ползунок «Зрелость сетапа в кластере» и поле «Разрыв кластера, ч» (по умолчанию 8, только при включённой галочке); при выключенной галочке ползунок недоступен (disabled), зрелость и разрыв не отправляются с запросом — в расчёт входят все сетапы. Настройки действуют одновременно на все разделы SHORT и LONG. Выбор времени (v0.4) во всех разделах — связка «селектор месяца + два селектора дат»: выбор месяца («Всё время»/конкретный) автоматически подставляет границы в селекторы дат (для «Всё время» — границы набора); ручное изменение даты переводит селектор месяца в прочерк «—» (произвольный диапазон дней UTC, передаётся как `fromDay`/`toDay`). Ячейка матрицы, вычисляемая в данный момент, показывает лоадер; кнопка «Рассчитать» на время расчёта заменяется на «Остановить» — остановка прекращает дальнейший досчёт, при этом уже показанные ячейки и записи серверного кеша сохраняются, а продолжение возможно только новым нажатием «Рассчитать» (правило от 9 ноября 2026). Фон ячеек матрицы не окрашивается; цвет жирного текста значения интерполируется от красного к зелёному между двумя порогами, задаваемыми ползунками «Красный при ≤» и «Зелёный при ≥» (диапазон −1..1 с шагом 0.05; дефолты SHORT 0.05/0.2, LONG 0.05/0.5, как в референсе). Опустевшие ячейки (`avg_move_pct: null`) отличаются от ошибок запроса; отменённый расчёт останавливает новые запросы логически, серверный досчёт выполняющегося запроса и запись его результата в кеш не прерываются.

Пользовательские настройки вкладки (v0.5–v0.6, решения владельца от 9 ноября 2026) хранятся в таблице `settings` платформы под ключом `web-analytics`: выбранный набор, глобальные настройки кластеризации (галочка, зрелость, разрыв в часах), признак «Авторасчёт матриц» и параметры каждого раздела/матрицы отдельно (период «месяц + даты», time-shift, галочка и порог смещения цены, TP/SL списков, пороги градиента матриц). При открытии вкладки сохранённые значения восстанавливаются как начальные. Настройки сохраняются автоматически при каждом изменении: селекты и галочки — сразу по смене значения, текстовые поля и селекторы дат — по потере фокуса, ползунки — по фиксации значения (pointerup/blur); все сохранения проходят через общий debounce 800 мс, поэтому движение ползунка не порождает потока запросов. Кнопка сохранения отсутствует; при ошибке автосохранения показывается «Не удалось сохранить настройки». Отсутствие записи или пустой объект означают значения по умолчанию.

Галочка «Авторасчёт матриц» (v0.6, по умолчанию выключена, хранится в настройках): при включении матрицы SHORT и LONG автоматически рассчитываются при входе во вкладку и после матрично-релевантных изменений настроек — выбор набора, глобальные настройки кластеризации, параметры самих матричных секций и переключение галочки (те же триггеры и debounce, что у автосохранения). Изменения параметров секций списков («Матожидание по сетапам»: TP/SL, период, time-shift, смещение цены) автосохраняются, но матрицы не пересчитывают; списки сделок автоматически не рассчитываются никогда и считаются только по кнопке «Рассчитать». При выключенной галочке матрицы тоже считаются только по кнопке. Расчёты при восстановлении настроек при входе не запускаются, если «Авторасчёт матриц» выключен.

График списка сделок — «Дневное матожидание в рисках»: точки по **UTC-дням исходных сигналов**, значение — средний `risk_return` закрытых сделок дня, линия тренда — линейная регрессия по прошедшим календарным UTC-суткам, а не индексам присутствующих дней. Всплывающие подсказки точки содержат UTC-день, R, число закрытых, TP/SL и долю строк из кеша. До первого расчёта и при отсутствии дней с закрытыми сделками график показывает пояснение вместо данных.

Уточнение владельца от 16 ноября 2026: слева у нулевой линии явно подписывается `0 R`, нижняя ось — «Дата сетапа (UTC)». Заголовок содержит «Среднее МО» за рассчитанный период: среднее по закрытым сделкам выбранной TP/SL-пары, а не невзвешенное среднее дневных точек или среднее матрицы. Значение положительного среднего зелёное, отрицательного красное, нулевого нейтральное; знак определяется до округления. Это изменение представления, без изменения UTC-группировки, OLS, фильтра периода или расчётных результатов.

**Подтверждённое изменение от 15 ноября 2026.** Ранее UI группировал по browser/user-local дням и считал регрессию по индексам присутствующих дневных buckets, сжимая отсутствующие даты. Владелец явно согласовал замену этой оси на календарную UTC **одновременно в «Аналитике», графике рекомендации, динамике и прогнозе МО**. Это намеренно может изменить дневные средние из-за timezone и fit из-за расстояний между датами, а не скрытая попытка сохранить прежние числа. Пропущенные/null-дни не превращаются в нулевые исходы и не участвуют в OLS; конечные дневные средние имеют равный вес независимо от числа сделок. Числа исходных исследований/матриц и старые рекомендации не переписываются. Точный версионированный контракт — §11.5.1.

### 6.1. Сглаженный тренд и оценка текущего уровня (N3+N4, 16 ноября 2026)

**Граница версий.** Раздел описывает прежний метод `trend`, сохраняемый для сравнения и совместимости истории. После одобренного обобщения от 17 ноября §6.2 имеет приоритет для новых рецептов во всех четырёх сценариях: probability становится основным forecast-методом, не меняя default режима `mean`. Прежние P-spline/`rowCount`-веса не подменяют новую модель. Старые расчёты по настоящему разделу и §10.1.1–10.1.2 не переинтерпретируются.

Решение владельца: в ручной «Аналитике» под блоком «Кластеризация», после разделителя, добавляются общие для SHORT/LONG настройки **«Перегиб на N дней»** (`trendBendDays`: `7`, `14`, `30` или `linear` — «∞ — прямая», default `linear`) и **«Среднее | Прогноз по тренду»** (`trendMode`: `mean|forecast`, default `mean`). Они сохраняются вместе с пользовательскими настройками и участвуют в прежнем debounce/авторасчёте матриц. Списки сделок автоматически не пересчитываются. Настройки не меняют отбор, TP/SL-исходы или среднее закрытых сделок.

Дневные точки по-прежнему используют календарные UTC-дни исходных сигналов и среднее R закрытых TP/SL-сделок дня. Вес конечной точки — число рассчитанных сетапов её дня (включая строки без закрытого исхода, но без `price_change_filtered`, как в списке сделок), а не равный вес дней. Null-день и день с нулевым весом не являются точками `y=0`. Это явное изменение ручного тренда относительно прежнего равновесного OLS; неизменяемые continuous-артефакты и исторические PNG §11.5.1 не переписываются. Опциональное использование этого метода как objective/gate **новых** исследований определено отдельно в §10.1.1 (N6).

Для конечного N строится взвешенный кубический P-spline: B-spline basis с узлами через N календарных суток от первой конечной даты, зажатыми границами и штрафом вторых разностей коэффициентов. В v1 фиксированный лёгкий штраф `λ=0.1` применяется после нормировки весов к среднему весу 1; автоматический GCV и выбор λ отложены. Система решается ленточным разложением Холецкого без новых зависимостей. Для менее четырёх пригодных дней либо численно вырожденной системы используется взвешенная линейная регрессия; `linear` всегда означает именно её. Требуются хотя бы две различные конечные даты, иначе тренд/прогноз недоступны. Счётчики и память ограничены 3661 дневной точкой, 3660 сутками и ограниченным числом точек отрисовки; данные принадлежат одному расчёту и освобождаются после него.

**Прогноз — оценка текущего уровня**, строго fitted-значение на **последней конечной дате** ряда: `f(x_last)`. Это не будущая экстраполяция, не значение за концом периода/на текущих часах и не гарантия доходности. В режиме `forecast` именно это значение возвращается как `riskExpectancy` ячейки; `meanRiskExpectancy` отдельно сохраняет прежнее среднее. При нехватке дней значение прогноза — null, даже если среднее определено. В режиме `mean` арифметика и payload сохраняемого результата прежние.

График поверх дневных точек рисует fitted-кривую только между первой и последней пригодными датами и полупрозрачную **95% полосу `f(x) ± 1.96·SE(x)`**. Это приближённая, условная при фиксированных узлах/λ точечная неопределённость сглаженного среднего, не prediction interval отдельной сделки и не одновременная гарантия покрытия всей кривой. Остаточная взвешенная дисперсия оценивается по числу пригодных дней минус effective degrees of freedom; SE — из ковариации линейного сглаживателя `σ² A⁻¹(BᵀWB)A⁻¹`. При отсутствии остаточных степеней свободы SE и полоса недоступны, а не равны вымышленному нулю. `endpointSe` доступен в API прогноза/матрицы; обе fitted-концевые подписи и границы полосы входят в масштаб графика. Чистый авторизованный `POST /v1/analytics/trend` принимает ограниченный дневной ряд и `trendBendDays`, возвращает ту же кривую/SE без БД или рыночных чтений; браузер не реализует отдельный численный solver.

**Аддитивный контракт кеша.** `trendMode` и `trendBendDays` входят в логическую идентичность вычисления матрицы. Канонический `mean` не зависит от настройки тренда и использует **побайтово прежний** ключ/payload/algorithm version: старые mean-записи остаются hits без миграции и очистки. Только `forecast` добавляет к прежнему matrix scope суффикс `:trend:v1:forecast:<7|14|30|linear>`; разные шаги не сталкиваются между собой или с mean. Индивидуальные исходы сделок и выборка кластеров от этих параметров не зависят, их ключи не изменяются. Изменение метода/λ требует новой версии суффикса, а не переопределения старых записей.

### 6.2. Общий прогноз для аналитики, исследований и Telegram (обобщение от 17 ноября 2026)

**Приоритет и область действия.** Владелец одобрил единый численный модуль для матриц/кривых ручной «Аналитики», ручной оптимизации, continuous и Telegram. Это последующее расширение первоначального Telegram-only решения §11.5.1: прежний запрет менять objective относился к тому срезу, а **новые** versioned forecast/blend-рецепты намеренно могут изменить score, ranking, robust TP/SL-пару и результат допуска. Формулы mode-specific gate не меняются. Старые исследования, рекомендации, checkpoints, PNG и delivery bytes остаются неизменными; нет автоматического пересчёта/конвертации/resend. Текущий этап заканчивается обновлением PRD, commit и уведомлением владельца **до правок исходников**; развёртывание остаётся отдельным действием.

**Режим и метод — разные настройки.** Сохраняются `mean|forecast|blend`, default режима **`mean`**. Для новых явно версионированных рецептов основной `forecast.method` — `decayed_probability`; `trend` остаётся явно названным прежним методом сравнения/исторической совместимости по §6.1. Отсутствие method в старом сохранённом forecast/blend означает legacy trend, не probability. Выбор нового default метода не включает forecast вместо mean, не меняет старые defaults/JSON и не создаёт автоматически трёхкомпонентный ансамбль.

**Популяция, cutoff и формула ячейки.** Модуль принимает доказанные закрытые `TP_{j,d}`, `SL_{j,d}` ячейки j по UTC-дням исходного raw-сигнала, её `q_j = tpPct_j / slPct_j`, точный период, frozen `C = observationCutoff`, версию и настройки рецепта. Используются только исходы, доступные не позднее C; сохраняются исходные правила прогрева, cooldown/кластеризации, entry shift, ценового фильтра, горизонта и пропусков. Период сигналов и граница наблюдения исходов различаются: ручной расчёт, использующий свечи после конца периода сигналов, не объявляет их известными на более раннем cutoff. `unclosed`, censored, observation-gap, `no_data` и отфильтрованные входы не превращаются в SL; пустые/null-дни не дают нулевых наблюдений. Цель — условное gross R закрытого TP/SL по выбранной популяции, не безусловный результат всех входов и не персональная PnL монеты. Нет BTC/global factors, fees, slippage, funding, damped/state-space-моделей первой версии.

Для конечных `H > 0`, `κ > 0`: `w_d(C) = 2^(−(C − dayStartUnix_d)/(86400 × H))`, `T_{w,j} = Σ w_d(C) × TP_{j,d}`, `L_{w,j} = Σ w_d(C) × SL_{j,d}`, `W_j = T_{w,j} + L_{w,j}`. Вес относится к UTC-когорте raw-сигнала относительно **одного C**, не к дню выхода/доставки и не к `rowCount`. При `0 < p0_j < 1`: `p̂_j = (T_{w,j} + κ × p0_j)/(W_j + κ)`, **`forecastR_j = F_j = (1 + q_j) × p̂_j − 1`**. Одна prior policy применяется ко всему рецепту; независимый исторический prior требует совместимого target и доказанного отсутствия утечки, а эвристический gross-break-even даёт **`p0_j = 1/(1 + q_j)` для каждой TP/SL-пары**, не одно числовое p0 для всей матрицы. При break-even `F_j = (q_j × T_{w,j} − L_{w,j})/(W_j + κ)`. Нулевое число пригодных закрытий/нулевой W либо недоказанные данные означают unavailable с причиной, не prior-only ноль. Фиктивные будущие исходы не добавляются.

**Три отдельные величины.** `meanR_j = M_j = (q_j × TPCount_j − SLCount_j)/N_j`, где `N_j = TPCount_j + SLCount_j` — реальное число закрытий за период. `forecastR_j` — чистая модельная оценка F. `decisionR_j` — выбранная метрика: M для mean, F для forecast, **`B_j = (1 − λ) × M_j + λ × F_j`** для blend. Сохраняются `trendBlendLambda: 0.05..0.95`, шаг `0.01`, default `0.7` (§10.1.2); новая модель не расширяет этот домен. Если компонента с ненулевым весом unavailable, смесь unavailable; веса не перенормируются скрыто и отсутствующая компонента не заменяется нулём. Общее численное правило «нулевой вес не требует неиспользуемой компоненты» не вводит крайние значения λ в UI/API blend и не меняет отдельные режимы mean/forecast. Поля/проекции результата различают M/F/decisionR; прежний `riskExpectancy` не выдаётся за period mean, когда хранит другую метрику.

**Матрица, выбор и gate.** Сначала вероятность **каждой ячейки** переводится в R со своим q, затем `score = Σ decisionR_j / K` по всем K исходным ячейкам с равными весами. Вероятности разных TP/SL не усредняются вместо R; неоценимые ячейки не исчезают из знаменателя. Требования `minClosedPerCell` и частоты прежние: prior/κ не выполняют минимум реальных закрытий, unclosed остаются в прежней eligible-популяции частотного допуска, если вход пригоден. Robust ranking по соседям, tie-break и выбор кандидата используют decisionR выбранного режима; period mean/F сохраняются отдельно. **Gate неизменен:** mean — `score_mean >= minMeanExpectancy`; forecast и blend — соответственно `score_forecast > minForecastExpectancy` и `score_blend > minForecastExpectancy`, **без дополнительного mean-gate**. Сохраняются прежние пороги/defaults из §10.1.1–10.1.2, не новая подстановка одного порога в другую метрику. Новая формула намеренно может изменить прохождение того же правила допуска; это не обещание прежнего поведения selection.

**Смысл смеси и ограничения.** В baseline без decay (все `w_d = 1`) и с break-even prior `F_j = N_j/(N_j + κ) × M_j`; тогда `B_j = (1 − λκ/(N_j + κ)) × M_j`. Это зависящая от N регуляризация, не независимый ансамбль. Decay меняет временное окно, но компоненты всё равно связаны; отрицательные значения shrinkage поднимает к нулю, поэтому это не универсальный пессимистичный risk penalty. Разные TP/SL/кандидаты имеют разные q, closed N, W и цензурирование; эти counts/ограничения видны, высокий score не доказывает прибыль всех raw-сигналов. Дробные веса не объявляются точным posterior независимых целочисленных trials. Старый trend имеет собственный last-finite endpoint, не автоматически общий будущий горизонт; он не добавляется третьей компонентой без согласования target/момента и отдельной проверки пользы.

**Один рецепт и единая кривая.** H — основной параметр памяти, κ и prior policy/source — расширенные, λ показывается для blend; bendDays остаётся только у выбранного legacy trend. H/κ/prior/λ и method/version фиксируются на исследование, не ищутся тем же optimizer по той же обучающей выборке. Численные defaults новой модели ещё инженерно выбираются, явно версионируются и проверяются **до активации**, без заявления об «оптимальности» и без требования владельцу выбирать математические числа. Telegram наследует рецепт исследования/артефакта, отдельных Telegram-настроек модели нет. В mean-режиме scoring не обязан считать неиспользуемый forecast; отображаемый производный F при его наличии имеет явный тот же рецепт.

График показывает фактические дневные средние, **саму модельную кривую F(x)**, отдельную горизонталь period mean M и, при необходимости, явно подписанную линию `B(x) = (1 − λ)M + λF(x)`. Нет отдельного декоративного spline, выдаваемого за probability-модель. История из sealed buckets помечается ретроспективной: префиксы когорт не доказывают ранней доступности поздно закрывшихся labels. Граница C видима; для probability при `t ≥ C` F(t)=F(C), без изменения весов/mean reversion только по часам. Значение pure forecast в ячейке, модельная кривая на том же t и Telegram forecast совпадают **только при одинаковых исходах, популяции, q, recipe/settings/version и C**. DecisionR режима blend не обязан равняться чистому forecast caption. Свежие ручные данные и frozen-рекомендация могут законно различаться; UI показывает provenance/cutoff, не скрывает различие за одинаковой подписью. Для Telegram сохраняются точный raw-close-маркер/его равенство caption, per-setup overlay и защищённая доставка §11.5.1/signals.md.

**Численный модуль, память и идентичность.** Общий чистый evaluator ячейки/кривой получает входы и рецепт явно; orchestration, рыночные чтения, отбор, кеш, UI/PNG и delivery остаются у своих владельцев. Не вводится plugin framework или второй solver в браузере/renderer. Trial получает компактные scalar/счётчики по ячейкам без генерации всех кривых; кривая строится только для отображаемых ячеек. Mean fast path сохраняется. Рабочие массивы/веса принадлежат оценке/явно ограниченному контексту исследования, освобождаются по success/error/cancel/drain, без глобального межисследовательского накопления; действуют пределы осей, дней и `maxWorkingBytes`.

Новые forecast/blend cache keys, spec/result и checkpoint identity фиксируют method, версию формулы/рецепта, активные H/κ/prior identity/λ, C, данные/популяцию и effective outcome policy. Неактивные настройки не дробят прежний mean-кеш. Старые записи без method читаются по прежнему контракту; новые defaults не пересчитывают их. Смена метода/рецепта/параметров несовместима с продолжением checkpoint как того же исследования; старый checkpoint возобновляется только по своей старой семантике. Seed-воспроизводимость проверяется при тех же recipe/input и бюджете завершённых оценок; другой objective может намеренно изменить seeded-последовательность поиска. PNG/overlay ключи дополнительно содержат время отображаемого raw-close и render version; старые assets/outbox bytes не мигрируют автоматически.

**Этапы приёмки и качество прогноза.** Сначала общий расчёт и паритет матрицы/кривой «Аналитики» на одинаковых входах: формула, разные q, реальные counts против prior, null/однодневные данные, смесь с отсутствующей ненулевой/нулевой компонентой, C/flat future и legacy-совместимость. Затем новые ручные/continuous-рецепты и Telegram: намеренные изменения score/ranking/robust pair при прежних gates, отсутствие поиска H/κ/prior/λ, совпадение чистого F/кривой/caption и отличие от blend, cache/checkpoint/version boundaries и bounded cleanup. Далее ограниченная хронологическая проверка на последующих данных с задержанными/перекрывающимися labels и настройками из более ранних периодов; Brier/log loss дополняются отдельной проверкой калибровки. Для заявления об улучшении **optimizer** нужна последовательность «обучить/выбрать на прошлом → оценить на следующем периоде», не только проверка фиксированного победителя. Из одних sealed buckets ранние OOS-прогнозы не фабрикуются. Качество fit не доказывает predictive superiority; эмпирический успех нового метода не является условием начала всего feature-кода, но настройки должны быть выбраны и проверены до активации. Это не разрешение широкого production-прогона или рыночной догрузки.

### 6.2.1. Тип итогового МО и графика Telegram (18 ноября 2026)

По прямому уточнению владельца для **новых** рекомендаций прежнее правило «caption всегда pure F, не decisionR смеси» заменяется следующим: тип итогового числа и основной линии/маркера PNG совпадает с objective исходного исследования. Подпись итогового числа в Telegram-тексте единообразна для всех типов — «Матожидание торговли: {sign}{value} R» (решение от 18 ноября 2026; описатели «среднее»/«смесь X/Y»/«Прогноз» и суффиксы «по тренду»/«вероятностный» из текста убраны). Два независимых discriminant — `trendMode: mean|forecast|blend` и опциональный `forecast.method: decayed_probability|trend`; отсутствие method в legacy forecast/blend означает weighted trend с исходным `trendBendDays`. В неизменяемой рекомендации режим однозначно представлен отсутствием `searchForecast` для mean, `searchForecast` без `blend` для forecast и `searchForecast.blend` для blend; bend/λ берутся из этих сохранённых полей, не из текущей формы/очереди.

- `mean`: итоговое число — M выбранной пары, основная линия — тот же постоянный M; даже имеющийся probability-рецепт не превращает mean-objective в F.
- `forecast + decayed_probability`: итоговое число — F(C), линия — та же ретроспективная probability-модель общего ядра, что в «Аналитике», с её реальными UTC-разрывами, C и плоским продолжением до raw-close.
- `forecast + trend` и legacy forecast: число — weighted linear/P-spline endpoint `f(x_last)` исходного bend, линия — та же общая fitted-кривая, не OLS-экстраполяция на raw-close. После последней конечной даты значение endpoint сохраняется; новые часы не продолжают склон.
- `blend`: число и основная линия — B = `(1−λ)M + λF`, причём F принадлежит **исходному** probability/trend-методу. M и pure F не выдаются за B. Тип/метод и доли смеси подписаны явно.

В новой версии представления сохраняется компактный типизированный objective вместе с его доступностью/decisionR и отдельной overlay identity, связывающей mode/method/bend/λ, исходные artifact/data/q/C, точный raw-close и число. Кривая и scalar используют общие core-evaluator/series projection, не независимую математику renderer/browser. Равенство с «Аналитикой» требует тех же sealed inputs/популяции/q/периода/C; одинаковой подписи либо endpoint недостаточно. Новая ручная выборка вправе отличаться с видимым provenance. M/чистый F и исторические поля артефакта сохраняют прежний смысл; optimizer score, ranking, gates и старая наука не пересчитываются.

Отсутствующие/невалидные данные выбранного objective, неизвестный тип, несовместимые recipe/cutoff/число/кривая не допускают generic PNG, другого метода, mean/нулевого fallback либо скрытой перенормировки смеси. Число недоступно с причиной, если нет его доказанных компонент; график опускается с явной причиной доставки, остаётся один полный форматированный текст. Доступное M допускается без неиспользуемого F. Нет новых market reads, research/replay, рассылки истории, изменения сохранённых PNG/рекомендаций/frozen bytes; версия нового renderer не запускает массовую перегенерацию старых assets. Рабочие ряды ограничены прежними 3661 днями и байтовыми лимитами, принадлежат одной bounded CPU-операции, освобождаются при успехе/ошибке/отмене; глобального кеша нет.

Целевые регрессии: все три режима с обоими методами и legacy bend; различные M/F/B, неравные rowCount и календарные пропуски; одинаковые scalar/основная кривая/маркер до округления и одинаковые данные с «Аналитикой»; несовместимый/недоступный objective без подмены; отдельные raw-close/overlay identities, строгие bounds и неизменность старых snapshots/delivery bytes. Разрешены только source/docs/tests; production и текущее развёртывание не входят в этот срез.

## 7. Кеш аналитики

Кеш результатов хранится в БД платформы (app DB), рядом с сетапами и настройками, — не в БД сервиса данных. Отдельные таблицы: ячейки матриц, построчные закрытия, выборки зрелости.

Ключ включает: идентификатор и отпечаток набора (число сетапов, первый/последний сигнал, последняя доступная свеча окна последнего сетапа), `direction`, зрелость (или «нет»), разрыв кластеризации в минутах (или «нет» при выключенной кластеризации; по умолчанию 8 ч = 480 мин), временной фильтр — месяц (или `all`) либо закодированный диапазон дней `d:FROM:TO`, TP, SL, горизонт, time-shift, нормализованный до миллионных долей процента порог смещения цены и версию расчётного алгоритма. Ответы содержат признак `cached`. Для матриц предусмотрен cache-only bulk-запрос готовых ячеек; недостающие ячейки досчитываются по одной. Выборка зрелости кешируется отдельно от сделок. Существующие записи кеша, посчитанные с кластеризацией, переносятся миграцией со значением разрыва 480 минут (прежняя константа 8 ч).

Догрузка истории и появление новых свечей автоматически не инвалидируют кеш — как у кеша replay; для пересчёта пользователь очищает кеш и повторяет запрос. Правки свечей внутри неизменного диапазона отпечатка не детектируются (ограничение референса сохраняется честно).

Этот компромисс относится к обычной ручной аналитике. Для автоматического допуска адаптивного варианта в этапе 2 совпадения прежнего ключа/отпечатка недостаточно: результат обязан относиться к тому же frozen input, точным параметрам и причинному bootstrap исследовательской цепочки «поиск → служебный replay → аналитика». Округление ключа цены не должно объединять разные эффективные пороги; null, 0 и отрицательные значения не могут сталкиваться из-за сентинела. Неидентичный общий кеш обходится, а не объявляется подтверждением результата; глобальная очистка ручных кешей ради continuous не допускается. Это не требует совпадения входов независимого live со снимком исследования (§11.6).

Очистка кеша аналитики — отдельная операция: сводка (число записей по таблицам) и удаление только таблиц кеша аналитики. Исходные сетапы, запуски, кеш replay, рыночные данные и настройки не затрагиваются. Выполнявшиеся до очистки расчёты могут создать новые записи после неё.

Вычислительное ядро вправе считать несколько ячеек/строк за один проход по свечам окна и заполнять кеш заранее (уточнение от 9 ноября 2026, реализуется в Rust-движке); контракт маршрутов, ответов, признак `cached` и режим «расчёт только по кнопке» от этого не меняются.

## 9. Критерии готовности

- Расчёты воспроизводят принципы референса: в матрицах — среднее матожидание только по закрытым сделкам; в списках сетапов — закрытие по цене Take Profit или Stop Loss; спорная свеча считается SL; месячный фильтр не обрезает горизонт.
- Повторный запрос с теми же параметрами возвращает `cached: true` без пересчёта; изменение любой компоненты ключа даёт новый расчёт.
- Очистка удаляет только кеш аналитики и показывает число удалённых записей; после очистки повторный запрос считает заново.
- Отсутствие свечей (`no_data`), незакрытие за горизонт (`unclosed`) и фильтр смещения цены различаются и не смешиваются.
- Покрыто тестами: кластеризация и выбор зрелости, гейт смещения в обоих направлениях, приоритет SL при двойном касании, месячная фильтрация до кластеризации, кеш hit/miss/очистка, пустые ячейки.

## 10. Оптимизация параметров алгоритма (Plan A)

Решение владельца от 10 ноября 2026, согласовано до реализации. Разделы 10.1–10.5 описывают ручное разовое серверное исследование, запускаемое из панели выбранного в сайдбаре алгоритма, а не серию пользовательских replay-запусков. Общая вычислительная семантика используется и в этапе 2 с отличиями раздела 11. Направление SHORT/LONG относится к моделированию сделки; исходные события остаются нейтральными WATCH. Комиссии, funding, проскальзывание и исполнение не добавляются.

### 10.1. Фиксированный контекст и оценка

- При создании фиксируются алгоритм/версия, полный снимок текущих параметров как baseline, пользовательский historical-список инструментов (включая делистнутые), период по времени **закрытия сигнала** `[fromUnix,toUnix)`, направление, seed и бюджет поиска. Исторический список не заменяется live-листингом и не меняется вслед за редактированием настроек.
- Зрелость фиксирована для всего исследования, default 0 (первый сетап кластера), диапазон 0..1 с шагом 0.1; **никогда не является поисковой координатой**. При отключённой кластеризации зрелость и разрыв игнорируются. Горизонт фиксирован, default 10080 минут; горизонт сделки не обрезается концом периода сигналов.
- Оси TP и SL выбираются независимо, default каждой `4,6,8,10,12,14,16,18,20` процентов. Это начальная сетка, не запрет других допустимых уровней. Каждая ось содержит 1..64 уникальных конечных числовых уровней `0 < level <= 100`; произведение не больше 4096 ячеек и неизменно для всех кандидатов.
- Score — простое арифметическое среднее **сырых неокруглённых `riskExpectancy` (R)** всех выбранных ячеек с равным весом каждой ячейки, без взвешивания числом сделок, выбора лучшей ячейки или скрытого штрафа за малую выборку. Внутри ячейки действует прежняя формула по закрытым TP/SL: `R = avgMovePct / slPct`.
- Необязательный `minClosedPerCell` — положительное целое, default 1. Если хотя бы в одной выбранной ячейке закрытых сделок меньше порога или R не определён, **весь кандидат неоценим**, `score: null`; пустые ячейки нельзя удалять из знаменателя. Числа закрытых, TP/SL, no_data, unclosed и отфильтрованных сделок показываются явно, малые выборки не скрываются.
- Решение владельца от 11 ноября 2026, уточнение от 12 ноября 2026: необязательный фиксированный `minSetupsPerDay` — конечное неотрицательное число, default 4; это **не поисковая координата**. Числитель — суммарный по выбранным инструментам `selectedSetupCount`: итоговое число сетапов полного кандидата «алгоритм + аналитика», по которым возможно открыть сделку, после детектора, фильтра времени закрытия `[fromUnix,toUnix)`, кластеризации/отбора зрелости **и всех предварительных фильтров допуска аналитики**, включая наличие свечи смещённого входа и включённый гейт смещения цены. UI-флаг «Учитывать смещение цены» разрешается в wire-параметр `priceChangePct`: null отключает этот фильтр. `setupCount` остаётся числом сигналов детектора в выбранном периоде до фильтров аналитики. Знаменатель — вся точная длительность выбранного периода сигналов, включая дробные дни и интервалы без сигналов/свечей, а не число торговых дней и не промежуток между первым и последним сетапом: `durationSeconds = toUnix - fromUnix`, `avgSetupsPerDay = selectedSetupCount × 86400 / durationSeconds`. Таким образом показанные `selectedSetupCount` и `avgSetupsPerDay` относятся к той же популяции, что и частотный допуск.
- Критерий допуска не зависит от успешности/закрытия сделки: TP, SL и `unclosed` входят в `selectedSetupCount`. `price_change_filtered` и `no_data` из-за отсутствия свечи входа не входят, поскольку такая строка не допущена к TP/SL-оценке (как `eligible_count` обычной аналитики). Отсутствие будущего касания при существующем входе остаётся `unclosed`, а не основанием уменьшить частоту. Для всех TP×SL-ячеек используется одна и та же кандидат-специфичная eligible-популяция, без отбора по исходам отдельных ячеек.
- Частотный допуск проверяется без округления среднего и без epsilon: **`selectedSetupCount × 86400 >= minSetupsPerDay × durationSeconds`**. Для сравнения порог берётся из кратчайшей десятичной записи нормализованного числового `minSetupsPerDay` в `spec`; десятичные множители сравниваются точно, без промежуточного binary-float произведения/деления. Равенство допускается: 6 допущенных сетапов за 10 дней дают 0.6/сутки, поэтому default 4 отклоняет кандидата, а порог 0.6 допускает. Если из 6 предварительно выбранных сетапов ценовой фильтр допускает только 2, `selectedSetupCount = 2`, частота равна 0.2/сутки и порог 0.6 не пройден. При нарушении частотного допуска `score: null` независимо от величины R. Значение 0 отключает только частотный допуск; `minClosedPerCell` и определённость всех ячеек остаются обязательными. Вес ячеек и формула целевой функции не меняются.
- Эквивалентный целочисленный минимум — `requiredSetupCount = ceil(minSetupsPerDay × durationSeconds / 86400)`, с тем же точным десятичным вычислением. Например, для диапазона 864060 секунд и порога 4 требуется 41 допущенный сетап; 6 допущенных сетапов дают примерно 0.599958/сутки и не проходят допуск. Порог не округляет длительность до целых дней.
- Совместимость: default 4 применяется к **новым** исследованиям, включая новый POST без поля; новая форма явно отправляет 4, а явный 0 отключает допуск. У ранее сохранённого исследования, чей исходный `spec` не содержит `minSetupsPerDay`, частотный допуск не применялся. Такой JSON/result не переписывается, не пересчитывается и не объявляется прошедшим новый порог. UI показывает отсутствие исторического допуска как legacy/«не применялся», не подставляя 4 при просмотре старой записи; отсутствие новых support-метрик означает «не сохранено», не 0. Serde-default нового вычислительного запроса не является основанием менять смысл старого персистентного результата.

### 10.1.1. Выбор оптимизируемого матожидания (N6, 16 ноября 2026)

**После обобщения 17 ноября:** ниже сохранён контракт legacy trend-рецепта. Новые явно версионированные рецепты используют общий метод и M/F/decisionR по §6.2; default режима mean, реальные evidence/frequency minima и приведённые ниже mode-specific gates сохраняются. Смена формулы новых forecast/blend намеренно меняет ranking, не переименовывает старые результаты.

По поручению владельца ручные и непрерывные исследования получают фиксированные, **не поисковые** настройки `trendMode: mean|forecast` (default `mean`) и `trendBendDays: 7|14|30|linear` (default `linear`, используется только в `forecast`). В continuous они входят в `study` конфигурации и фиксируются на поколение вместе с исходными параметрами. Отсутствие обоих полей в старом config/spec/checkpoint означает `mean`; исходные JSON и результаты не мигрируют и не пересчитываются. Сериализация канонических defaults, mean-арифметика и последовательность seeded-поиска сохраняют совместимость со старыми checkpoints.

В `mean` сохраняется §10.1 без изменений. В `forecast` R ячейки для поиска — `f(x_last)` её взвешенного дневного ряда **точно по §6.1**, включая UTC-день исходного сигнала, setup-count weights, исключение `price_change_filtered`, null-дни, фиксированный `λ=0.1`, линейный fallback и отсутствие экстраполяции. Требования частоты и `minClosedPerCell` прежние; недостаток двух конечных дней хотя бы в одной ячейке делает весь кандидат неоценимым, а не даёт ему среднее/ноль. Score — равновесное среднее выбранной метрики **всех** исходных ячеек. Сравнение кандидатов, incumbent/pending-результатов, winner selection, 3×3 median-capped ranking и tie-break по собственному R используют именно выбранную метрику. Фиксированный шаг/λ не подбираются поиском и не добавляют случайности: при тех же входах, настройках и завершённом бюджете результат детерминирован.

**Решение владельца по gate (N7, заменяет предложение N6):** mean использует прежний `score >= minMeanExpectancy` (default 0.15 R, включая прежнюю допустимость неположительного mean-порога). Forecast использует отдельный фиксированный `study.minForecastExpectancy`, default `0`, конечное число `0..100` R: **`score > minForecastExpectancy`**. Строгое сравнение сохраняет прежнее исключение нуля при default 0; прежний mean-порог к forecast больше не применяется. Это намеренное изменение уже опубликованного N6: положительный forecast ниже старого mean-порога теперь может пройти при default 0. Порог записывается в ручной и continuous study-spec и checkpoint, не является поисковой координатой; отсутствие поля сохраняет default 0, исходные JSON не переписываются. Gate ручного поиска допускает только полностью оценённого победителя выше порога, continuous применяет тот же порог при рекомендации. Принятие нового поколения не меняет уже принятые поколения и live-полномочия.

Исходное неокруглённое среднее R каждой ячейки и всей матрицы вычисляется и сохраняется **всегда**. В forecast-матрице `riskExpectancy` обозначает optimizing forecast, `meanRiskExpectancy` — исходное среднее; победитель сохраняет `trendMode`, `trendBendDays` и отдельный `meanScore`. В generation/рекомендации прежние `rawR`, `meanR` и `meanExpectancy` остаются **средними за период** для совместимости и проверяемого provenance. `selectedCell.forecastR`/`forecastMatrixR` содержат optimizing R выбранной пары/матрицы; аддитивный `searchForecast: {bendDays, cellR, matrixR}` фиксирует эти значения и настройку в рекомендации. Default-поля и отсутствующие forecast-метаданные не сериализуются, сохраняя прежнюю форму mean/checkpoint. UI и Telegram явно подписывают «Выбор по прогнозу», не называют forecast средним и не меняют правила freeze/retry/resend. Сохранённый mean-enrichment и его исторический OLS/PNG не объявляются optimizing P-spline и не переписываются.

В payload списка и детали continuous-процесса `slots[].trendMode: "mean"|"forecast"|null` сопровождает сохранённый `meanExpectancy` в колонке «Среднее матрицы» и описывает режим исследования, которому принадлежит это значение; само `meanExpectancy` остаётся средним за период. Источник — неизменяемый `spec` активного поколения либо, после снятия live-владения, завершённого поколения с совпадающими сохранёнными `meanExpectancy` и `selectedCell`, **не** текущий конфиг или просто последнее исследование. У proven legacy-spec без поля режим равен `mean`: до N6 этот путь всегда оптимизировал среднее за период. Если принадлежность сохранённого значения поколению не подтверждена либо поле невалидно, передаётся `null`, без выдуманного маркера. Записи и исходные JSON при проекции не изменяются.

Для эффективности дневные счётчики принадлежат одной оценке и ограничены исходными осями (≤4096 ячеек), календарём (≤3661 день) и `maxWorkingBytes`; превышение лимита — ошибка, не усечение. Mean-режим не строит дневной массив. B-spline design/узлы/штраф готовятся один раз и переиспользуются всеми ячейками с одинаковыми первой/последней **конечными** датами. Если правое цензурирование даёт разные конечные границы, используются отдельные группы с одним общим design на группу: принудительно общие границы изменили бы endpoint/узлы §6.1. Одновременно удерживается один design, без межоценочного или глобального кеша; по ячейкам меняются только веса/значения и ленточное решение. Расчёт неопределённости и curve sampling не нужны для scoring всех 4096 ячеек.

Приёмка: снижающийся ряд меняет ranking `mean`/`forecast`; повторный запуск детерминирован; старый config/checkpoint без полей сохраняет mean-поведение; gate проверяется в обоих режимах; shared-design endpoint совпадает с N3+N4 на одинаковых дневных рядах, включая null-дни и разные конечные границы.

### 10.1.2. Смесь среднего и прогноза (N7, 16 ноября 2026)

**Граница версий:** правила ниже описывают прежнюю смесь mean + trend. Для новых рецептов смесь mean + выбранный forecast-метод и её доступность определяются §6.2; автоматической третьей компоненты нет. Домен/шаг/default λ сохраняются, checkpoints и результаты не переписываются; forecast/blend по-прежнему не получают дополнительного mean-gate.

Решение владельца: третий фиксированный режим исследования `trendMode: blend` использует `R_blend = (1 − λ) × R_mean + λ × R_forecast`. `trendBlendLambda` — доля прогноза, default `0.7` (30% среднего / 70% прогноза), допустимы `0.05..0.95` с шагом `0.01`; это не поисковая координата и не штраф P-spline `λ=0.1`. Значение хранится как целое число процентов, в JSON сериализуется каноническим числом (например, `0.70` → `0.7`), в ключе — двухзначными процентами. Среднее и прогноз получаются из **одних и тех же** дневных корзин `DailyMatrix`: среднее — сумма R закрытых исходов / число закрытых исходов (не среднее дневных средних), прогноз — прежний weighted fitted endpoint с setup-count weights. Неполные/null-дни, finite-bound groups, fallback и отсутствие экстраполяции те же, что в forecast; без пригодного прогноза смесь тоже недоступна. Второй проход детектора, отдельный дневной массив, глобальный кеш или дополнительный fit не вводятся.

Objective всей матрицы, сравнение кандидатов/incumbent, robust ranking и tie-break используют blend. Периодное среднее и чистый прогноз сохраняются отдельно: `riskExpectancy` — blend, `meanRiskExpectancy` — периодное среднее, `forecastRiskExpectancy` — чистый forecast. Выбранная ячейка дополнительно хранит `blendR`, `blendMatrixR`; прежние forecast-поля остаются чистым прогнозом. В рекомендации аддитивный `searchForecast.blend: {lambda, cellR, matrixR}` обозначает выбранную смесь, не переименовывая исторические поля. Победитель и checkpoint фиксируют режим, bend и λ; изменение λ или forward-порога несовместимо с продолжением того же checkpoint. Для mean/forecast отсутствующий λ означает неактивный default 0.7, новые default/optional-поля не сериализуются: старые config/checkpoint/result сохраняют прежние значения, байты и смысл. Ключ blend-матрицы имеет вид `{scope}:trend:v1:blend:{lambda_key}:{bend}`, например `...:blend:70:7`; старые mean/forecast-ключи не меняются. Исследования по-прежнему не заполняют общий analytics-кеш.

**Решение владельца по gate:** blend — forward-looking семейство и использует **тот же** `study.minForecastExpectancy` (default 0), что forecast: `score_blend > minForecastExpectancy`. Третий порог не вводится; `minMeanExpectancy` к blend не применяется. Отдельный gate по периодному среднему или чистому прогнозу не вводится. Это заменяет предварительное предложение о gate N6/N7; согласование gate больше не ожидается.

Payload сохранённой матрицы расширяется до `slots[].trendMode: "mean"|"forecast"|"blend"|null` и `slots[].trendBlendLambda: number|null`. Для blend λ берётся из того же неизменяемого spec, что и режим (отсутствующий λ в валидном blend-spec означает 0.7), а не из текущего config; для mean/forecast и неизвестного источника λ равен null. Маркер `blend · 30/70` показывает доли **mean/forecast**, вычисленные из сохранённого λ. Legacy-проекция mean/forecast и само периодное `meanExpectancy` остаются неизменными. Ручная и continuous-формы используют общие контролы и сохраняют λ в draft. Приёмка включает blend/forecast same-seed benchmark с одинаковым числом завершённых trials: медианное wall-time blend не выше forecast более чем на 20% (цель — около 0% overhead); timing не превращается в нестабильный обязательный CI-тест.

### 10.1.3. Лучшая forecast-пара сохранённого результата (17 ноября 2026)

**Общий рецепт §6.2:** `forecastBest` остаётся максимумом **чистого forecastR** сохранённой матрицы победителя, не decisionR/blend-score. Для новых результатов метод/версия и cutoff принадлежат сохранённому рецепту того же исследования; UI не выводит их из текущей формы. Старое отсутствие method означает прежнюю семантику, не новый default; старые матрицы не пересчитываются для получения нового F.

В таблице исследований и карточке выбранного ID дополнительно показывается **максимальный чистый прогноз ячейки** сохранённой матрицы `result.best.matrix`. Это максимум по TP×SL-ячейкам **одного сохранённого победителя**, а не поиск другого алгоритмического кандидата среди несохранённых trials, не среднее прогнозов матрицы, не blend-score и не новый критерий допуска или применения live. Прежний `bestScore`/score победителя не меняется: в mean/forecast/blend это objective выбранного режима. По решению владельца от 17 ноября 2026 колонка называется «Лучший Score», не выдавая forecast/blend-score за периодное среднее.

Компактная аддитивная API-проекция `forecastBest: {forecastR, meanR, tpPct, slPct} | null` содержит прогноз максимальной ячейки и **её же** периодное среднее и TP/SL, не независимо найденный максимум mean. Равенство прогнозов разрешается исходным порядком ячеек замороженной матрицы; сравнение выполняется без округления, в том числе для нулевых и отрицательных прогнозов. Учитываются только полные пары конечных чисел с допустимыми положительными TP/SL. Все значения принадлежат тому же сохранённому слепку параметров алгоритма/аналитики.

Проекция использует только сохранённые данные: для blend чистый прогноз находится в `forecastRiskExpectancy`, для N6 forecast — в `riskExpectancy` при сохранённом `trendMode=forecast` (периодное среднее — `meanRiskExpectancy`). Явный `forecastRiskExpectancy` имеет приоритет; отсутствие/невалидность явного поля не позволяет подменить blend чистым `riskExpectancy`. Режим берётся из `result.best`, а при отсутствии поля — из исходного сохранённого spec, никогда из текущей редактируемой конфигурации. Mean/legacy без сохранённых прогнозов и неполные пары возвращают null; отсутствующая метрика не равна нулю. Во время работы без сохранённой матрицы `progress.bestScore` не позволяет восстановить пару.

Список возвращает только компактную `forecastBest` рядом с прежним `bestScore`: максимум извлекается SQL-проекцией из уже сохранённой матрицы только для ограниченной страницы, без передачи полных matrix/events клиенту или API-процессу. Деталь вычисляет ту же проекцию при выдаче уже загруженного сохранённого результата. Расчёт не запускает fit, research, replay, backfill или рыночные чтения, не обновляет старые JSON, не требует миграции и не хранит дополнительный архив trials/кеш. Временная память ограничена одним проходом матрицы (до 4096 ячеек) и одной возвращаемой парой на запись, срок жизни — обработка запроса.

### 10.2. Поиск и применимость

Plan A реализуется нативно в Rust: начальное покрывающее исследование пространства (space-filling), чувствительность параметров в нескольких контекстах, несколько стартовых точек и уточнение от крупного к мелкому шагу (multistart coarse-to-fine), одиночные, парные и совместные мутации с продолжающимся глобальным исследованием. Чувствительность в одной точке не считается основанием навсегда исключить параметр. Результат — лучший полностью проверенный кандидат в пределах бюджета, **не доказанный глобальный оптимум**.

Все домены конечны и зафиксированы пользователем до старта. UI строит параметры по метаданным выбранного модуля; числовые границы допустимости не подменяют разумные поисковые диапазоны. Текущая конфигурация служит baseline; параметры качества данных по умолчанию фиксированы, но доступны для осознанного включения в подбор. Составные ограничения проверяются общей валидацией модуля. Исследование не меняет текущую конфигурацию. Полный baseline алгоритма и аналитики обязательно оценивается как trial 0, даже если его значения не входят в поисковые массивы, и входит в общий бюджет. Поисковая структура алгоритма — generic map реальных field keys, не hardcoded AlgorithmSpace с переименованными координатами.

В аналитике варьируются кластеризация (bool), разрыв кластера, time-shift и гейт цены (отключён или числовой порог). Неактивные координаты канонизируются: без кластеризации нет измерений зрелости/разрыва; без гейта нет порога. Отключённый гейт отличается от порога 0. Разрыв приводится к минутам, эквивалентные значения не создают отдельные кандидаты. Неприменимые поля другого алгоритма, зрелость и `minSetupsPerDay` как поисковые поля отклоняются. Фиксированные параметры, включая направление, период, горизонт, оси и частотный порог, не мутируют.

Seed, версия оптимизатора, стабильный порядок кандидатов и детерминированные пакеты оценки обеспечивают повторимость при одинаковых входных данных и бюджете завершённых оценок; скорость параллельных задач не задаёт порядок обновления поиска. Ограничение по реальному времени и ручная остановка могут дать разное число законченных пакетов. Равные score разрешаются стабильным порядком, а не порядком завершения потоков.

### 10.3. Данные и изоляция

Перед сравнением кандидатов фиксируются фактически прочитанные свечи **и пропуски** для всех инструментов: максимальный прогрев по доменам, период сигналов, максимальный time-shift и фиксированный горизонт сделок. Все оценки используют один неизменный снимок; новые свечи/догрузки во время поиска его не меняют. Сетевой сбой, неверный ответ или незавершённая пагинация чтения являются ошибкой исследования, а не отсутствующими свечами или нулём сигналов. Чтение не запускает backfill.

Общий расширенный снимок не меняет семантику детектора: каждый кандидат получает собственное начало прогрева и начальное состояние cooldown, идентичные отдельному свежему replay с его параметрами. Сигналы фильтруются по `[fromUnix,toUnix)` **до** кластеризации; метрики не включают сигналы общего максимального прогрева.

В app DB отдельно сохраняются метаданные исследования, статус, прогресс, ограниченный список крупных событий/выводов и компактный итог. Вычисление кандидатов изолировано: не создаёт обычные `replay_runs`/`replay_batches` и не читает/заполняет общие replay/analytics-кеши. В ручном режиме это ограничение действует на всё исследование; отдельная служебная post-chain этапа 2 разрешена по разделу 11, но не для каждого trial. Первая реализация держит raw-снимок и промежуточные данные только в RAM исследования с явным настраиваемым byte cap; превышение лимита — явная ошибка, не усечение входов. Ограниченный приватный временный каталог допускается как последующее расширение, но не является критерием приёмки первой версии. Нет постоянного архива trials и memoization результатов между исследованиями; из результатов кандидатов сохраняется только победитель, не коллекция матриц. Временные данные освобождаются по окончании владеющей операции; для continuous frozen input удерживается до окончания всей post-chain, не только вычислительной стадии.

Сохраняемый победитель содержит полный набор параметров, фиксированный входной scope, матрицу и счётчики, seed/версию поиска, происхождение/хеши реально использованных данных и ограниченные главные выводы. Во время работы персистентны только progress.bestScore и ограниченные события вместе с метаданными/статусом; полный лучший кандидат удерживается в RAM до завершения, затем сохраняется в result. Промежуточные incumbent-снимки в БД запрещены. В победителя допускаются только полностью законченные оценки всех выбранных ячеек/инструментов. При остановке ручного исследования сохраняется лучший завершённый результат с явной пометкой частичности; при отсутствии оценимых кандидатов победитель отсутствует. При аварийной потере процесса RAM-победитель теряется, по одному bestScore он не восстанавливается. После окончания владеющей операции raw-снимок удаляется: хеши позволяют обнаружить несовпадение входов при повторе, но **не гарантируют точное воспроизведение позже**. Ручное исследование не применяет результат в live и не меняет пользовательские настройки; применение в адаптивные слоты continuous разрешено по разделу 11.

### 10.4. Серверный жизненный цикл и API

Владелец работы — сервер, не браузерный цикл запросов. Состояния: `queued`, `running`, `cancel_requested`, `completed`, `cancelled`, `failed`. Создание возвращает 202 после персистентной регистрации; разрыв HTTP, закрытие диалога/страницы или обновление браузера не отменяют работу. UI после загрузки обнаруживает исследования через список и восстанавливает отображение через GET деталей; polling только наблюдает. Ограничение первой реализации — одно активное исследование (`queued/running/cancel_requested`) во всей платформе — не является целевым глобальным правилом этапа 2: continuous использует отдельную ёмкость и не блокирует ручные исследования, replay и аналитику (раздел 11.1).

Общий UI-опрос исследований и наблюдение непрерывных процессов используют интервалы 3 секунды при активной работе и 15 секунд в покое; скрытые страницы/вкладки не опрашиваются. Смена выбранного алгоритма не скрывает активность других алгоритмов от общего наблюдателя. Подписи настроенных профилей, отсутствие результатов и смысл даты изменения слота определены в [UX](ux.md#s-00-оптимизация-параметров-алгоритма); они не меняют серверный жизненный цикл или сохраняемую идентичность слотов.

Явная отмена кооперативна: прекратить допуск новых вычислений, остановить/дождаться текущих задач, сохранить только полностью проверенный incumbent, очистить временные данные, затем `cancelled`. Повторная отмена идемпотентна; терминальный статус не переписывается. При рестарте серверного процесса прерванное незавершённое исследование получает `failed` с причиной `interrupted_by_restart`, сиротские временные каталоги очищаются. Автоматическое возобновление вычислений после падения сервера **не обещается**; восстановление UI после reload обязательно.

Некорректный домен/составные параметры — 400; неизвестное исследование — 404; занятый слот соответствующего режима или сменившаяся версия алгоритма — 409 (ответ busy содержит activeStudyId); превышение ресурсного допуска — 429 с ресурсом/лимитом. Наличие continuous-работы само по себе не означает занятость ручного слота. Список и детали не запускают вычисления.

Решение владельца от 11 ноября 2026, уточнение UI от 12 ноября: алгоритм выбирается в правом сайдбаре, видна одна панель его настроек. В разделе «Оптимизации» этой панели встроенная таблица показывает пять последних summaries (`limit=5,offset=0`) без элементов пагинации. Кнопка «Посмотреть весь список» открывает полную историю в отдельном диалоге с серверной пагинацией по 10 строк; данные полной таблицы загружаются только при открытом диалоге, без фонового накопления страниц или матриц. Колонки обеих таблиц: «ID», «Диапазон дат» (закрытие сигналов `[fromUnix,toUnix)`), «Время исследования» (`progress.elapsedSeconds`), «Минимум сетапов в день» (для legacy без поля — «Гейт не применялся», явный 0 остаётся 0), «Лучший Score» (score с двумя десятичными знаками и ` R`, при отсутствии — «—») и «Действия». ID загружает полную запись отдельным GET и открывает существующий подробный результат строго этого исследования. При выборе ID в полном списке его диалог остаётся под результатом с сохранённой страницей; закрытие результата восстанавливает список и фокус на исходной кнопке ID. Два экземпляра таблицы не разделяют DOM ID. Переключение алгоритма скрывает, а не размонтирует его форму. Отдельная кнопка «Оптимизировать» сохраняет рабочий процесс создания/просмотра активного или последнего исследования и перехода к новому запуску; открытие полной истории само по себе не запускает исследование.

Для ручных `queued/running` в обеих таблицах доступна остановка; `cancel_requested` показывает принятый запрос без повторной команды. Для continuous построчной Stop нет, в том числе через API; остановка выполняется для режима выбранного алгоритма (раздел 11.6). Терминальные исследования можно удалить с подтверждением, если это не нарушает ссылки на сохраняемый результат/адаптивный слот. Удаление отдельной записи не удаляет обычные прогоны, общие analytics/replay-кеши, настройки или market-data. После остановки/удаления таблицы и состояние соответствующего режима обновляются без reload страницы; при опустевшей последней странице полной истории offset корректируется. Placeholder гибкого live относится к UI-каркасу первого этапа [S-00](ux.md#s-00-оптимизация-параметров-алгоритма), а не к целевому контракту continuous раздела 11. Ручные исследования по-прежнему не включают live и не применяют к нему победителя.

Дополнение от 12 ноября 2026: «Время исследования» показывает фактическое `progress.elapsedSeconds`, а не разность `updatedAt-createdAt`. Общий formatter показывает полное число целых дней/часов/минут без искусственного верхнего ограничения, отбрасывая остаток секунд; для времени меньше минуты — «Менее 1 мин». Отрицательное конечное значение ограничивается нулём, отсутствующее или нечисловое/бесконечное — «—». Даже большое конечное время не заменяется порогом вида «9999 дн+»; вывод ограничен тремя единицами измерения. «Лучший Score» показывается ровно с двумя знаками после десятичной точки и суффиксом ` R` (например, `0.00 R`, `-0.13 R`), отсутствующий score — «—». Это только форматирование summaries, без изменений серверного времени, score, пагинации, остановки/удаления и вложенного диалога выбранного ID.

Нормативная JSON-форма создания (значения ниже иллюстративные; baseline передаётся полностью, decimal-параметры алгоритма — строки, integer — числа):

```json
{
  "algorithmId": "price_volume_spike",
  "algorithmVersion": "1.1.1",
  "instruments": [{"exchange":"bybit","category":"linear","symbol":"BTCUSDT"}],
  "fromUnix": 1793491200,
  "toUnix": 1794096000,
  "direction": "short",
  "setupMaturity": 0,
  "horizonMinutes": 10080,
  "tpLevels": [4,6,8,10,12,14,16,18,20],
  "slLevels": [4,6,8,10,12,14,16,18,20],
  "minClosedPerCell": 1,
  "minSetupsPerDay": 4,
  "algorithmParams": {"priceGrowthPct":"12","windowMinutes":5,"baselineLongDays":30,"baselineShortDays":7,"volumeMultiplier":"3","cooldownMinutes":5,"maxGapPercent":"1","maxConsecutiveGapMinutes":5,"requiredRecentMinutes":10},
  "algorithmSearch": {"priceGrowthPct":["8","12","16"],"windowMinutes":[3,5,10]},
  "analyticsParams": {"clusterEnabled":true,"clusterGapMinutes":480,"timeShiftMinutes":0,"priceChangePct":null},
  "analyticsSearch": {"clusterEnabled":[false,true],"clusterGapMinutes":[240,480],"timeShiftMinutes":[0,5],"priceChangePct":[null,0,1]},
  "seed": 42,
  "maxTrials": 256,
  "maxSeconds": 3600
}
```

`algorithmParams` и `analyticsParams` — полные baseline-объекты. `algorithmSearch` и `analyticsSearch` — maps непустых конечных массивов; UI может принимать min/max/step, но разворачивает bounded диапазоны в значения перед отправкой. Отсутствующие в search поля фиксированы в соответствующем baseline; неизвестные ключи запрещены. Decimal-поля алгоритма сохраняют строковый тип; analytics использует bool/integer/number/null. `clusterGapMinutes` — целое 1..10080, `timeShiftMinutes` — целое 0..43200, `priceChangePct` — null либо конечное число −100..1000. UI может показывать разрыв в часах, wire всегда в минутах. Начальные значения формы analytics: true/480/0/null; maturity и horizon находятся только в фиксированном scope, не в search. Плоские поля бюджета: `maxTrials` — 1..4096 (default 256) полных совместных trials, `maxSeconds` — 1..86400 (default 3600); baseline trial 0 учитывается. Размеры доменов/запроса ограничиваются ресурсным допуском. Сервер возвращает нормализованный полный request, включая применённые defaults и фактический бюджет; бюджет не повышается скрыто.

Запись API имеет точную форму `{id,status,spec,progress,result,error,createdAt,updatedAt,events}`, id — целое число. `spec` — нормализованный полный `StudyRequest` в camelCase по примеру выше, включая algorithmId, scope, baseline и поисковые домены; дублирующего поля request нет. `progress` — текущий снимок `{phase,evaluatedCandidates,scorableCandidates,maxTrials,elapsedSeconds,bestScore}`; `bestScore` всегда присутствует, null до первого оценимого кандидата. Подготовка входов обозначается `progress.phase = acquiring`, не отдельным lifecycle-статусом. Дальнейшие фазы различают начальное исследование, чувствительность, уточнение и очистку. Статусы записи остаются `queued/running/cancel_requested/completed/cancelled/failed`.

`result` — null во время работы, после завершения null либо `StudyOutcome` формы `{progress,best,reason}`. `reason` принимает `trial_budget`, `time_budget`, `space_exhausted`, `cancelled`; ошибка исследования выражается через status/error, не вымышленной причиной успешного завершения. `error` — null либо `{code,message}` без секретов. `best` — null, если оценимого победителя нет, либо `{score,partial,params,analytics,matrix,provenance,conclusions}`. `params` содержит полный алгоритмический набор; `analytics` — эффективные clusterEnabled/clusterGapMinutes/timeShiftMinutes/priceChangePct (неактивный разрыв null); фиксированные maturity/horizon берутся из `spec`, maturity не применяется при clusterEnabled=false. При `best: null` UI явно объясняет отсутствие кандидата, удовлетворившего одновременно частотному допуску `minSetupsPerDay` и требованиям всех ячеек/`minClosedPerCell`; нулевой score не подставляется. Незавершённый trial не публикуется как результат; после аварийной потери RAM result остаётся null.

`matrix` содержит все выбранные `{tpPct,slPct,riskExpectancy,avgMovePct,closedCount,tpCount,slCount,unclosedCount,noDataCount,priceChangeFilteredCount}`. `provenance` содержит `{optimizerVersion,seed,snapshotHash,capturedAt}`; точный scope и домены находятся в `spec`. `partial` true для частичного итога отмены, false только при штатном завершении выбранного бюджета/поиска; даже false не означает доказанный глобальный оптимум. `events` — ограниченные крупные события `{at,kind,message}`, без payload промежуточных кандидатов или архива trials; `conclusions` победителя ограничены по числу и размеру. Baseline score/counts для сравнения допустимы как компактная сводка, не вторая сохранённая матрица кандидата. `TrialSummary` в `result.baseline` и `result.best.support` содержит итоговый `selectedSetupCount` после всех фильтров открытия сделки, фактический `avgSetupsPerDay` на его основе и целочисленный `requiredSetupCount`; для нового завершённого кандидата число и среднее всегда числа. Для старого сохранённого результата отсутствующие метрики остаются null/неизвестными; исторические score, счётчики и среднее не пересчитываются под новый порядок фильтров, их смысл определяется сохранённой `optimizerVersion`. `requiredSetupCount` также null, если конечный порог требует числа сетапов за пределами представимого целого счётчика — такой кандидат не проходит допуск. Показанное среднее не используется вместо точного сравнения допуска. В выводах победителя кратко указываются допущенное после фильтров число, фактическая частота и требуемый минимум. История отдельных trials не добавляется. При `best: null` пояснение UI учитывает также невыполнение `minSetupsPerDay`, а не только требования ячеек.

### 10.5. Приёмка

- При закрытом браузере сервер продвигает работу; после reload UI обнаруживает то же исследование и его результат без повторного POST. Закрытие модалки не равно Stop.
- Explicit Stop, ошибка чтения и рестарт сервера дают честный терминальный статус; временные данные освобождены, незавершённый trial не становится победителем.
- Score проверен на неравных числах сделок по ячейкам: равные веса ячеек, отсутствие округления до усреднения, вся матрица неоценима при одной пустой ячейке/нарушенном minClosedPerCell.
- Частотный допуск проверен на 6 допущенных сетапах за 10 дней (неоценимы при default 4), равенстве порогу, дробной длительности периода и отключении порогом 0. При одинаковых параметрах алгоритма ценовой фильтр может уменьшить eligible-число и сделать кандидата неоценимым, хотя число до фильтра достаточно; выключенный фильтр не уменьшает его. Отсутствующий вход исключает строку, но `unclosed`, TP и SL не уменьшают частотный числитель. Высокий R не обходит допуск, отключение частотного порога не отменяет `minClosedPerCell`, а legacy-spec/result без нового поля сохраняются в API/БД без изменений.
- Все кандидаты используют одинаковый frozen input; сравнение со свежим replay подтверждает прогрев/cooldown и close-time границы, включая разные длины прогрева и пропуски.
- Кластеризация off и гейт off не порождают дубликаты из неактивных координат; maturity не изменяется поиском. Оба зарегистрированных алгоритма работают через metadata, без отдельных форм.
- До/после ручного исследования списки обычных запусков и общие кеши не меняются; настройки live/аналитики не изменены. Финальный snapshot переживает reload, raw/trials не переживают завершение ручной операции. Для continuous действует отдельная служебная цепочка раздела 11.

## 11. Непрерывные исследования и адаптивный live — этап 2

Решение владельца от 12 ноября 2026 с уточнением от 14 ноября: live инициализируется независимо от frozen-входов исследования, без повторной проверки завершённого победителя. Ручной one-shot раздела 10 остаётся отдельным режимом без автоматических побочных действий. Биржевая автоторговля — отдельный будущий этап, сейчас не разрешена.

**N8 — решение владельца от 16 ноября 2026, реализация разрешена локально.** Непрерывное исследование и адаптивные live-профили — независимые подсистемы. Единственная передача между ними — полностью завершённый проходной результат исследования связки «алгоритм × minSetupsPerDay», создающий первый профиль либо новую принятую версию существующего профиля. У каждого профиля собственные Stop/Play; Stop исследования отменяет и очищает текущую исследовательскую цепочку, последующий Start создаёт новое исследование. Решения Q1–Q8 утверждены в §11.8 и обязательны для реализации. Разрешены локальные код, миграции и тесты; развёртывание отменено, push и серверные изменения не разрешены.

Контракты maintenance drain/resume и durable recovery §11.1.1 не подменяются пользовательским Stop/Start; сохранение будущей research-конфигурации под завершённой maintenance-паузой описано там же. Разграничение исторических названий команд и новых операций дано в §11.1.2.

### 11.1. Область и очередь

- У пользователя есть последовательная серверная очередь исследований: запущенные исследовательские процессы алгоритмов × их сохранённые непустые списки уникальных `minSetupsPerDay`. Состав берётся из конфигурации research, **не** из списка существующих/запущенных профилей. Элементы обходятся round-robin; один элемент проходит полную цепочку «исследование → служебный replay → аналитика → gate/finalize», затем очередь продолжается независимо от live-инициализации. «Полный круг одного исследования» означает завершение этой цепочки одной связки, не барьер ожидания всех связок очереди. Частотный порог фиксирован внутри исследования, не является поисковой координатой.
- Изменение списка порогов после research Stop/cleanup либо при закрытом maintenance admission в состоянии `drained` меняет только следующий обход новой конфигурации. Для новой связки профиль появляется после первого полностью принятого результата, не при сохранении конфигурации. **Утверждено Q3:** исключённые из очереди связки больше не исследуются, но их самостоятельные профили сохраняют настройки и состояние Stop/Play; удаление порога не является командой остановки или удаления профиля. Разные связки могут иметь одинаковые параметры, но не общие runtime-состояния.
- Домены, baseline, направление, historical-инструменты, оси TP/SL, горизонт, аналитические параметры и бюджет задаются как для one-shot; алгоритмические поля берутся из метаданных модуля. Отличия — относительный период, список частотных порогов, зрелость 0 и служебная цепочка. Seed, версии и эффективная конфигурация сохраняются в происхождении результата.
- Ручные исследования, replay и аналитика не блокируются непрерывной очередью: для них предусмотрена отдельная ёмкость, без общего межрежимного «одно активное исследование». Это не отменяет явных ресурсных лимитов. Будущие tenant-ы должны работать параллельно на сбалансированных кластерах; такой распределённый контур сейчас не объявляется реализованным.

**Переполнение отдельного кандидата continuous (18 ноября 2026).** Превышение только `setups_per_candidate` при материализации пробного кандидата означает его ресурсную непригодность, а не ошибку всего непрерывного исследования. Жёсткий предел raw-сигналов по полному universe сохраняется: набор не усекается, неизвестные метрики не заменяются нулями. Если один проход детектора обслуживает несколько предложений с одинаковыми алгоритмическими параметрами и разной аналитикой, непригодны все предложения только этой группы. Каждое учитывается один раз в `evaluatedCandidates` и бюджете `maxTrials`, наблюдается поиском с `score: null`, не увеличивает `scorableCandidates` и не становится победителем; последующие предложения продолжают оцениваться в прежнем стабильном порядке. Причина возвращается ограниченным событием без массива raw-сетапов или полного снимка параметров. Ровно предельное число сигналов допустимо; превышение не расходует технический retry. Если все рассмотренные кандидаты непригодны, поиск штатно заканчивается по существующей причине исчерпания пространства/бюджета с `best: null`, `scorableCandidates: 0`, без искусственного score, служебного replay и нового live-handoff; прежний принятый профиль не меняется. Непригодность отличается от незавершённой оценки при отмене/deadline; порядок предложений, RNG и joined-batch граница checkpoint не меняются.

Это правило относится и к baseline trial 0, в том числе вне поисковых доменов. Если baseline превысил cap, его научная сводка отсутствует (`baseline: null`), а не содержит выдуманные counts/score. Приватный checkpoint получает обратно совместимый `baseline_infeasible`: отсутствующее поле означает false, false не сериализуется; true устанавливается только для такого превышения trial 0 и восстанавливается вместе с counters/frontier/records. До первого trial сводка отсутствует и marker=false; после него существует ровно одно из сводки и marker=true. Marker=false сохраняет прежнее требование наличия даже неоценимой обычной baseline-сводки, поэтому её потеря остаётся ошибкой. Marker=true требует отсутствия оценимого baseline-record и победителя trial 0: для baseline внутри доменов обязателен его record с `score: null`, вне доменов сохраняются прежние baseline-sent/seen identity без фиктивных координат/record. Это не общий архив причин непригодности. Старые корректные checkpoints без marker сохраняют прежние строгие проверки; результаты и численные оценки непереполненных кандидатов не переписываются.

Все прочие ресурсные/инвариантные ошибки, включая working/snapshot/checkpoint/runtime budgets, ошибки детектора/входов и persistence, остаются ошибками исследования; отмена и deadline сохраняют прежние исходы. Исключение не распространяется на ручной one-shot и прямую оценку/материализацию. Итоговый служебный replay и аналитика победителя повторно соблюдают тот же cap: превышение запрещает публикацию и остаётся технической ошибкой, не публикует усечённый набор и не выбирает молча другого победителя.

### 11.1.1. Безопасные обновления и durable resume

Решение владельца от 14 ноября 2026 разрешает **только для continuous** приватный персистентный снимок входов и текущего состояния поиска. RAM-only ограничения, запрет промежуточного incumbent и `interrupted_by_restart` из §10 сохраняются для ручного one-shot, но не запрещают этот внутренний checkpoint. Публичный `optimization_studies.result` по-прежнему null во время поиска; приватные артефакты не являются готовым `StudyOutcome`, пользовательской историей trials или межисследовательской memoization.

- **Maintenance drain на пользователя.** Сохранённый в app DB флаг запрещает admission новых continuous-цепочек всех его алгоритмов. Уже допущенные цепочки продолжаются до полного gate/finalize с heartbeat; после рестарта их восстановление разрешено и при drain. Drain не меняет desired-running, ревизии, конфигурацию или разрешения live, не отменяет incumbent и не действует на manual/fixed/live. `draining` означает наличие незавершённой цепочки, `drained` — её отсутствие при закрытом admission. Возобновление admission снимает только maintenance-флаг; оно не включает ранее остановленный процесс и не сбрасывает retries. Общий Stop сохраняет прежние отмену, fencing, деактивацию и точный cleanup.
- **Будущая конфигурация под maintenance-паузой.** Существующий авторизованный `PUT /v1/continuous-studies/{algorithmId}` может изменить research-конфигурацию при `desired_running=true` только в одной fenced-транзакции: durable maintenance-строка пользователя существует и имеет `admission_paused=true`, у пользователя нет ни одного running continuous-поколения (`drained`), процесс не `stopping`, его `active_generation_id` и `active_study_id` равны null. Общая owner advisory mutation lock сериализует проверку с resume/admission, maintenance-строка дополнительно блокируется до commit. Если эти условия не выполнены (исследование может быть в полёте, включая случай без maintenance-строки), сохранение не отклоняется, а откладывается: конфиг записывается в `pending_config` (HTTP 200), активное поколение сохраняет свои config/revision-фенсы и завершается с параметрами, заданными до его запуска; membership очереди до применения не меняется. Отложенный конфиг применяется атомарно в транзакции конца поколения (finalize/fail) перед постановкой следующего исследования или при старте остановленного процесса: один раз увеличивается `config_revision`, `continuous_slots.enabled` перестраивается по порогам из применяемого конфига. Процесс в статусе `stopping` по-прежнему отклоняет сохранение 409. Форма параметров непрерывного исследования в вебе доступна для редактирования и сохранения во время идущего исследования (источник значений — `pendingConfig`, если задан, иначе активный конфиг) и показывает сообщение, что сохранённые параметры будут применены только к следующему запущенному исследованию; кнопка сохранения — «Сохранить параметры». Немедленное (прежнее разрешённое) сохранение увеличивает `config_revision` один раз и меняет только research-конфигурацию и membership очереди (`continuous_slots.enabled` по новому списку порогов); сохраняются desired-running, status, phase, error, retry count, next-attempt, next-slot и null active-указатели. Самостоятельные профили, live-intent/runtime и отдельная проекция adaptive-разрешения не меняются. После maintenance resume следующий обычный admission использует новую ревизию/spec без скрытого Start и сброса retries; прежние поколения, история и их сроки не переписываются. Настройка остановленного процесса сохраняет прежнюю семантику.
- **Frozen input.** До поиска PostgreSQL хранит bounded `bytea`-chunks и атомарно committed version/checksum manifest полного упорядоченного входа: исходные decimal-строки детектора, точные числовые представления аналитики, timestamps, scope, границы и пропуски/пустые инструменты, snapshot hash/capturedAt. Запись/чтение потоковые, без дополнительного клона размером со снимок. Полнота, порядок, длины и checksums всех chunks проверяются до использования. Незавершённый initial acquisition можно честно повторить; committed snapshot нельзя заменять свежим чтением или дозаполнять после backfill.
- **Checkpoint поиска.** После полностью joined-пакета атомарно сохраняются версия/identity, RNG и точная позиция, frontier/очереди/seen/records/influence, фаза, evaluated/scorable/submitted и proposal counters, baseline и полный лучший законченный кандидат с матрицей. Частично вычисленный пакет после crash переоценивается, но не считается завершённым и не пропускается. Постоянный архив матриц всех trials не создаётся.
- **Восстановление стадий.** Совместимый snapshot/checkpoint продолжает те же study/generation/start/cutoff и параметры. Завершённый поиск не повторяется: следующий этап — replay; committed replay читается для аналитики/gate, готовый gate финализируется идемпотентно. Completed research/replay/result и incumbent не переписываются из-за recovery. Совместимая пауза процесса не является новой технической попыткой; реальные ошибки/неуспешные recovery ограничены исходным retry budget, рестарт его не сбрасывает.
- **Время и fencing.** Исходный абсолютный wall-clock deadline поиска фиксируется один раз от `execution_started_at`, acquisition включён; downtime его не продлевает. После истечения сохраняется исход `time_budget` с последним полностью оценённым incumbent (либо без победителя); обязательная post-chain имеет отдельный жизненный цикл и не отменяется самим истечением поискового бюджета. Resume сохраняет точный committed frontier и порядок предложений, но при wall-clock ограничении downtime может уменьшить число оценок и изменить итогового победителя относительно непрерывного прогона; равенство финального trial count при разных таймерах не обещается. Все записи/restore/finalize проверяют owner, revision/config identity, lease epoch, формат, версии optimizer/algorithm, request/input hashes. Несовместимый/повреждённый checkpoint — видимая bounded техническая ошибка, не скрытый restart с новыми ID/окном и не качественный nonpass. Старый RAM-only процесс нельзя retroactively превратить в resumable; его потерянный вход не восстанавливается по одному bestScore. Rollback на старый бинарник после появления нового private state не поддерживается: он не умеет ни resume, ни новый maintenance gate; откат требует отдельной совместимой стратегии.
- **Неопределённый исход записи.** Потеря подтверждения `COMMIT` не является повреждением исследования: typed transport/availability ошибки допускают не более трёх идемпотентных попыток принять тот же durable head. Неустранённая неопределённость сохраняет те же active study/generation/input/deadline и даёт видимую ошибку/backoff; новую попытку восстановления учитывают атомарно при следующем lease claim, в том числе после потери связи до записи ошибки. Третий допущенный recovery исполняется, четвёртый автоматически не начинается; `durable_resume_retry_exhausted` оставляет head до явного Start, который повторяет эту же цепочку, либо прежнего разрушительного Stop. Maintenance resume не сбрасывает попытки. Счётчик consecutive recovery failures сбрасывается только новым durable boundary, не heartbeat, phase/progress или повторным подтверждением того же checkpoint. Чистая приостановка уже допущенного recovery сохраняет его учтённую попытку даже до нового boundary; lease для housekeeping сам по себе не даёт разрешения на исполнение. Авария третьей попытки до записи ошибки вызывает только metadata-latch, не четвёртый recovery. Неизвестная свежесть контрольных DB-проверок обрабатывается так же; достоверный Stop/fence loss, повреждённые/несовместимые данные и ошибки вычисления остаются отдельными исходами.
- **Освобождение.** Снимок и приватный checkpoint принадлежат поколению до завершения/drain исходной цепочки. При terminal/fail/Stop они удаляются после fencing/drain, не затрагивая успешных детей и историю; действует orphan reclamation. Maintenance drain сам по себе не удаляет вход ещё работающей цепочки. Storage admission учитывает per-chain и общий объём snapshots/checkpoints, пиковую замену, DB/WAL и резерв остальных линий.

Авторизованный API (cookie mutations требуют существующий browser Origin/CSRF guard):

| Маршрут | Ответ 200 |
|---|---|
| `GET /v1/continuous-studies/maintenance` | `{admissionPaused,state,activeChains,resumableChains,updatedAt}` |
| `POST /v1/continuous-studies/maintenance/drain` | Установить durable drain, вернуть тот же статус; идемпотентно |
| `POST /v1/continuous-studies/maintenance/resume` | Возобновить admission без Start/сброса retries, вернуть тот же статус; идемпотентно |

`state` — `running`, `draining` или `drained`; counts — целые bounded counts на пользователя; `updatedAt` — ISO timestamp либо null до первой настройки. `resumableChains` считает только цепочки с committed frozen manifest; статус не обещает совместимость произвольной будущей версии. Список `GET /v1/continuous-studies` аддитивно содержит `maintenance` той же формы. Приватные input/checkpoint payloads в polling не выдаются.

**Штатный порядок последующих развёртываний.** До обслуживания фиксируются исходный maintenance-флаг и активные работы каждого затрагиваемого пользователя. Через авторизованный существующий `POST /v1/continuous-studies/maintenance/drain` закрывается новый admission, состояние проверяется через `GET /v1/continuous-studies/maintenance`. Это не продуктовый Stop/Start, не мгновенная пауза всех исполнителей: уже допущенная цепочка заканчивает исследование, служебный replay, аналитику и gate/finalize, live продолжает работу. По умолчанию до cutover ожидается `drained`. Более ранний cutover требует отдельного разрешения, подтверждённой совместимости durable state и безопасного graceful shutdown; один `resumableChains` этого не доказывает. Незавершённые ручные работы проверяются отдельно: RAM-only исследование не покрывается этим resume и не отменяется автоматически.

Maintenance-флаг сохраняется закрытым при замене/запуске сервиса. После запуска проверяются здоровье, сохранность конфигурации/истории, совместимое восстановление незавершённых цепочек с теми же ID, входами и исходным deadline, затем их фактическое продвижение. Для live проверяется реальное продвижение курсоров, не только статус `active`. Только после успешной проверки установленная для этого обслуживания пауза снимается авторизованным `POST /v1/continuous-studies/maintenance/resume` с проверкой возобновления admission. Если допуск был закрыт до обслуживания, он остаётся закрытым; ранее остановленные процессы не запускаются, retries не сбрасываются. При ошибке восстановления пауза сохраняется, причина сообщается явно. Эта процедура сама по себе не разрешает рестарт защищённых сервисов или несовместимый rollback.

Историческое условие перехода №19/№20 ниже — уникальное legacy-исключение для того обновления, не повторяемое разрешение прерывать работу при последующих деплоях. Новый порядок не меняет его исходную запись или условия.

Приёмка: crash до/после snapshot commit и batch checkpoint, сохранение ID/окон/дедлайна/порядка кандидатов и матрицы; recovery после completed search/replay/gate; drain с heartbeat/finalize и restart, resume без скрытого Start; stale lease/revision/Stop/cleanup; corrupt/version mismatch; лимиты storage, bounded replacement и реальное освобождение/orphans. Ручной one-shot, fixed/live и успешная история не меняются. Переходный production-rollout согласуется отдельно: №19 должен завершить всю исходную цепочку до допустимого однократного прерывания уже начавшегося №20. Telegram отложен, локальный publisher не входит в этот этап.

### 11.1.2. Разграничение пользовательских команд и обслуживания

Новые пользовательские команды описаны в §11.6 и не вызывают прежнюю совмещённую операцию остановки research + live. Сохранённые исторические формулировки «Общий Stop … деактивацию» и «Start, который повторяет эту же цепочку» в §11.1.1 относятся к прежнему API/управлению восстановлением, **не** определяют новые кнопки Stop/Start исследования. Для пользовательского Stop/Start действует решение от 16 ноября: отмена только исследовательской работы и новый study ID после cleanup; действующие профили не выключаются. Не допускается реализовать обе семантики одним неразличимым Start.

Сам maintenance-контракт не меняется: drain закрывает новый admission, уже допущенная цепочка доходит до finalize; совместимый crash/restart восстанавливает прежние ID, frozen input, checkpoint, исходный deadline и retry accounting. Maintenance resume не запускает остановленные исследования/профили, не выдаёт бюджет и не создаёт новое исследование вместо восстанавливаемого. Пользовательски остановленная цепочка fenced и очищена, поэтому не подлежит durable resume. При исчерпанном recovery и сохранённом head новый пользовательский Start не подменяет его новой цепочкой молча: сначала явный research Stop/cleanup либо отдельный `POST /v1/continuous-studies/{algorithmId}/recovery/retry` для технического восстановления того же head (утверждено Q6).

### 11.2. Последние N суток, исходы и частота

- В момент **фактического старта каждого исследования**, не постановки в очередь, фиксируются `start` и точный период закрытия сигналов `[start - N×86400, start)`. Это последние N суток до старта: без horizon lag, ожидания семи дней или скрытой замены периода. UTC-границы и длительность сохраняются; выравнивание технического чтения свечей не меняет выбранные даты. Внутри всей цепочки и повторов её стадий период не движется; новое исследование получает новый фактический старт.
- При фактическом старте один раз фиксируется единый для всех инструментов и стадий исходной исследовательской цепочки `observationCutoff` — время закрытия последней завершённой минуты, доступной на этот старт, **≤ start**. Ни acquisition, включая длительное постраничное чтение, ни replay/аналитика не добавляют свечи, закрывающиеся после cutoff, даже если теоретическое окно time-shift + horizon уходит дальше. Снимок однократно фиксирует реально прочитанные свечи до cutoff и пропуски; поздно загруженная историческая свеча входит только если попала в этот снимок, без последующего дозаполнения/перечитывания его дыр. В матрицах, score, win rate, среднем движении и других performance-агрегатах **на всех исследовательских стадиях участвуют только наблюдавшиеся закрытые TP/SL-сделки**. Незавершённая сделка не становится нулевой доходностью, принудительным SL или закрытием по последней доступной цене. Этот cutoff не ограничивает последующее чтение текущих закрытых свечей независимым live.
- Отсутствие свечи входа (в том числе если её время ещё не наступило), открытая сделка без доступного полного горизонта, пропуски наблюдения и реально истёкший горизонт без касания различаются в диагностике. Отсутствие будущего ряда не выдаётся за доказанное horizon-expired `unclosed`. Правое цензурирование последних сигналов и состав закрытой выборки раскрываются явно; последние N суток не называются полностью созревшей оценкой всех открытых сделок. Старые ручные результаты автоматически не переклассифицируются.
- **Частотный допуск не является агрегатом доходности.** `selectedSetupCount`/`avgSetupsPerDay` сохраняют смысл раздела 10.1: число допущенных открытых входов, включая `unclosed` и ещё не закрывшиеся открытые сделки; отсутствующий вход и `price_change_filtered` исключаются. Отбор только TP/SL для матожидания не переносится в числитель частоты. Знаменатель — весь frozen-интервал, не время наблюдавшихся закрытий. Это историческая частота eligible-входов, а не обещанное число немедленных live-сообщений с условием будущей цены.

### 11.3. Причинная кластеризация

При `clusterEnabled=true` зрелость **всегда 0**, заблокирована для редактирования и не включается в search: представитель — первый raw-сигнал gap-связанного кластера по инструменту. Gap отсчитывается от предыдущего raw-сигнала детектора, а не последнего опубликованного/прошедшего ценовой гейт. Если первый представитель не прошёл гейт, следующий сигнал того же кластера не выбирается вместо него. При разрешённом доменом `clusterEnabled=false` кластеризация выключена на всех стадиях; добавлять её только поверх live-публикации победителя нельзя.

Исследование, служебный replay и аналитика используют один зафиксированный причинный bootstrap: начальную границу/состояние детектора, cooldown и предыдущего raw-сигнала. Предшествующая периоду история продвигает состояние без экспорта сетапов; её наличие не заменяется новым пустым кластером на границе replay или очередной порции. Модель инициализации сохраняется в происхождении исследовательской цепочки. Адаптивный live соблюдает те же причинные правила обработки, но получает собственные начальную границу и состояние по доступным текущим закрытым свечам, а не копирует bootstrap исследования. Его прогрев также продвигает cooldown и предыдущий raw-сигнал без публикации исторических сетапов; граница live-порции не сбрасывает состояние. Равенство двух независимо инициализированных состояний не требуется. Это не автоматическое изменение прежней ретроспективной зрелости ручной аналитики.

### 11.4. Frozen post-chain и сохраняемый набор

После исследования с оценимым победителем выполняются обычный по вычислительной семантике служебный исторический replay с его полными параметрами, сохранение завершённого набора и аналитика этого набора с его лучшими/фиксированными аналитическими параметрами и **исходной полной сеткой TP×SL**. Не подставляются другие UI-defaults, только удачные ячейки или иной набор инструментов. Точные даты, свечи/пропуски и bootstrap совпадают со снимком исследования; перевод close-time границ в интервалы открытия свечей не меняет scope.

Frozen input с явным владельцем и бюджетом удерживается до окончания/прекращения исходной цепочки «исследование → служебный replay → аналитика → gate», затем освобождается после drain использующих его задач; ожидание или восстановление независимого live не продлевает его жизнь. Служебные артефакты имеют происхождение continuous, пользователя, алгоритм, порог и связь с исследованием. Численный перебор trials остаётся изолированным; служебные наборы создаются для проверки итогового победителя, не для каждого кандидата. Завершённый replay остаётся сохраняемым набором, даже если дальнейшая аналитика не завершилась.

Все чтения для допуска строгие: транспортная ошибка, неполная пагинация или невалидные значения — технический сбой, не пустой ряд/`no_data`/успешная нулевая выборка. Общий кеш допустим только при доказанном совпадении frozen input, точных эффективных параметров и bootstrap; прежний cache hit без такой идентичности обходится. Нельзя объединять отличающиеся price-change-пороги округлением ключа или смешивать null с числовым сентинелом. Изменившиеся данные не подменяют входы начатой исследовательской стадии и не переписывают завершённые score/матрицу/происхождение. Только согласованный проходной результат всей исходной цепочки передаётся независимому профилю по §11.6; повтор на тех же данных не объявляется независимой проверкой доходности. Последующая догрузка, ремонт истории или отличие текущих live-свечей не запускают автоматическую revalidation или повторную оптимизацию старого победителя. Новые параметры и рекомендации поступают только из следующего полностью принятого исследования той же связки в round-robin-очереди. Наличие либо запуск такой очереди не является условием дальнейшей работы уже принятого профиля.

### 11.5. Допуск и рекомендуемая ячейка

Ниже описан default `mean`. Для opt-in `forecast` численные R в objective, gate и robust ranking заменяются выбранной метрикой по §10.1.1; отчётные средние за период §11.5.1 остаются отдельными исходными метриками.

- Допуск — **неокруглённое среднее R всей исходной матрицы ≥ заданного порога**, default **0.15 R**, вместе с прежними частотным допуском и `minClosedPerCell`. Вес всех исходных ячеек одинаков; неопределённые/непригодные ячейки не исключаются из знаменателя. Это не порог R одной выбранной ячейки и не порог статистики соседей.
- Для рекомендации оси исходной сетки сортируются численно. Для ячейки `c` окно `W(c)` — центр и ближайшие индексы ±1 по обеим осям (3×3 с обрезанием по краям, без padding/интерполяции). `robustScore(c) = min(R(c), median({R(u): u ∈ W(c)}))`. Медиана чётного числа значений — среднее двух центральных. Невалидные ячейки не пропускаются ради улучшения окна. Максимизируется `robustScore`, затем собственное сырое R; оставшаяся ничья разрешается стабильным численным порядком TP, затем SL по возрастанию. Singleton не называется подтверждённо устойчивым к соседям. Дополнительный top-K, допуск «почти максимум» и новые настраиваемые пороги не вводятся.
- В сообщении рекомендуются направление исследования, TP/SL выбранной ячейки, time-shift и условие смещения цены. Показываемое R — **сырое R выбранной ячейки**, не `robustScore`; среднее всей матрицы показывается отдельно. Выбор локально поддержанной ячейки не подменяет objective оптимизатора.
- Сетап публикуется немедленно при raw-детекции, с причинным отбором кластера, если он включён. Time-shift задаёт **рекомендуемое будущее время**, не отложенную отправку/подтверждение. Пользователь сам проверяет ценовое условие к этому времени; система не ждёт будущую цену, не отменяет сообщение по ней и не утверждает заранее, что условие выполнено. Очередь ожидающих live-входов/отложенных подтверждений не создаётся. Формулы направления и ценового гейта остаются из раздела 4; отдельная адаптивная рекомендация LONG/SHORT сопровождает исходный нейтральный WATCH, не изменяет его тип и не является автоматической сделкой.

### 11.5.1. Обогащение рекомендации и динамика матожидания (15 ноября 2026)

Согласовано владельцем до реализации. Обогащение — отдельный версионированный производный снимок со ссылкой на исходные исследование/поколение/профиль, provenance frozen input, выбранные TP/SL, effective analytics и точный период. Отдельно разрешённый ниже исторический пересчёт дополнительно сохраняет собственное происхождение данных и не объявляется исходным frozen-результатом. Обогащение не является новым победителем, новым gate или изменением сохранённой науки. **Решение от 17 ноября ниже заменяет для будущей новой ревизии прогноз и PNG от 15–16 ноября; описание OLS, динамики и общего study-PNG ниже сохраняет контракт прежних ревизий, а не альтернативный fallback нового predictor.** Метрики различаются:

- **Среднее выбранной пары** — уже сохранённое сырое `rawR` этой ячейки по наблюдавшимся закрытым TP/SL-сделкам; не `robustScore` и не среднее дневных точек. **Win rate** той же пары равен `100 × tpCount / (tpCount + slCount)` при ненулевом знаменателе. Недостающие/отфильтрованные входы, unclosed, right-censored и observation-gap не становятся закрытыми сделками и не входят в знаменатель. Исходная выборка и ограничения правого цензурирования из §11.2 сохраняются.
- **Среднее матрицы** остаётся прежним равновесным средним **всех** исходных ячеек, включая выбранную; gate и значение `meanR` не меняются. Подпись «В среднем для других уровней TP и SL» — пользовательское переименование прежнего показателя, не исключение выбранной ячейки или введение нового objective.
- **Период N** берётся из зафиксированных границ конкретного исследования: `(toUnix − fromUnix) / 86400`. Он динамический, может быть дробным, не подменяется константой из примера или текущей отредактированной конфигурацией continuous. Настройка периода применяется к следующему исследованию штатным путём.
- **Дневной ряд** выбранной пары использует причинный отбор исходного continuous-набора, его time-shift/ценовой gate и frozen cutoff; R закрытой сделки относится к **UTC-дню закрытия исходного raw-сигнала**, не к времени входа или закрытия сделки. Одинаковые сохранённые индивидуальные исходы дают одинаковые UTC-точки и тренд в рекомендации и обновлённой «Аналитике» по §6. Настройка timezone текстового интерфейса не меняет эти дневные группы. Обычные ручные cache-строки, рассчитанные позже по новым свечам, не объявляются исходной frozen-аналитикой только из-за совпадения TP/SL или агрегатных counts.

**Единая временная ось UTC, подтверждена владельцем 15 ноября.** Для набора один раз фиксируется и сохраняется `originUnix` — UTC-полночь дня начала его точного периода (`floor(fromUnix / 86400) × 86400`). Координата UTC-bucket с полуночью `dayStartUnix` равна `x_i = (dayStartUnix − originUnix) / 86400`; у произвольного timestamp `x(t) = (t − originUnix) / 86400`. Таким образом отсутствующие даты сохраняют реальные календарные расстояния, а произвольное время получает дробную координату суток. Используются Unix-секунды и UTC без DST; browser timezone не участвует в расчёте. Для ручного графика «Аналитики» origin аналогично закрепляется за началом отображаемого периода; произвольная смена origin внутри одного снимка запрещена.

Для конечных дневных средних `y_i` вычисляется OLS с **равным весом каждого конечного дня**: `b = Σ((x_i − meanX) × (y_i − meanY)) / Σ((x_i − meanX)²)`, `f(x) = meanY + b × (x − meanX)`. День без строк либо без закрытых исходов не становится точкой `y=0`: отсутствующий/null-bucket не участвует в суммах, на графике отсутствие данных/разрыв не маскируется вымышленным нулём. Требуются хотя бы две конечные точки с разными UTC-днями; иначе линия тренда, её изменение и прогноз недоступны, а не равны нулю. При единственной точке допустимо показать её без тренда. Дневные средние не взвешиваются числом сделок и не подменяют отдельное среднее всех закрытых R выбранной ячейки.

**Динамика МО** — `f(x_last) − f(x_first)` между **первой и последней конечными UTC-датами** исходного ряда, не разность самих наблюдаемых крайних точек, не `b × N` и не процентная доходность. Подпись «Динамика МО за последние N суток» связывает оценку с зафиксированным исследовательским периодом, но не обещает наличие закрытий в каждый его день. На обоих концах линии подписываются fitted-значения `f(x_first)` и `f(x_last)`; endpoints и наклон относятся к той же календарной UTC-регрессии. Смена периода будущего исследования не двигает endpoints уже сохранённого снимка.

**Прогноз МО торговли** — `f(x(rawSignalAt))` по той же календарной UTC-линии и тому же сохранённому origin. `rawSignalAt` — исходное закрытие сигнальной минуты, не DB commit, отправка/повтор доставки, открытие UI или рекомендуемый вход `rawSignalAt + timeShift`. Дробная часть координаты учитывает время внутри UTC-суток; нельзя округлить его до дня или начать отсчёт заново в момент выдачи. Коэффициенты не пересчитываются по live-исходам. Прогноз фиксируется один раз в новой рекомендации и не меняется при просмотре/повторе; это линейная экстраполяция без гарантии доходности и без влияния на допуск/ордера. Версия расчёта, `UTC`, origin, границы, координаты дней и provenance сохраняются в производном снимке. Старый индексный/browser-local fit не переименовывается в новый: версия меняется явно, без записи новых значений в исходный результат или старые рекомендации.

**Сохранение и обогащение существующих профилей.** Для новых цепочек необходимые компактные дневные исходы/счётчики формируются из исходных post-chain данных до освобождения frozen input, с теми же причинными правилами и проверкой согласованности с выбранной сохранённой ячейкой. Хранение ограничено числом дней допустимого периода и byte budget; полные свечи/trials не удерживаются ради графика. Для уже существующего профиля разрешено прочитать относящиеся именно к нему сохранённые результаты, наборы и подтверждённые исходы и создать отдельный аддитивный производный снимок. Результаты исследования, матрицы, origin, параметры и выбранная пара остаются побайтово неизменными. Нет повторного research/replay/gate/revalidation или чтения новых рыночных данных для восстановления якобы исходной оценки. Старые рекомендации, сообщения и уже зарегистрированные delivery bytes не переписываются и не ставятся заново; обогащение копируется только в последующие новые рекомендации этого же профиля. WATCH без исходной рекомендации не получает задним числом текущего победителя.

Сохранённая post-chain матрица достаточна для среднего/win rate, но **не** для восстановления порядка дневных исходов; одни raw replay-сетапы также не содержат закрытий сделок. Само наличие записей в `analytics_trades_cache` не доказывает точные параметры/фильтры, полноту выборки или совпадение с исходным cutoff: для старого точного тренда нужны полный совместимый набор индивидуальных исходов и доказанное происхождение. Освобождённые frozen-свечи не предполагаются существующими. Каждая отсутствующая или не подтверждённая метрика имеет явное состояние «недоступно»/причину; нельзя показывать 0, выдумывать линию или заменять старую выборку текущим рынком. Пересчёт по иным данным не входит в разрешение «из сохранённых результатов»; отдельное ограниченное разрешение владельца от 15 ноября приведено ниже. Неполнота enrichment не выключает ранее принятый профиль, не меняет его retries/readiness и не задерживает публикацию свежего сетапа. Для нового сетапа такого действующего профиля отправляются доступные метрики и полные условия одним текстовым сообщением без PNG, с видимой недоступностью тренда/прогноза; этот режим заранее фиксируется до freeze тела по signals.md, не переписывает уже pending-доставку и не обещает отправку отсутствующего фото.

**Отдельный исторический производный пересчёт действующих профилей (дополнительное решение владельца от 15 ноября 2026).** Владелец поручил выполнить пересчёт для **текущих действующих legacy-профилей без дневного ряда**, а не для всей прошлой истории и не только при следующем запуске приложения. Разрешено оценить сделки по сохранённым исходным raw replay-сетапам на доступных исторических свечах в пределах исходного периода и границ чтения, с закрытиями не позднее исходного `observationCutoff`. Применяются исходные направление, выбранные TP/SL, effective analytics, причинная инициализация/кластеризация, time-shift, ценовой gate и horizon; отсутствующие параметры не заменяются текущими defaults. Нет нового поиска, оптимизации, детекторного replay, gate/revalidation, догрузки или изменения рыночной истории. Будущие поколения штатно сохраняют дневные исходы своей исходной post-chain до cleanup; их путь не заменяется этим пересчётом.

Доступные исторические свечи могут отличаться от освобождённого frozen input, в том числе из-за поздней догрузки или исправлений. Новый производный снимок явно отличается от исходной frozen-оценки: сохраняются отдельная версия/ревизия, время пересчёта, ссылка на исходную цепочку, её период/cutoff и параметры, а также происхождение, отпечаток и пропуски фактически прочитанных данных. Даже совпадение агрегатов не делает эти данные исходным frozen-снимком. Формулы UTC-дней, OLS, динамики и прогноза выше неизменны. Перед использованием сверяются TP/SL/closed counts и среднее выбранной ячейки, а также причинно отобранные/допущенные счётчики с сохранёнными исходными значениями. Расхождение сохраняется как явный результат сравнения для решения владельца; конфликтующие метрики не публикуются молча и не переписывают исходную оценку. Ошибка или неполное чтение не считаются нулевым исходом.

Пересчёт выполняется отдельно от live commit, с ограниченными чтением, CPU/RAM, временем и параллелизмом, без остановки live или перезапуска выполняющейся цепочки (на момент поручения — поколение №21 / исследование №25). Повтор идемпотентен; перед началом и подключением результата проверяется прежняя идентичность действующего профиля. Остановленный или заменённый профиль не включается заново, его readiness/retries и текущая исследовательская очередь не меняются. Исходные результаты и производные артефакты неизменяемы; пригодная новая производная ревизия предпочтительно используется только для **последующих новых сетапов** того же ещё действующего профиля. Старые рекомендации, сообщения и pending bytes не меняются и не рассылаются заново. Приёмка этого поручения требует фактически обработать текущие подходящие профили с видимым исходом: новый ряд/график, расхождение либо конкретная нехватка данных; одной startup-only возможности недостаточно. Согласованный ограниченный пересчёт не требует повторного разрешения; он не разрешает посторонние защищённые изменения или прерывание текущих работ.

**График.** PNG «Динамика матожидания» представляет сохранённый исторический ряд и тренд, без зависящего от будущего сетапа продления: прогноз остаётся отдельным числом в рекомендации, поэтому изображение переиспользуется для исследования. Базовый визуальный контракт — [signals.md](signals.md#форматированная-рекомендация-и-png-15-ноября-2026), уточнённый ниже решением владельца от 16 ноября. Ключ учитывает исходное исследование/снимок, выбранную пару, версию расчёта, timezone и версию оформления; PNG хранится один раз с ограничением байтов/пикселей, не в каждом снимке сетапа и не в неограниченном RAM-кеше. Восстановление изображения из сохранённых производных данных допустимо без нового исследования. Если данных для ряда нет, картинка не фабрикуется.

**Telegram PNG — уточнение владельца от 16 ноября 2026.** Следующие правила относятся к будущим отсутствующим рендерам 900×320; уже сохранённые PNG, их exact-key кеш и байты pending-доставок не регенерируются и не переписываются. Это изменение представления, не новая научная ревизия: сохранённые OLS, динамика/прогноз рекомендации, матрица, результаты исследования и выбранная ячейка остаются неизменными.

- Заголовок содержит **среднее МО выбранной TP/SL-пары за весь период** и **win rate по совокупности точек графика**: `100 × ΣTP / (ΣTP + ΣSL)`, не среднее дневных процентов. Среднее берётся из сохранённой выбранной ячейки, а при отсутствии её агрегата — из дневных средних с весом числа закрытых TP/SL. Положительное среднее окрашивает заголовок зелёным, отрицательное — прежним негативным цветом, нулевое — нейтральным; знак определяется до округления. Незакрытые/неполные/цензурированные исходы не входят в знаменатель win rate и не становятся SL. При отсутствии конечных дней PNG не строится; данные не дополняются текущим рынком.
- Параметры `trendMode`, `trendBendDays`, `trendBlendLambda` берутся из **сохранённого spec исходного исследования**, связанного с артефактом, а не из текущей конфигурации очереди или последней версии профиля. Для legacy-spec без этих полей действуют `mean`, `linear`, `0.7`. `mean` показывает постоянный уровень среднего за период; `forecast` — `f(x)` общего weighted linear/P-spline solver из §6.1 с выбранным перегибом `7|14|30|linear`; `blend` — `(1−λ)·mean + λ·f(x)` с тем же ограниченным `trendBlendLambda`, default `0.7`. Вес конечного дня — его сохранённое число допущенных сетапов `rowCount`, включая незакрытые; null-дни не становятся нулями. Обе конечные подписи относятся к отображаемой линии. При менее чем двух конечных датах линия не фабрикуется. Новый fit — только ограниченное представление sealed UTC-точек; старый численный OLS артефакта не заменяется им.
- Прямая и кривая аппроксимация рисуются **только линией без жёлтой заливки**, доверительной полосы или замкнутого заполненного пути. Линия не продлевается за первую/последнюю пригодные исторические даты.
- Нулевая линия имеет слева явную подпись **`0`**. Верхняя подпись оси равна максимуму отображённых дневных значений и линии, но не меньше `1`; нижняя — минимуму тех же значений, но не больше `0`. Декоративный padding не меняет подписанные пределы; крайние значения кривой включаются в масштаб.
- Единственный render job удерживает только ограниченный артефакт и три trend-поля исходного spec; fit/кривая и RGBA-пиксели освобождаются после рендера. Прежние лимиты дней, SVG/PNG-байтов, пикселей, single-CPU lane, durable retries и кеша сохраняются. Изменения live/research lifecycle, повторная отправка истории и миграция сохранённых PNG в этот срез не входят.

Приёмка уточнения: заголовок со средним и агрегированным win rate, включая незакрытые строки и разный вес дней; сохранённые study-параметры и default λ для mean/forecast/blend; линейный fallback короткого ряда и кривая без заливки; явный ноль и точные пределы оси при положительных, отрицательных, субединичных и экстремальных значениях; неизменность sealed artifact и уже сохранённого exact-key PNG, детерминированность и прежние byte/pixel budgets.

Приёмка этого среза: одинаковые UTC-дневные точки/календарный OLS в обновлённой «Аналитике», сохранённом графике, динамике и прогнозе на одинаковых исходах; отсутствующие/null-дни не становятся нулями и не сжимают расстояние; смена browser timezone не меняет fit; выбранное среднее/win rate отдельно от дневного тренда и неизменного gate; динамический дробный N; оба endpoint labels на первой/последней конечных UTC-датах, одноточечный/пустой ряд; дробная UTC-координата raw-close и стабильность при задержанном commit/повторе/UI; versioned переход без переписывания старых результатов; backfill с полной/частичной/отсутствующей доказанной историей без scientific rewrite или resend; byte/pixel/cache limits, cleanup и защищённая совместимая доставка по signals.md.

#### Единый вероятностный прогноз Telegram (решение от 17 ноября 2026)

**Первоначальный Telegram-only срез, позднее расширенный владельцем.** Ограничения ниже «не меняет optimizer» относятся к этому исходному срезу. Актуальный §6.2 распространяет общий рецепт на ручные матрицы/кривые и новые manual/continuous forecast/blend, разрешая намеренное изменение их ranking/выбора/допуска при неизменных формулах gates. Старые артефакты сохраняют исходную семантику. Совпадение caption с чистым F не означает совпадения с decisionR смеси.

**Статус и scope.** Владелец одобрил замену раздельных OLS-caption и spline/blend-PNG единым frozen predictor для **обоих** представлений. Порядок работ: сначала необходимые PRD-правки и отчёт владельцу, затем утверждённая реализация; текущая фаза заканчивается отчётом без правок кода. Это производное обогащение выбранного принятого профиля, не новый objective/gate, поиск TP/SL или изменение `rawR`, матрицы, winner и научных результатов. Первая версия не включает damped-тренд, динамическую logistic/state-space-модель, глобальные рыночные/BTC-факторы, комиссии, проскальзывание и funding; она не читает новые данные ради этих признаков.

**Целевая величина и выборка.** Оценивается общая для исходного universe профиля и его выбранной TP/SL-пары вероятность TP **условно на разрешившемся TP/SL** при сохранённых направлении, алгоритме/параметрах, причинном отборе, effective analytics, entry shift, ценовом условии и horizon. Это не отдельная обученная вероятность данного symbol, не безусловный результат каждого raw-сетапа и не персональная доходность/исполнение. В выборку входят только доказанные TP/SL, ставшие наблюдаемыми не позднее frozen `C = observationCutoff`; timestamp касания в минутной модели не подменяет фактическую доступность закрытой свечи. `unclosed`, right-censored, `no_data`, observation-gap, отфильтрованные и ещё не наступившие входы не считаются SL. Пустые/null-дни не становятся нулевыми исходами.

**Формула первой версии.** Пусть `q = tpPct / slPct > 0`, `TP_d`, `SL_d` — числа пригодных закрытых исходов UTC-когорты исходного raw-сигнала с полуночью `dayStartUnix_d`. Возраст в сутках `a_d(C) = (C − dayStartUnix_d) / 86400`, вес `w_d(C) = 2^(−a_d(C) / H)`, где конечный `H > 0` — half-life в календарных UTC-сутках. Не используются день закрытия сделки, число отправок или возраст доставки. Все веса конечной оценки вычисляются относительно **того же C**, а не текущих часов. `T_w = Σ w_d(C) × TP_d`, `L_w = Σ w_d(C) × SL_d`, `W = T_w + L_w`; это веса **закрытых TP/SL counts**, не `rowCount`, число допущенных/незакрытых сетапов или равные веса дневных средних.

При `κ > 0`, `0 < p0 < 1`: `p̂_C = (T_w + κ × p0) / (W + κ)`, `forecastR_C = (1 + q) × p̂_C − 1`. `κ` — сила регуляризации, не число реально наблюдавшихся сделок. `p0` берётся либо из независимой исторической базы с доказанными совместимостью target и отсутствием утечки/повторного использования той же выборки, либо задаётся как **явно эвристический** gross-break-even anchor `1 / (1 + q)`; во втором случае `forecastR_C = (q × T_w − L_w) / (W + κ)`. Источник/политика `p0` сохраняются, независимая история не фабрикуется. Равные вероятности TP/SL не означают нулевое R при `q ≠ 1`. Нет пригодных закрытий/положительного конечного `W` либо нет доказанного происхождения — прогноз **недоступен с причиной**, а не prior-only ноль или подстановка period mean. Будущие TP/SL, экстремальные сценарии и пустые дни не добавляются как наблюдения для fit.

**Открытое инженерное уточнение настроек.** Конкретные численные `H` и `κ`, а также выбор политики/источника `p0` **ещё не определены и не считаются калиброванными**. Их нужно явно выбрать, версионировать и проверить при подготовке **до активации модели**; это инженерная задача, не требование к владельцу самостоятельно выбирать математические числа и не новое согласование уже принятого продуктового направления. Критерии: воспроизводимость и простота baseline; отсутствие подбора на его же последующей оценке/победителе; чувствительность к sparse/correlated counts; совместимость target и независимость исторического prior либо честно обозначенный эвристический gross-break-even anchor. Значения и статус доказанности явно фиксируются как версионированные настройки; не допускаются молчаливые defaults или объявление произвольных констант «оптимальными». Изменение настроек создаёт новую модельную ревизию, не меняет старую. Обсуждённое сравнение простых baseline, включая отсутствие decay, не включает такой режим автоматически в первую активируемую версию.

**Frozen и время прогноза.** Снимок хранит версию модели/формулы, `H`, `κ`, `p0` и его происхождение, target/outcome policy, полный universe/его проверяемую идентичность, TP/SL, effective analytics, исходные study/generation/profile, точные период/UTC-origin/C, доказанное происхождение и отпечаток исходов, счётчики и доступность. Для `t = rawSignalAt ≥ C` прогноз равен **постоянному `forecastR_C`**: без новых исходов часы не пересчитывают веса и не тянут оценку к нулю или «среднему рынка». Не возникает ни линейной экстраполяции, ни нового slope/сценария. `rawSignalAt` не заменяется entry/commit/send/UI-time. Пересчёт по новым исходам допустим только как отдельная явная модельная ревизия; live-свечи не обновляют sealed snapshot скрыто. Невозможный для prospective-прогноза порядок `rawSignalAt < C` не маскируется исторической оценкой без lookahead.

**График и число в тексте — одна модель.** PNG сохраняет тёмное оформление и размер 900×320 целиком с заголовком; фактические дневные средние выбранной пары и число закрытых TP/SL отделены от модельной линии. Модельная история строится той же формулой по префиксам UTC-когорт с соответствующей границей префикса; её конечная точка на C равна `forecastR_C`. При наличии только sealed buckets все использованные исходы известны лишь на C: такой участок явно подписывается **«Ретроспективная модельная оценка»**, а не исторический online/OOS-прогноз. Нельзя выдавать закрытие сделки, позднее добавленное в раннюю когорту сигнала, за известное в тот ранний день. Подлинную историческую доступность можно утверждать только при доказанных timestamps раскрытия исходов.

На графике явно отмечается граница C; справа — горизонтальное продолжение модели до исходного `rawSignalAt` конкретного сетапа и отдельный маркер **«Прогноз на закрытие сигнала»**. Его неокруглённый R **в точности равен** сохранённому числу caption; подпись использует то же округление. При `rawSignalAt = C` маркер совпадает с границей. Смена момента просмотра/отправки не сдвигает маркер. Заголовок по-прежнему показывает отдельные **среднее за весь период** и совокупный win rate по закрытым TP/SL, не прогноз и не среднее дневных средних. UTC-пропуски и реальные расстояния сохраняются, модель/маркер входят в масштаб осей. Линия без заливки; первая версия не заимствует spline-SE/95%-полосу как свою неопределённость. Прогноз, его версия и provenance в тексте и PNG не смешиваются со старыми OLS/spline-ревизиями; если совместимый PNG недоступен, штатный один text-only fallback фиксируется до freeze, без старого PNG «для иллюстрации».

**Новая идентичность рендера и владение ресурсами.** Прежнее правило «одно готовое PNG исследования для всех будущих raw-close» для этой новой ревизии заменяется общей неизменяемой базой и **per-setup overlay** с C, горизонтальным участком и raw-close-маркером. Новая версия расчёта/рендера и ключ включают идентичность исходного/производного снимка, модели и всех её настроек, TP/SL, UTC/C, оформление, точный `rawSignalAt` и значение/доступность прогноза; одинаковый R при разных raw-close не даёт права вернуть чужой маркер. База может переиспользоваться, финальный PNG формируется для конкретной рекомендации и freeze доставки. Не создаётся неограниченный постоянный study-кеш всех overlay.

Владелец базы — производный снимок/ограниченный asset-кеш; временных модельных точек, overlay и RGBA — один render job; frozen image/body — соответствующая durable-доставка. Сохраняются пределы 3661 дневной точки/3660 суток, бюджета входного артефакта, одного CPU-render lane, PNG 256 KiB, 900×320 и relay body 384 KiB. Кеши базы/overlay и очередь ограничены одновременно числом элементов и байтами, с фактическим вытеснением/cleanup по действующей политике; ссылки, пиксели и буферы освобождаются после success/error/cancel и drain. Сохранение immutable delivery bytes до завершения retries не подменяется RAM-кешем. Новый рендер не блокирует detector/commit, не продлевает TTL и не разрешает очищать исторические артефакты ради смены версии.

**Границы статистических утверждений и проверки.** Дробные decay-веса — power-likelihood/регуляризованная оценка, не точный posterior целого числа независимых Bernoulli trials. Перекрывающиеся сетапы и выбор победителя ограничивают интерпретацию sample size/неопределённости. Ни красивая кривая, ни shrinkage не доказывают превосходство над прежними OLS/spline/blend; первая версия не обещает калиброванного 95% покрытия или prediction interval отдельной сделки.

Обсуждённая историческая проверка этого производного predictor — хронологическая, с прогнозом до раскрытия исхода, учётом задержанных/перекрывающихся labels, настройками из более ранних данных и отдельным последующим оцениванием. Используются Brier/log loss и отдельная проверка калибровки; эти scores не объявляются чисто calibration error. Из одних sealed дневных buckets нельзя восстановить, когда были доступны labels: без такого доказательства результат помечается ретроспективным и OOS-превосходство не заявляется. Проверка фиксированного выбранного профиля не выдаётся за проверку всей процедуры оптимизации. Это не поручение запускать широкую testing/production-кампанию, новый поиск, сбор факторов или рыночную догрузку.

**Переход и приёмка.** Только новые рекомендации новой явно определённой ревизии используют predictor сразу в caption и графике. Старые OLS/сглаженные артефакты, рекомендации, уже сохранённые PNG, queued/frozen outbox bytes и отправленные сообщения сохраняются; resend, переименование старой науки и повторный research/replay/gate не выполняются. Недоступность predictor не выключает действующий профиль и не подставляет старый forecast/среднее. Приёмка новой реализации должна проверить TP/SL-only веса и формулу; gross anchor против равных вероятностей; пустые/null/неполные данные; отсутствие prior-only нуля; фиксированный cutoff и плоское продолжение при задержанной отправке; совпадение caption/маркер до округления; ретроспективную маркировку без ложной ранней доступности; разные raw-close/cache keys; смешанные старые/новые версии и fallback; неизменность objective/gate/истории; bounded memory/cache и cleanup success/error/cancel. Сейчас эти требования зафиксированы документально, не выданы за выполненные проверки.

### 11.6. Замена, остановка и история

**Независимые профили — delta от 16 ноября 2026.**

**Две подсистемы и единственная граница взаимодействия.** Research владеет очередью, своей конфигурацией/ревизией, текущей цепочкой, frozen input/checkpoint и её отменой/cleanup. Adaptive live владеет профилями, их Stop/Play, принятыми снимками, pending/active-версиями, прогревом, leases, readiness, cursors, watermark и публикацией. Research не управляет жизненным циклом профилей; live не запускает/возобновляет исследование, replay или gate. Общие DB, сервис данных и ресурсные лимиты допустимы, но ожидание либо отсутствие research не является запретом работы live.

- **Идентичность.** Логический профиль уникален по `K = user × algorithmId × minSetupsPerDay`. Используется существующая точная числовая нормализация порога: `4` и `4.0` — один ключ, разные значения не склеиваются округлением. `profileId` устойчив при заменах и Stop/Play; принятое поколение — неизменяемая версия его параметров, а не новый независимый профиль с дублирующим K. У профиля отдельно хранятся последнее принятое поколение, pending-кандидат и фактически действующее поколение. Термин «слот» ниже означает этот же профиль/ключ, а не членство в исследовательской очереди. Пользователи, разные алгоритмы и пороги изолированы, в том числе при совпадающих параметрах.
- **Передача завершённого результата.** Только атомарный finalize всей исходной цепочки с проходным gate и полным снимком создаёт durable handoff `ProfileCandidateReady`, уникальный по исходному поколению и содержащий K, идентификаторы исследования/поколения, версию формата и проверяемую ссылку на неизменяемый снимок. Один completed search без post-chain не создаёт handoff. Событие фиксируется вместе с finalize, затем независимо и идемпотентно принимается live; повтор/потеря ACK не создаёт второй профиль или повторную замену. Порядок принятых версий проверяется, запоздавшая доставка старой версии не вытесняет новую. Нет распределённой транзакции с прогревом: исследование завершено независимо от дальнейшей готовности live, очередь не ждёт её.
- **Независимые fences.** Research run/config revision и research lease защищают finalize/handoff до его commit. После него действуют отдельные profile control revision, accepted-generation identity и live lease/epoch; дальнейшая смена research-конфига, его Stop/Start, maintenance или отсутствие процесса не делают принятый снимок устаревшим. Уже committed handoff остаётся допустимым после research Stop; если Stop выиграл гонку до finalize, устаревший исполнитель не создаёт handoff. Stop самого профиля fences позднюю promotion и hot commit независимо от research. Общие locks не должны превращать heartbeat live в ожидание долгой исследовательской операции.
- **Разрешения.** Сохраняются прежние область действия и смысл `adaptiveEnabled` как общего разрешения адаптивного live, а также общий выключатель live. Отдельный `profile.desiredRunning` — дополнительный слой; сканирование/публикация требуют всех применимых разрешений и фактической готовности. `research.desiredRunning` в эту проверку не входит. Принятие результата, research Start и profile Play не включают `adaptiveEnabled` или общий live. Их хранение/API отделяются от research-конфига: редактирование очереди не меняет live-разрешение, а его выключение не стирает выбор Stop/Play отдельных профилей.
- **Первое принятие и замена.** Первый проходной handoff создаёт профиль и допускает независимую инициализацию при разрешённом live; отключённый глобальный live не объявляется активным. Следующий проходной результат обновляет только тот же K, даже при худшем score, с прежней fenced watermark-заменой. **Утверждено Q2:** вручную остановленный профиль остаётся остановленным и при новой принятой версии; параметры обновляются без скрытого Play.
- **Настраиваемый допуск Q5.** Начальная конфигурация на пользователя: всего не более **50** самостоятельных профилей, одновременно active/warming — не более **30**; pending/ожидающий запуск резервирует место, чтобы параллельные команды не обходили лимит. Замена поколения того же K не создаёт новый профиль и не расходует второе место. Превышение при новой связке/возобновлении даёт видимый код/лимит, сохраняет научный результат и не вытесняет incumbents. Источник лимитов — валидируемая внешняя конфигурация с начальными значениями 50/30, не зашитые в алгоритм константы. В дальнейшем это гибкая настройка внешне управляемого пользовательского профиля: системный администратор или subscription tier задаёт индивидуальные лимиты. Обычные profile/research API не дают пользователю повышать собственную квоту.

**Инициализация, обработка и замена.** В следующих правилах Stop означает Stop конкретного профиля, а revision/fence — его live-управление, не ревизию исследовательского процесса.

- **Независимая live-инициализация (решение владельца от 14 ноября 2026).** После исходных frozen replay/аналитики и gate сохраняется неизменяемый снимок: версия и полные параметры алгоритма, effective analytics, направление, выбранные TP/SL, time-shift/ценовое условие и исторические метрики с происхождением. Для пользователя × алгоритма × порога live прогревает собственное состояние по доступным текущим закрытым свечам с теми же настройками и зафиксированным набором инструментов. Нельзя подменять его текущими UI-defaults, новым глобальным списком или молча сокращать universe; недостаток данных по инструменту показывается как его неготовность. Начальная граница, текущая граница чтения и состояние live фиксируются отдельно от исследования; равенство research-префиксу, его fingerprint/cutoff или bootstrap не является условием готовности. Проверка полноты/валидности live-входов и отсутствие lookahead обязательны, но новый расчёт доходности/gate по ним не выполняется. Исторический `minSetupsPerDay` не обещает будущую частоту live-сетапов.
- **Готовность по инструментам.** Как и в обычном live, недостаточная база нового листинга, устаревший ряд или ожидание данных одного инструмента не блокируют готовые инструменты. Профиль может активироваться, когда готов **хотя бы один** инструмент, а **каждый** инструмент объявленного universe явно учтён: готов либо ожидает с конкретной причиной, включая отдельную техническую ошибку. При нуле готовых профиль не объявляется ACTIVE. Universe сохраняется полностью; ожидание не является исключением инструмента или фиктивным успешным обследованием его минут. Ошибка транспорта, неполная пагинация или parse/validation failure остаются технической ошибкой источника, не переименовываются в отсутствие свечей/недостаточную базу. Готовые инструменты продолжают обработку, ожидающие получают ограниченное справедливое восстановление и явно видимые причины неготовности.
- Готовность live отделена от готовности результата исследования. Прежний принятый вариант продолжает работать во время прогрева и догоняющей обработки кандидата. При указанной готовности профиля атомарная fenced-замена проверяет owner/revision/lease, актуальность кандидата и полный объявленный scope с учтёнными состояниями всех инструментов; CAS/fence не сужается до готового подмножества. Фиксируется watermark публикации: старое поколение отвечает за закрытия до него включительно, новое — после него, только по фактически готовым инструментам. Watermark не является доказательством потребления свечей: checkpoint/cursor каждого инструмента отражает только реально обработанные данные, а для ещё не обработанного инструмента остаётся явно отсутствующим, без фиктивного продвижения к общей границе. Независимая инициализация не отменяет причинные cooldown/кластеризацию и дедупликацию внутри слота; совпадение параметров разных слотов не объединяет их состояния.
- Позже готовый инструмент присоединяется к **тому же** активному профилю/поколению с теми же неизменяемыми настройками и рекомендациями, без нового исследования или перепроверки победителя. Его ограниченный прогрев/догоняющая обработка продвигают реальное состояние с выключенной публикацией; при готовности под тем же полным scope/CAS/fence фиксируется собственный publication floor, не раньше watermark поколения. Публикация разрешена только для закрытий после этого floor; прогрев не выдаёт исторические сигналы как свежие и не создаёт вымышленных consumed cursors. Ожидавшие/непригодные минуты остаются честно обозначены, а не объявляются непрерывно обслуженными.
- **Микропакеты checkpoint одного слота.** Для горячего adaptive-пути требуется bounded-транзакция по нескольким инструментам одного owner/слота/поколения/ревизии, с пределами строк, байтов, dwell, RAM и времени I/O; состояния разных слотов не объединяются. Порядок блокировок детерминирован, а для каждого инструмента независимо сохраняются точный предыдущий checkpoint/CAS, source proof, fences и publication floor; полный объявленный scope не сужается. Checkpoints, новые сетапы и соответствующие outbox-записи фиксируются атомарно, с прежней дедупликацией и durability. Спекулятивное RAM-состояние принадлежит незавершённому микропакету и не становится подтверждённым до ACK; при неоднозначном ACK сначала сверяется точный durable successor, не только ID поколения. Отказ/отмена освобождают bounded-буферы после drain; неподтверждённое состояние не выдаётся за обработанные минуты. Разбиение и повтор пакета сохраняют точный причинный паритет и историю.
- **Приоритет восстановления и справедливые joins.** После cold restart реконструкция ранее готовых инструментов получает приоритет, чтобы восстановить горячую обработку; waiting-инструменты при этом продолжают получать ограниченную долю работы без голодания. Число одновременных joins, минуты/байты чтения, CPU-время и RAM одной попытки и всего tick ограничены. Курсор справедливого обхода сохраняется между tick, не сбрасывается на начало universe при каждом повторе: большой хвост waiting не вытесняет ready-трафик и не оставляет последние инструменты без обследования. Неготовая попытка освобождает ёмкость с видимой причиной/backoff; смена поколения, Stop, отмена и shutdown fences/drain исключают позднее применение. Лимиты не дают права укорачивать базу/историю, исключать инструменты, продвигать cursor к текущему времени без обработки или ослаблять source proof/publication floor. Это требования следующей оптимизации, не отчёт о готовой реализации.
- Ожидание данных/ресурса и техническое восстановление live выполняются ограниченно для каждого слота: попытка имеет конечный бюджет, retries/backoff и совокупная память/число ожидающих кандидатов ограничены; ошибка и следующая попытка видимы. Неудачная попытка освобождает ресурсы после drain и не удерживает round-robin-очередь исследований бесконечно. Восстановление повторяет только инициализацию того же неизменяемого кандидата на доступных закрытых свечах, не старые research/replay/аналитику и не пересчёт рекомендаций. При новом кандидате того же слота устаревшие попытки fenced; Stop и смена ревизии также исключают позднюю активацию. Исследовательская очередь продолжает остальные алгоритмы/пороги независимо от такого ожидания, с общим ресурсным допуском.
- **Supervision и штатный рестарт (решение владельца от 15 ноября 2026).** Единственная owned live-инициализация продлевает короткую lease независимо от чтения/CPU/persistence и долгих owner-lock очередей, только при прежних fences, внутри фиксированного шестичасового окна и конечного бюджета без подтверждённого прогресса. Временный timeout/lock-wait/statement-cancel heartbeat сам по себе не означает потерю supervision: продление повторяется с коротким server-side timeout внутри последнего подтверждённого срока lease за вычетом защитного запаса; неуспешная или неопределённая запись этот срок не продлевает. Подтверждённый отказ fences прекращает владение сразу, недоступность продления — только при достижении безопасной границы lease. Heartbeat изменяет только fenced-строку warmup-lane, без advisory owner lock и row-lock process/slot; диагностика отражает последовательность повторов и оставшийся запас lease. Потеря supervision прекращает новый допуск, дожидается уже допущенной работы и запрещает позднюю promotion; действующий incumbent не сбрасывается. При чистом graceful shutdown после drain ещё действующая warmup-lease нейтрально освобождается с возвратом оплаченной попытки и fencing старого worker; исходный initialization anchor сохраняется. Истёкшая lease принудительно не освобождается: recovery учитывает её как платную неудачу. После рестарта новый claim получает новое шестичасовое окно; владелец явно допускает неограниченное число рестартов и такое продление бюджета, но уже исчерпанный лимит автоматически не пополняется. Обслуживание не сбрасывает действующие live-профили, checkpoints и результаты прошлых исследований; их штатное восстановление и дальнейшая работа не зависят от сохранения текущего незавершённого research.
- **Явный повторный live-допуск исчерпанного кандидата (решение владельца от 14 ноября 2026).** Авторизованный владелец может отдельной fenced-операцией с точными generation/profile/control revision и устойчивым ключом идемпотентности предоставить тому же завершённому принятому кандидату **новый ограниченный live-бюджет в три попытки** независимой инициализации. Обычное исчерпание не пополняет бюджет автоматически: накопительный счётчик оплаченных попыток не обнуляется, явный grant увеличивает лимит с 3 до 6 при трёх использованных попытках; следующий grant с другим ключом возможен только после повторного исчерпания бюджета и новой проверки всех fences. Размер добавления всегда равен трём, задаётся сервером и не выбирается вызывающим. Нейтральный fenced-yield сохраняет штатный возврат одной оплаченной попытки (claim 4 → release 3 → повторный claim 4), не стирая ранее завершённые неудачи.
  Durable-квитанция до перехода сохраняет наблюдаемые прежние счётчик, лимит, статус, последнюю ошибку и имеющиеся диагностические времена, но не выдумывает отсутствующую историю отдельных попыток; повтор того же ключа возвращает исходную неизменяемую квитанцию даже после нового исчерпания, Stop или смены profile revision, не выдаёт бюджет и не восстанавливает указатели повторно. Допуск возможен только для последней принятой версии этого профиля при актуальном profile fence и разрешённом live, без конфликтующего pending-кандидата/занятой warmup-lane. Требования «research запущен», совпадения с текущей research config revision и отсутствия более нового research nonpass/no-winner снимаются: эти события не отзывают принятую live-версию (утверждено Q1). Supersession новым принятым handoff и profile Stop исключают устаревшую promotion. Операция возвращает тот же снимок в штатный pending/claim/warmup/promotion-путь, сохраняя исходную границу этой попытки инициализации, полный universe, source proof, CAS и publication floors; не объявляет ACTIVE и не повторяет research/replay/gate. Исследовательские retries/config/очередь/дедлайны/leases и другие профили не меняются. После исчерпания добавленных трёх попыток автоматического нового grant нет. Связь явного grant с кнопкой Play утверждена Q4: при исчерпании Play атомарно выдаёт ещё три попытки с durable-квитанцией; повтор того же запроса не пополняет бюджет.
- **Результат без замены — утверждено Q1.** Completed nonpass/no-winner, ошибка, отмена или незавершённая post-chain не создают live-handoff и не меняют прежние принятые/pending/active-поколения, Stop/Play или readiness профиля. Старый профиль продолжает работать, если был разрешён; если его не было, отсутствие результата не создаёт пустой live-профиль. Техническая ошибка остаётся ошибкой research с его ограниченными повторами, не качественным nonpass и не командой live. Это заменяет прежнее правило деактивации слота при нормальном nonpass/no-winner.
- **Происхождение.** Последний итог research, последняя принятая версия профиля, pending-кандидат и реально сканирующее поколение различаются и содержат собственные study/generation IDs. Граница научного завершения — атомарный finalize всей цепочки, не один `optimization_studies.status='completed'`. Новый nonpass не подменяет метрики действующего профиля, а новое accepted-поколение не объявляется сканирующим до promotion. Текущее исследование показывается отдельно, не как новая сохранённая рекомендация. Mean/forecast/blend, λ и пороги остаются из immutable spec соответствующей версии, не текущего редактируемого research-конфига.

**Пользовательские операции и история.**

- **Stop исследования.** Команда выбранного исследовательского процесса запрещает его новый admission, меняет только research fence и фиксирует точный набор собственных незавершённых queued/running-ID, downstream-работ и неполных материализаций **до** изменения статусов. Далее — кооперативная отмена, ограниченный drain и адресный cleanup; `stopping` видим до подтверждённого завершения. Live-профили, их управление, leases, accepted/pending/active-версии, checkpoints и доставка не затрагиваются. Выбранный ID отслеживается после `cancel_requested/cancelled/failed`, перед удалением повторно проверяется завершённость: успешно завершившиеся при гонке исследование/ребёнок сохраняются. «Удалить все неуспешные/все терминальные» запрещено. Frozen input и приватные checkpoints отменённой цепочки освобождаются после drain; эта цепочка не возобновляется после рестарта или следующего Start.
- **Настройки и новый Start исследования.** После research Stop/drain пользователь меняет параметры/список связок и запускает новый обход. Каждый новый запуск после остановки получает новый research run/chain и **новый study ID**, новый фактический start/cutoff и собственный бюджет; ни старый поиск, ни его cleanup targets не переиспользуются. Повтор той же команды Start при уже запущенном процессе идемпотентен и не порождает второй поиск. Start или смена конфигурации во время `stopping` дают 409 с наблюдаемым состоянием, без скрытой гонки cleanup с новым исследованием. Research config revision не инвалидирует live. Для настройки research достаточно остановить **исследование**, не профили; отсутствие активных профилей не является условием сохранения.
- **Stop отдельного профиля.** Адресная идемпотентная команда устанавливает `desiredRunning=false`, меняет profile control revision и fences только его scan/warmup/joins/promotion и допуск новой публикации. Уже допущенная работа дренируется с конечными бюджетами и видимым `stopping`; после ACK старого worker нет позднего commit/активации. Принятый immutable снимок, происхождение, подтверждённые checkpoints, watermark, дедупликация и прежние сигналы сохраняются для Play; Stop не является удалением. Другие профили, fixed live и вся research-очередь продолжают работу. Уже подтверждённые отправки не отзываются; ещё не допущенные к отправке jobs этого профиля завершаются штатным terminal status/accounting без переписывания frozen bytes и не оживают после Play. Исход внешней отправки, начатой до Stop, отражается честно по signals.md, а не обещанием отменить уже совершённый внешний эффект.
- **Play отдельного профиля.** Явный запуск не запускает исследования: он допускает повторную независимую live-инициализацию из принятого immutable generation snapshot профиля с прежними lease/supervision/readiness/source-proof/CAS-правилами. Для нового периода работы сохраняется отдельный live activation epoch/anchor; source study/generation не переименовывается в новое исследование. Прогрев и пропущенный из-за остановки период не публикуются задним числом как свежие; publication floor не раньше новой границы допуска и прежнего watermark, cursors не продвигаются фиктивно. Профиль становится ACTIVE только по фактической готовности. Пока общий live/`adaptiveEnabled` запрещён, показывается блокирующая причина, скрытого включения нет; повтор Play не создаёт параллельный прогрев. **Утверждено Q4:** используется последняя принятая версия; Play всегда допускает штатный запуск в пределах общих разрешений/квот, при исчерпании атомарно выдаёт +3 попытки с квитанцией. Повтор запроса не даёт нового grant; retries не обнуляются.
- **Сохраняемая история.** Завершённые исследования, включая completed nonpass/no-winner, прежние failed/cancelled-записи и все завершённые служебные replay-результаты не являются целью research Stop-cleanup. Каждый завершённый дочерний прогон/набор сохраняется, даже если downstream не завершён; неуспешный родитель не даёт права каскадно удалить успешных детей. Immutable снимок остановленного профиля также не является незавершённым research-артефактом. Manual/чужие артефакты и общие кеши не затрагиваются. Раздельные fences не дают устаревшему research-исполнителю создать новый handoff, а остановленному live-исполнителю — включить профиль.
- Активные и завершённые исследования видны в существующей истории с происхождением manual/continuous; завершённые служебные replay — в истории запусков со связями цепочки. Метки аддитивны, legacy без признака continuous считается manual. Для continuous нет построчной Stop исследования/служебного прогона: используется **только research Stop** соответствующего процесса, без live-деактивации. Явное удаление терминальной записи запрещено при нарушении ссылок **в том числе остановленного** профиля/сохраняемой цепочки. Stop/Play профиля не удаляет научную историю.

**UI.** Таблица самостоятельных профилей загружается независимо от research-процессов и содержит отдельную колонку управления Stop/Play каждой строкой с доступным именем, состоянием команды и повторным чтением подтверждённого серверного состояния. Существующие профили не исчезают из таблицы после research Stop или, по Q3, удаления связки из очереди. Кнопки «Остановить исследование»/«Запустить исследование», форма и состояние research находятся отдельно: ни подписи, ни disabled-условия не подразумевают остановку профилей. Матрица основных статусов/цветов от 16 ноября в [UX S-00](ux.md#s-00-оптимизация-параметров-алгоритма) сохраняется: подтверждённый ACTIVE не перекрашивается из-за следующего исследования/кандидата или ошибки процесса, readiness остаётся в popup, проблемы показываются отдельно. Источник статуса становится самостоятельным profile DTO; новый research nonpass не делает действующий профиль `rejected`, а research Stop — `stopped`. Исторические описания общей Stop/nonpass-деактивации и transport-кнопки recovery в UX требуют синхронизации после решения владельца, а не сохранения старой связанности в UI. Polling остаётся серийным, 3/15 секунд, без скрытых вкладок и без запуска работ через GET.

**Проект API.** Авторизация владельца и существующие Origin/CSRF guards обязательны; `ownerId` не берётся из произвольного тела запроса. Команды fenced, с ожидаемыми profile revision/accepted generation и устойчивым ключом идемпотентности; повтор ACK не является новым grant или новой активацией. Неизвестный/чужой профиль — 404, stale revision/переход/занятая попытка — 409, исчерпанный admission — 429 с причиной. Ответ принятой команды содержит подтверждённые intent/revision/operational status, не безусловный `ACTIVE`.

|---|---|

Существующие maintenance API §11.1.1 остаются неизменными. Legacy transport Start, использовавшийся как recovery, нельзя сохранить одновременно с обещанием нового пользовательского Start без разделения действий и согласованного перехода клиентов.

### 11.6.1. Явная очистка прошлой continuous-истории

Исключение подтверждено владельцем 13 ноября 2026. Это отдельное owner-wide действие для всех алгоритмов, не часть Stop и не автоматическая retention. Preview показывает точные counts, eligibility и fingerprint; подтверждённый запрос повторно проверяет их в транзакции. Все research-процессы должны быть stopped/drained, без незавершённых дочерних работ; активные/ожидающие профили проверяются **отдельно**, research Stop их больше не останавливает. Смена preview даёт 409. Нет скрытого Stop профилей, частичного успеха или удаления данных других владельцев.

**Адаптация к независимым профилям — утверждено Q7.** Обычный profile Stop сохраняет возможность Play и ссылки принятого снимка. Поэтому одной остановки всех работ недостаточно для удаления поколений: cleanup/построчное удаление возвращает 409 для любого referenced accepted/pending/active-поколения, включая остановленный профиль. До отдельного решения владельца о подтверждаемом удалении/отвязке профиля такое происхождение защищено. Не допускается молча очищать принятый snapshot под видом Stop или считать research Stop разрешением на каскад. Описанный ниже прежний состав полной очистки применим только после согласованного снятия этих ссылок; сам этот delta не разрешает их удаление.

Удаляются только continuous-исследования, поколения и внутренние checkpoints/warmup/outbox/runtime-результаты. Сохраняются все replay runs/batches/quality, общие replay/analytics-кеши, опубликованные fixed/adaptive live-сетапы с неизменными identity/recommendations, market-data, настройки/общий черновик и configured slot identities. Независимый сохранённый post-chain `result.analytics` архивируется один раз на retained batch вместе с происхождением; полные research spec/result/bootstrap tombstones не сохраняются. Слоты остаются конфигурацией, их старые результаты/указатели очищаются. При удалении своих adaptive outbox jobs фиксируется честный terminal delivery status, глобальный budget корректируется штатным accounting; fixed/чужие jobs не затрагиваются. Fencing исключает позднее восстановление очищенных данных, повторная очистка возвращает нулевые удаления.

Терминальные оставшиеся исследования и исторические runs/batches допускают отдельное построчное удаление с подтверждением. Живые ссылки действующего, остановленного или неочищенного профиля/поколения дают 409 с объяснением зависимости: один Stop их не снимает, требуется отдельно согласованное разрушительное действие по Q7; архивное происхождение после допустимого cleanup само по себе не блокирует удаление. Удаление выбранного исторического набора не является глобальной очисткой кешей или аналитики.

Вместе с post-chain матрицей сохраняются точные effective analytics-параметры победителя (кластеризация/gap, time shift, ценовой gate, maturity, horizon) и направление исходного исследования; неизвестные legacy-поля не подменяются текущими настройками. Архив доступен без пересчёта через необязательное поле деталей retained batch, но не загружается в списки запусков. Он не содержит полный best/spec/bootstrap и хранится один раз на исходный batch, не на каждый дочерний run.

### 11.7. Приёмка этапа 2

- Round-robin по алгоритмам × списку порогов не превращается в глобальный busy-lock; при continuous доступны ручные исследование, replay и аналитика. Каждый период фиксируется при фактическом старте, не enqueue, и не меняется между стадиями.
- Последние N суток включают незрелый правый край без horizon lag: единый `observationCutoff ≤ start` не движется при долгом чтении/смене инструмента/стадии, свечи с более поздним закрытием не попадают в снимок. Незавершённые/ненаблюдавшиеся исходы не попадают в R/performance и не выдумываются, цензурирование видно; число уже открытых eligible-входов по-прежнему участвует в частоте.
- Одинаковые frozen input и bootstrap дают одинаковые сигнальные идентичности, eligible-счётчики и матрицы в исследовании, служебном replay и аналитике; старый общий кеш, округлённый alias цены и lossy-чтение не проходят эту проверку.
- Поздняя догрузка или отличие live-префикса не отменяет завершённое исследование и не запускает повторный gate/revalidation. Независимый live использует его неизменяемые настройки/universe, собственные текущие закрытые свечи и причинный прогрев; readiness не выдаётся без данных. Отказ/таймаут одного слота сохраняет incumbent и не блокирует round-robin; восстановление не запускает повторную оптимизацию старого победителя. Проверяются fenced watermark-замена, отсутствие повторов, ограниченность ресурсов и неизменяемость старых результатов/рекомендаций.
- Checkpoint-микропакеты и waiting joins проверяются при горячем ready-трафике, большом ожидающем scope и cold restart одновременно с исследованием: точный паритет, all-scope/per-instrument CAS и source proof, атомарность checkpoint/сетапов/outbox, потеря ACK после реального commit без продвижения неподтверждённой RAM и дублей, неизменность истории/publication floors. Ранее ready восстанавливаются приоритетно, но waiting-круг доходит до последних инструментов; повторы/отмена освобождают память, ресурсные лимиты соблюдаются. Полный нагрузочный и latency-контракт — [capacity.md](capacity.md#актуальный-live-контур-решение-от-13-ноября-2026).
- Clustering on означает locked maturity 0 и первый raw-сигнал; цепь внутри gap не превращается в throttle от последней публикации. Off применяется одинаково в расчёте и live; ручная ретроспективная зрелость сохранена.
- Допуск проверяет всю матрицу без округления по 0.15 R, а рекомендация — median-capped формулу и порядок ничьих, включая края, singleton и невалидную ячейку. В сообщении различимы собственное R и среднее матрицы; time-shift не задерживает отправку и не создаёт автоматического контроля будущей цены.
- Проходной handoff меняет только профиль того же K и допускается при ухудшении score; повтор и перестановка доставки не создают дубликат/откат версии. По решению Q1 nonpass/no-winner/failed/cancelled не меняют профиль или ранее принятого кандидата. Stop исследования fences только новый finalize, фиксирует точные незавершённые ID до смены статуса и очищает их после drain; завершённая история и успешные дети сохранены. Настройки research меняются без Stop профилей; новый пользовательский Start после cleanup получает другой study ID/start/cutoff.
- Profile Stop/Play действует адресно при остановленном/отсутствующем research и не меняет другие профили/fixed live/очередь. Проверяются гонки Stop с handoff, promotion, микропакетом и внешней отправкой; поздняя активация fenced, подтверждённые сигналы/снимки не переписываются. Play проходит штатный причинный прогрев, не replay исследования; глобальные разрешения соблюдаются, retries не обнуляются. Матрица badge/readiness остаётся независимой от research, колонка управления отдельная.
- Миграция шести исходных incumbents №17–22 сохраняет pairing keys, generation/slot identity, снимки, profile intent, фактические cursors, watermark/floors и дедупликацию; повтор backfill/restart не делает их stopped или новыми сигналами. Смешанный режим несовместимых старых/новых fences не допускается. Maintenance drain/resume §11.1.1 проходит прежние сценарии с теми же ID/входами/дедлайнами, не вызывая пользовательского Stop/Start.
- Continuous-исследования появляются в существующей истории с меткой происхождения, без построчной Stop; API не позволяет обойти research-owner stop. Удаление уважает ссылки, в том числе остановленных самостоятельных профилей по Q7. Проверяются ответы авторизации/stale revision/старого API и идемпотентность команд. Ни один сценарий не выставляет ордер на бирже.

Исследовательские формы/кнопки/черновики и recovery отдельно; восстановление сохранённых mean/forecast/blend/порогов не меняется. Не опрашивать скрытые панели, не выдавать stale DTO за подтверждённый переход. |
| P6 | Изолированная приёмка | Сначала focused Rust/реальный PostgreSQL и web regression ниже, затем локальная rehearsal миграции на совместимом снимке с шестью incumbents; race/fault injection только в тестовом окружении. Проверить отсутствие legacy process-live joins/fences на всех write-paths, лимиты и освобождение RAM/leases/буферов при многократных Stop/Play/replace/cancel. Нагрузочный контур не расширять без отдельного задания. |
| P7 | Будущий rollout, отдельное разрешение | Только после утверждения и приёмки — штатное обслуживание по §11.1.1, без пользовательских Stop/Play. Сохранить исходный maintenance-флаг, profile intent и recovery. Проверить фактические курсоры/сетапы, совместимый startup и resume прежних цепочек; затем снять только собственную maintenance-паузу. Отменённый deploy не возобновляется этим планом. |

**Конкретные точки текущей связанности, подтверждённые локальным чтением исходников.** `crates/db/src/continuous.rs::{configure,stop}` сбрасывают slot live-указатели и warmup; `active_adaptive_slots` фильтрует `p.desired_running`; `continuous/live.rs::pending_adaptive_slots` дополнительно требует текущую research config revision. `continuous/scheduler.rs::finalize` на negative-исходе очищает active/pending; `continuous/readmission.rs::grant` требует работающий process и запрещает более новый completed nonpass/no-winner. Это обязательные точки разделения, не перечень всех необходимых правок. Rust-пути здесь указаны относительно `services/setups-platform-rs`; worker store/promotion/supervision/delivery и API routes проверяются по всем вызываемым DB fences. В web основная поверхность — `apps/web/src/routes/continuous-study.tsx` и её API/тесты; чужие параллельные полосы не редактируются до распределения работ.

**Миграция существующего состояния.** Исходные данные владельца: шесть действующих incumbents поколений №17–22 в шести связках. Это вход миграционного требования, не результат нового обследования сервера при подготовке PRD.

1. Перед будущей миграцией получить авторизованную read-only inventory шести K/slot IDs, active/pending generations, permission/intent, leases/retries, universe/readiness, checkpoint/cursor, watermark/floors и outbox/dedup references. Несовпадение не исправлять предположением «включить всё»; уточнить актуальный набор, не меняя состояние.
2. Аддитивный expand/backfill идемпотентно создаёт самостоятельные профили с теми же устойчивыми slot/profile IDs и связями поколений №17–22. Исторические `spec/result`, рекомендации, научные hashes, исходные timestamps и идентичности сигналов неизменны. Config-only слоты без принятого результата остаются research-очередью, не становятся фиктивными действующими профилями. Для прочих существующих состояний намерение выводится из подтверждённого прежнего live-состояния, не из defaults.
3. Перенести/связать actual checkpoints, принятый snapshot, readiness, active/pending pointers, retry accounting и pending-доставку без очистки и нового research/warmup действующих профилей. `adaptiveEnabled` сохраняет прежнее значение и область. FK/алиасы должны сохранить прежнюю дедупликацию и ссылки на источник; смена таблицы не является новой identity.
4. Сначала все readers/writers понимают оба формата через совместимый адаптер, затем единая fenced-граница включает независимый controller. На каждом профиле только один авторитетный live-owner/epoch; одновременно исполняемые старый и новый controllers недопустимы. Старый runtime не должен после backfill обнулить новый профиль своим process Stop/configure. Нельзя включать UI новой семантики раньше завершения перехода write-paths.
5. Подтвердить сохранённые K/IDs и intent, **продвижение** всех ранее готовых cursors, фактические signal/delivery IDs без потери/дублей, честное ожидание остальных инструментов, recovery текущей цепочки и прежний maintenance-флаг. Продолжение уже активного поколения после restart не получает новый publication floor, скрывающий пропущенный интервал; новые floors относятся к настоящему Play/замене. Применяется обычная durable migration с короткой cold gap по Q8, без standby и пользовательского Stop.
6. Пока независимое управление не включено, возможен только заранее проверенный совместимый откат expand-фазы. После новых profile-control state/формата нельзя запускать несовместимый старый бинарник или восстанавливать указатели по текущему research-конфигу; нужен совместимый forward fix/отдельная проверенная стратегия. Снимки/история не удаляются ради rollback. В текущем docs-поручении ни inventory сервера, ни migration/deploy не выполняются.

### 11.10. Изменённые гарантии и риски

- **Остановка меняет смысл.** Research Stop больше не является способом выключить adaptive live, а research config revision больше не отзывает принятые поколения. Полагавшийся на старую семантику пользователь/клиент должен увидеть отдельные команды; ошибочное сохранение хотя бы одного process fence снова свяжет подсистемы или выключит профиль поздним commit.
- **Качество не является live-командой (Q1).** Прежнее «nonpass отключает слот» заменяется сохранением incumbent. Плохой новый итог виден в research, не скрыт, но сам по себе не отзывает старую рекомендацию. Автоматическая давность/качество-disable не добавляются без нового продуктового решения.
- **Управление и принятый результат могут гоняться (Q2/Q4).** Ручной Stop сохраняется при замене; Play берёт последнюю принятую версию и при исчерпании выдаёт идемпотентный +3 grant без сброса счётчиков. Неоднозначные actions/fences ведут к неожиданному включению либо бесконечному бюджету; готовность не следует из `desiredRunning=true`.
- **Новый долговечный владелец.** Profile snapshot/checkpoints больше не живут до research Stop или удаления порога. Нужны отдельные admission/count/byte budgets (Q5), FK-защита и политика удаления (Q7); нельзя освободить принятый снимок вместе с временным frozen input или держать историю всех версий в RAM.
- **Maintenance не перепроектируется.** Исходные durable input/checkpoint, recovery retry accounting, deadline, lease safety и drain/resume §11.1.1 сохранены; отдельно меняются только пользовательские intent/transport-команды. Текстовая совместимость названия Start не оправдывает продолжение user-cancelled head.
- **Миграция — не пересоздание профилей.** Потеря slot/generation identity, cursors, дедупликации или outbox links нарушит непрерывность сигналов и происхождение. ACTIVE в API не доказывает работоспособность. По Q8 допускается короткая cold gap замены контейнера с durable продолжением без standby; несовместимый rollback и смешанные исполнители запрещены.
- **Неизменяемые гарантии.** Научные окна/метрики и mean/forecast/blend/gates, причинность, readiness всех инструментов, bounded supervision, atomic checkpoint/setup/outbox, публикационные floors, история/доставка по signals.md и отсутствие ордеров не ослабляются. Это изменение владения и управления, не новый поиск, revalidation или массовая пересылка старых сигналов.

## 12. Аналитика выпущенных сетапов (18 ноября 2026)

### 12.1. Область и фильтры

- Анализируются сохранённые адаптивные live-сетапы (`live_setups` с непустыми `adaptive_slot_id` и `recommendation`) выбранного алгоритма, чей момент выпуска — окончание сигнальной минуты `close_time` — попадает в заданный диапазон, и чьё исследование-основа входит в выбранное множество. Legacy WATCH-сетапы без рекомендации не анализируются: у них нет рекомендованных условий входа.
- Список исследований для фильтра формируется по выбранному диапазону: в него попадают только исследования-основы, для которых в диапазоне выпущен хотя бы один сетап выбранного алгоритма. Исследование-основа сетапа определяется по поколению выпуска (`adaptive_generation_id`; при архивной записи — сохранённый `generationId` из `adaptive_generation_archive`) и его study. Список обновляется при изменении дат/времени диапазона (по потере фокуса полей ввода дат); после обновления все исследования списка снова выбраны. По умолчанию (и при пустом выборе) учитываются все исследования списка.
- Выбранные фильтры (алгоритм, диапазон, выбор исследований) сохраняются локально в браузере и восстанавливаются при возврате в систему; сохранённый выбор исследований применяется к актуальному списку (пересечение), при пустом пересечении — выбраны все.
- «Рассчитать» выполняет разовый серверный расчёт по сохранённым данным; результаты не кешируются ни в БД, ни в браузере и не создают фоновых заданий.

### 12.2. Методика исхода каждого сетапа

- Вход: минутная свеча, открывающаяся в момент `close_time + time_shift_minutes` из рекомендации (та же семантика рекомендуемого времени входа, что в Telegram-caption). Цена входа — **open** этой свечи: цена, фактически стоявшая на бирже в момент рекомендуемого входа, а не минуту позже. Отсутствие свечи — статус «нет данных», в среднее не входит.
- Гейт смещения цены: применяется только при заданном в рекомендации `price_change_pct`; порог повторяет caption-формулу (`passes_price_change`): short — вход только если цена входа не ниже `close_price × (1 + pct/100)`; long — только если не выше `close_price × (1 − pct/100)`; `pct` берётся со знаком из рекомендации, без abs. Непрошедший гейт — статус «гейт не пройден», в среднее не входит, но виден в списке и счётчиках. Без `price_change_pct` гейта нет.
- Исход: уровни TP/SL — рекомендованные проценты от фактической цены входа; сканирование реальных минутных свечей от самой свечи входа (включительно) до горизонта 10 080 минут (тот же default-горизонт, что у существующей аналитики), первое касание; при касании обоих уровней в одной свече приоритет SL (консервативно, как в существующем `evaluate_limit`). Результат в рисках: TP — `+TP%/SL%`, SL — `−1`. Не закрылось в горизонте — «не закрылась», в среднее не входит.
- Кластеризация/зрелость не переоцениваются: рекомендация уже применила их при выпуске; аналитика проверяет только сообщённые условия входа и исход.

### 12.3. Агрегаты и отображение

- Итоговая оценка = `Σ R закрытых сделок / число закрытых сделок` среди прошедших гейт сетапов выбранного множества. Цвет: зелёный при >0, серый при =0 или отсутствии закрытых, красный при <0.
- Фиолетовый лейбл «X/Y»: X — число сетапов, прошедших гейт (включая незакрытые и «нет данных» после гейта не бывает: нет данных классифицируется до гейта), Y — число сетапов, выбранных фильтрами (до гейта).
- Тот же расчёт отдельно для каждого исследования-основы (группировка по study поколения выпуска), с теми же цветами и лейблом «X/Y» своего подмножества. Список исследований-основ отображается таблицей в том же стиле, что список сетапов; колонка «Закрытых» имеет формат `закрыто/всего`, где `всего` — общее число сетапов исследования в диапазоне (setupCount из `/studies`); номер исследования — кнопка `#ID` того же стиля, что кнопка ID в таблице «Последние исследования» (outline/sm), открывающая модальное окно (в полтора раза шире прежнего, `max-w-5xl`): подробности исследования — полные параметры алгоритма лучшего кандидата с подписями полей ввода из настроек алгоритма (label + единица; незнакомый ключ — как есть), аналитические параметры, выбранные оптимальными (сдвиг времени, смещение цены, кластеризация, зрелость сетапа, разрыв кластера, горизонт сделки; для старых исследований без сохранённых — «Не сохранено»), лучшая пара по типу objective — mean/forecast/blend и лучший score — и под ними график «Динамика матожидания: ретроспектива и live» в стилистике Telegram-графика. Слева от разделителя — дневные значения матожидания того самого исторического запуска, который лежит в основе исследования (запечатанные дневные точки expectancy-артефакта, без нового исторического расчёта); вертикальный разделитель — UTC-день старта исследования (createdAt, fallback — граница наблюдения C); справа — средние дневные матожидания реальных сетапов, выданных адаптивным профилем на основе этого исследования (закрытые сделки по дню входа). Точки обоих источников, включая день выпуска, окрашены по знаку (зелёный/красный); в день выпуска (день старта исследования) рисуется одна точка — среднее МО всех сетапов этого дня из обоих источников. Вертикальная дневная сетка строится по каждому дню, подписи дат разрежены. Жёлтая линия — типа, заданного как оптимизируемое матожидание при старте исследования (mean — горизонтальная на объединённом взвешенном среднем, forecast — трендовая прямая/кривая по bend-параметрам, blend — λ-комбинация среднего и прогнозной кривой) и строится фитированием по объединённому ряду «прошлое + live» как по единому источнику данных, поэтому покрывает весь график. График строится заново при каждом открытии модального окна.
- Над таблицей исследований-основ, непосредственно под итоговым средним МО — график «Результаты торговли по дням» в стилистике Telegram-графика МО (тёмный фон, та же палитра, сетка по дням и целым R, маркеры окрашены по знаку). По X — дни UTC (день входа сделки), по Y — средний R закрытых сделок этого дня: суммарный результат закрытых сделок, открытых в этот день, в рисках, делённый на их число. Данные — те же отфильтрованные сетапы, что попали в нижний список сетапов; не прошедшие гейт, незакрытые и без данных сделки не участвуют; при отсутствии закрытых сделок — текстовая заглушка.
- Полный список сетапов — под собственным заголовком раздела (как у списка исследований-основ): колонки и лейблы как в разделе «Матожидание по сетапам» (инструмент, время сетапа, вход, TP, SL, закрытие, результат в R с цветом по знаку, статус-бейдж), дополнительно колонка «Профиль» (ID профиля).

### 12.4. API и границы

- `GET /v1/setups/analytics/studies?algorithmId=…&from=…&to=…` — исследования-основы, выпустившие сетапы в диапазоне: studyId, externalName, число сетапов, generationId последнего выпуска и artifactId (expectancy-артефакт последнего сетапа исследования в диапазоне, для PNG-модали). Тип objective исследования веб берёт из существующего `GET /v1/optimization-studies/{id}`.
- `GET /v1/setups/analytics?algorithmId=…&from=…&to=…&studies=25,26` — полный расчёт: агрегаты, per-study сводка, построчные результаты.
- `GET /v1/setups/analytics/expectancy-png/:artifactId` — PNG артефакта (`image/png`) с существующей авторизацией: сначала сохранённый PNG (legacy-рендеры в `study_expectancy_pngs`); при его отсутствии — детерминированный рендер из запечатанного числового артефакта, без нового исторического запуска: для исследований модельной эры (recipe forecast в source) — model-рендер с маркером на границе наблюдения C и значением запечатанного тренда, для legacy — trend-рендер. Это закрывает 404 у исследований новой эры (#40/#41), чьи Telegram-сетапы рендерятся по-сетапово без сохранения study-level PNG; явная ошибка — только при отсутствии/нечитаемости артефакта или несовместимости рендера.
- `POST /v1/setups/analytics/study-expectancy/:studyId` — запечатанная серия матожидания исследования для модального графика «ретроспектива и live». Тело: `{live: [{dayUnix, meanR, closedCount}]}` — агрегированные дневные исходы реальных сетапов адаптивного профиля (веса — число закрытых), вычисляются вебом из `/setups/analytics?studies=`. Ответ: последний артефакт исследования (`owner=admin`), дневные точки (`dayUnix`/`meanR`/`tpCount`/`slCount`), граница наблюдения, среднее МО за период и жёлтая линия (метод + точки), построенная по типу оптимизируемого МО из spec исследования (serde-дефолты для legacy) фитированием по объединённому ряду «артефакт + live» (без live — только по артефакту); без нового исторического запуска.
- Расчёт ограничен: не более 5 000 сетапов на запрос (явная ошибка при превышении с подсказкой сузить диапазон); свечи читаются по инструменту инкрементально через существующий сервис данных и освобождаются после расчёта; endpoint только читает сохранённые данные с существующей авторизацией.

### 12.5. Приёмка

- Rust-тесты: гейт (short/long, с/без pct), исходы на фикстурных свечах, агрегаты и лейблы, группировка по study, границы (пустой диапазон, превышение лимита, отсутствие рекомендации), мета исследований (список по диапазону, artifactId, PNG-роут).
- Web-тесты: сайдбар и keep-alive подразделов, модальные окна выбора исследований и подробностей исследования с PNG, обновление списка исследований по потере фокуса дат со сбросом выбора, локальное сохранение/восстановление фильтров, цвета/лейблы результатов, колонки списков.
- Приёмка основной сессии: повторные расчёты идентичны, реальный расчёт на данных medved после деплоя.
