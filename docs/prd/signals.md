# Сетапы, экспорт и доставка

[К оглавлению PRD](PRD.md)

Статус: частота решения `closed_bar_1m`, цена close сигнальной минуты, время конца минуты в Unix-секундах и cooldown утверждены. Структура дополнительных экспортных полей предлагается ниже. Сетап не равен ордеру, позиции или гарантированному исполнению.

## 1. Содержание сетапа

Сетап должен отвечать на вопросы: какой инструмент, на какой бирже и рынке, какое условие выполнено, когда оно стало известно, какая опорная цена и откуда она взята, какая версия алгоритма это решила.

Обязательный смысловой набор: биржа, market type, исходный symbol и стабильная идентичность инструмента, время решения, нейтральный тип события, цена и тип цены, стратегия/версия/параметры, частота решения, качество данных, объяснение с численными признаками. Времена биржевого события, решения, сохранения и доставки не смешиваются.

`entry_price` в CSV означает **опорную цену**, а не цену реально исполненной сделки. В MVP это close сигнальной минуты с `entry_price_kind=closed_bar_close`. Сигнал утверждён как нейтральное событие `price_volume_spike` с меткой `WATCH`, не рекомендация LONG или SHORT. Вопрос торгового направления не является открытым требованием MVP. Будущая модель исполнения после задержки будет отдельной версией контракта, а не переименованием старых значений.

`signal_time` соответствует правой границе сигнальной минуты; например, бар `[10:04:00,10:05:00)` даёт время сигнала `10:05:00 UTC`. Фактическое вычисление и доставка происходят после получения закрытой свечи, могут задерживаться и фиксируются отдельно. Время открытия свечи не является временем входного сигнала.

Первый алгоритм проверяет рост цены не менее 12% за настраиваемое окно (по умолчанию последние 5 минут) И оборот USDT этого окна строго больше трёх средних оборотов, приведённых к той же длительности, хотя бы по одной базе: 30 дней ИЛИ 7 дней. Обе полные базы обязательны даже при выполнении только одной ветви OR. Базы заканчиваются сигнальной минутой и включают недавнее окно; дополнительные 5 минут из них не исключаются. Точные минутные формулы определены в [strategies.md](strategies.md).

Объяснение сохраняет рост цены, оборот USDT, обе базы и оба отношения к ним, пороги и признак выполненной ветви: `7d`, `30d` или `both`. USD-подобный объём здесь означает quote turnover в USDT, не количество базового актива. При нехватке непрерывной истории сигнал не формируется; это причина пропуска расчёта, а не результат «условия ложны».

## 2. Предложение CSV v1

UTF-8, разделитель запятая, десятичная точка, стандартное CSV-экранирование. Экспорт сигналов имеет строку заголовков; это не формат импорта списка инструментов. Машинные имена столбцов английские; в UI есть русские подписи. Цены сериализуются без потери точности источника. Unix time в основном столбце задаётся **целыми секундами UTC**; экспортёр не должен угадывать единицу по длине числа.

| Поле | Значение |
|---|---|
| `schema_version` | Версия формата, первоначально `1` |
| `run_id` | Идентификатор исторического запуска или live-сессии |
| `setup_id` | Идентификатор записи результата в пределах принятого контракта |
| `exchange` | Например, `bybit` |
| `market_type` | Например, `linear_perpetual` |
| `instrument_id` | Стабильная идентичность конкретного контракта с учётом его жизненного цикла |
| `symbol` | Исходное обозначение биржи, например `BTCUSDT` |
| `signal_time_unix_s` | Правая граница сигнальной минуты, целые секунды Unix |
| `signal_time_utc` | То же время ISO 8601 с `Z` для чтения человеком |
| `side` | `WATCH`: нейтральное событие, не направление сделки |
| `entry_price` | Опорная цена, не исполнение |
| `entry_price_kind` | Источник/смысл цены |
| `strategy_id`, `strategy_version` | Какая логика сработала |
| `config_hash` | Ссылка на точный набор параметров в описании запуска |
| `decision_resolution` | Всегда `closed_bar_1m` в MVP |
| `replay_mode` | `full_minute_replay` для истории, `not_applicable` для live; детализации и грубого поиска нет |
| `data_quality` | `complete` для минутных данных, необходимых данному сигналу; частичное покрытие всего запуска описывается отдельно |
| `reason_code` | `price_volume_spike` для первого алгоритма |
| `price_change_pct`, `quote_turnover_usdt` | Наблюдаемый рост и оборот недавнего окна |
| `turnover_ratio_7d`, `turnover_ratio_30d`, `qualified_baseline` | Оба отношения к базам и выполненная ветвь `7d`, `30d` или `both` |

Полный набор параметров, выбранные пары, запрошенный/эффективный период, warmup, версии данных и ограничения прилагаются как описание запуска, рекомендуемый машинный формат JSON. В нём также указаны обработанные и пропущенные минуты по инструментам с причинами. Отсутствие пригодных данных не обозначается как успешный поиск с нулём сигналов. Для простого внешнего потребителя предлагается дополнительная проекция из четырёх полей: `exchange,symbol,signal_time_unix_s,entry_price`; она не заменяет полный архив результата.

Описание запуска обязательно связывает `instrument_id` с неизменяемыми метаданными контракта: биржа, тип, исходный symbol и известный жизненный цикл. Переиспользованный биржей symbol не должен объединить разные инструменты при внешнем анализе.

Секунды Unix являются основным форматом, а не дополнительной проекцией. Единица timestamp не означает секундную гранулярность анализа: решения принимаются по закрытым минутам. Неполнота минутной истории явно отражается в результате, а не скрывается за точным форматом timestamp.

Сортировка CSV: время решения, биржа, инструмент, стабильный смысловой ключ. Сравнение повторных прогонов игнорирует технический `run_id`, время формирования файла и транспортные поля, но не время/цену/тип сетапа. Результаты из кэша сохраняют исходное время вычисления и исходный статус частичности; новая дата экспорта не означает пересчёт на новых данных. Управление кэшем описано в [ux.md](ux.md).

## 3. Повторы и неизменность

- Для первого алгоритма cooldown равен 5 минутам на инструмент и алгоритм: новый сигнал допустим при разнице времён решений не менее 300 секунд от предыдущего сигнала. Это только временной шлюз; сброс условия и повторное взведение не требуются. Если условия остаются истинными, повтор на границе 300 секунд разрешён.
- Cooldown одинаков в live и replay и отсчитывается от сигнала, а не от времени доставки. Повтор отправки не создаёт новый сигнал и не сдвигает cooldown.
- Дедупликация результата и дедупликация отправки являются разными задачами.
- Повторное чтение тех же данных и рестарт не должны создавать новый смысловой сетап из-за смены идентификатора процесса.
- Сохранённый live-сетап не удаляется автоматически после исправления исторических данных. У исправления есть причина, время и связь с исходным результатом.
- Изменение версии алгоритма создаёт новые результаты; их нельзя сравнивать как результат одного и того же запуска.
- Исторический replay сохраняет результаты для просмотра и экспорта, но не запускает поток Telegram- или браузерных уведомлений. Отправка тестового сообщения или примера результата выполняется явно.

## 4. UI, браузер и Telegram

Лента сигналов в UI обязательна. Сохранённые сигналы доступны после повторного открытия интерфейса независимо от состояния каналов уведомлений и возраста события. **Web Push входит в MVP на поддерживаемых платформах:** Push API, service worker и показ системного уведомления позволяют получать сообщения без открытой вкладки. Нужны защищённый контекст HTTPS (localhost является исключением для локальной разработки), явное разрешение и запрос подписки по действию пользователя. При отказе, отзыве разрешения или отсутствии поддержки остаётся UI-лента.

Работа без открытой вкладки не означает гарантированную доставку при полном завершении браузера, принудительной остановке приложения, offline, ограничениях фоновой работы ОС или режиме Focus. WebKit документирует доставку в Safari 16 на macOS Ventura и новее даже без запущенного Safari благодаря системному push-процессу; это не универсальная гарантия для всех браузеров. На iOS/iPadOS Web Push поддерживается с 16.4 для веб-приложений, добавленных на Home Screen; обычная вкладка не равнозначна этому режиму. UI сообщает требования конкретного окружения и состояние подписки. Принятие сообщения push-сервисом не доказывает его показ или прочтение.

Telegram опционален: один бот отправляет сообщения в закрытый канал, где ему выданы необходимые права. Настройка адресата и тест доставки доступны администратору, но наличие бота не является условием запуска сканера. Доставка не встроена в алгоритм.

Предлагаемое сообщение:

```text
BYBIT · BTCUSDT · WATCH · price_volume_spike
Алгоритм: price_volume_spike, версия 1
Время решения: 2026-10-28 10:05:00 UTC
Опорная цена: <цена> (close минуты, не исполнение)
Рост за 5 минут: <значение>%
Оборот USDT за окно: <значение>
Оборот к базе 7д / 30д: <значение>x / <значение>x
Выполнена ветвь: <7д / 30д / обе>
Точность: закрытая минута · качество данных: полное
Сетап: <короткий идентификатор>
```

Это пример структуры, не результат наблюдения рынка и не торговая рекомендация.

Сначала результат сохраняется, затем доставляется. Ошибка UI-соединения, браузерного уведомления или Telegram не должна остановить сбор данных или потерять сетап. Статусы и попытки учитываются отдельно по каналам: отключён/нет разрешения, ожидает, отправлен, повторяется, ошибка, просрочен/пропущен по согласованной политике. Повторы ограничены, учитывают возможности канала и ответы сервиса, включая Telegram `retry_after`; отказ в разрешении не вызывает бесконечных попыток. Стабильный `setup_id` используется для дедупликации UI и доставки, а не идентификатор каждой попытки.

Нельзя обещать строгую exactly-once доставку: если Telegram принял сообщение, но подтверждение потерялось, повтор может продублировать его. Стабильный идентификатор сетапа и журнал попыток помогают обнаружить дубль. В UI видны исходное время сигнала и задержка.

### Возраст уведомления

В UI Settings настраивается максимальный возраст уведомления, по умолчанию **1 минута (60 секунд)**. Возраст равен `now_utc - signal_time_utc`, где `signal_time_utc` всегда конец сигнальной минуты, а не обнаружение, сохранение, догрузка или последняя попытка доставки. Условие включительное: при значении по умолчанию `age <= 60 секунд` уведомление ещё допустимо, `age > 60 секунд` означает пропуск с причиной `expired`. Новая попытка не обновляет начало отсчёта и не даёт ещё 60 секунд.

Проверка выполняется перед каждой отправкой и повтором Telegram/Web Push, а также перед показом навязчивого UI-toast. Она не фильтрует постоянную UI-ленту, сохранённые сигналы, историю или CSV. Исторический replay не запускает массовые уведомления даже для свежих минут. После backfill/сбоя применяется тот же возраст, без отдельной льготы на время обнаружения.

Web Push передаёт время сигнала и абсолютный срок допустимого показа. TTL сообщения ограничивается оставшимся бюджетом до этого срока, а не полным значением настройки при каждой попытке; на точной границе допустим TTL 0 (немедленная попытка без хранения offline). Service worker повторно проверяет возраст перед `showNotification` и пропускает просроченное сообщение. UI-toast проверяет возраст перед показом аналогично. Отправленное Telegram-сообщение и дальнейшие задержки внешнего сервиса/ОС не подконтрольны приложению: возраст гарантируется при нашей отправке, но не в момент прочтения пользователем.

### Подписки и ограничения Web Push

Подписки принадлежат app DB; endpoint и ключи подписки являются чувствительными данными, не попадают в логи, CSV, публичные URL и обычный экспорт настроек. Создание/удаление подписки требует аутентификации и защиты от CSRF. UI поддерживает отказ от подписки и показывает отзыв разрешения; приложение прекращает отправки и очищает недействующие подписки, в том числе после постоянных ответов push-сервиса 404/410. Изменение/переиздание подписки не должно оставлять бесконечно растущий реестр старых endpoints. Резервная копия app DB с такими данными защищается как содержащая секреты.

Web Push не используется для скрытого постоянного фонового исполнения. Некоторые платформы требуют видимого уведомления для каждого принятого push; подавление уже просроченного сообщения нельзя превращать в регулярный silent push. При проверке поддерживаемых окружений необходим тест TTL, позднего получения и поведения разрешений: если платформа не позволяет соблюсти контракт, этот канал отмечается недоступным с fallback в UI, а не обещает гарантированную фоновую доставку.

Основания (официальные документы, проверены 1 ноября 2026): [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API), [MDN Notifications API: разрешение и HTTPS](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API), [WebKit: Web Push и ограничения фоновой работы](https://webkit.org/blog/12945/meet-web-push/), [WebKit: iOS/iPadOS Home Screen](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Web Push Protocol: TTL и недействующие подписки](https://web.dev/articles/push-notifications-web-push-protocol).

Токен бота хранится отдельно от экспортируемых настроек, скрыт в UI и логах. Получение торговых ключей биржи для выпуска сетапов не требуется. Основание по API доставки: [Telegram Bot API](https://core.telegram.org/bots/api).
